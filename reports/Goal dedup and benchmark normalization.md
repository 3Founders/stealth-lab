# Link entities first, merge by redirect, score per instance

Kel should get maximal Goal deduplication without over-merging by adding the one stage its pipeline lacks: **before any embedding or LLM comparison, parse each Goal into a structured signature (action, object, package/repo entity ID, version constraint) and link the library mention to a package-registry identity**. The "docx-js library" vs "'docx' library" split is an entity-linking failure. A better threshold would not fix it. On top of that, Kel should judge a new Goal against whole candidate *clusters* in one LLM call, with a label set that separates same, variant and parent/child, and calibrate that judge on a gold set scored with B-cubed. Merges should stop being in-place rewrites. Each merge becomes an append-only event plus a row in a bi-temporal canonical-ID map on the control database, and readers resolve through the map. Merge, unmerge and cross-shard cases then reduce to a small write on one database, followed by idempotent recomputation of derived statistics. This matters now because the current `merge_goal` (`backend/app/services/identity_resolution.py:1167`) deletes the loser's projection row, and the nightly routing fit (`backend/app/routing/fit.py:305-316`) keeps only observations whose Goal is still in `goal_search_index`. **As written, every merge silently drops the loser's routing evidence from the recommender.** On benchmarks, the lesson from Singh et al. (arXiv:1802.04538) and the literature that followed is not "use PageRank". It is that sparse, disconnected comparison graphs and misattributed numbers dominate error. Kel's IRT/GLMM already fixes the ranking-method problem. What it still needs is canonical task identity keys, provenance-complete score rows and explicit scaffold, contamination and reporter terms.

## The docx failure is an entity-linking gap, not a threshold problem

Kel's Goal identity today works like this (`docs/dedup_and_identity.md`). An exact match runs on `normalize_goal_name` (`backend/app/services/goals.py:189`), which deliberately does no semantic normalization. FTS and ANN candidates are fused by RRF, then `judge_identity("goal")` returns same, specializes/generalizes, related or distinct. A "same" verdict below `SAME_MIN_CONFIDENCE = 0.75` is downgraded to related. A ±30-minute `reconcile_goals` sweep catches concurrent paraphrases. By the standard of shipped agent memory, this is already ahead. Agent Workflow Memory deduplicates only by identical extracted action sequence ([arXiv:2409.07429](https://arxiv.org/html/2409.07429v1)). Voyager never merges skills at all. Letta still has an open request for archival-memory deduplication ([letta-ai/letta #3116](https://github.com/letta-ai/letta/issues/3116)). The entity-resolution literature describes a three-stage pipeline: blocking, then matching, then a clustering stage that repairs the intransitive verdicts pairwise matchers inevitably produce ([Binette & Steorts, Science Advances 2022](https://www.science.org/doi/10.1126/sciadv.abi8021)). Kel has the first two stages and only a single-pass stand-in for the third.

The docx pair shows what is missing upstream of all three. "docx-js" and "docx" are two surface forms of one npm package. No embedding distance or judge prompt reliably knows that, because package-name aliasing is arbitrary. npm supports explicit aliases (`<alias>@npm:<real>`) ([npm aliasing guide](https://medium.com/@mahesh.jsdev/demystifying-npm-package-name-aliasing-a-comprehensive-guide-5a0a59519de9)). PyPI alias distributions can carry names unrelated to the real package ([pypi-alias](https://github.com/ionelmc/pypi-alias)). The intent-detection literature treats this as slot filling: fill an (action, object, modifier) template before comparing, because joint intent-and-slot modeling beats either alone ([arXiv:2011.00564](https://arxiv.org/html/2011.00564)). **No published system does package-registry entity linking inside goal or skill deduplication**, so Kel has to build this stage itself. That gap is real, and the claim that it fixes the docx class is a design inference, not a measured result. One trap deserves a note. A naive registry lookup of the literal string "docx-js" can resolve to a different, unrelated package if one exists under that name. Linking must therefore score candidates using context (the repository URL in registry metadata, download counts, the language of the surrounding trace) and keep the result ambiguous when evidence is thin, never forcing a link.

The 0.75 rule also explains why errors lean toward under-merging. It uses the model's self-reported confidence, and nothing in the repo shows that number has been calibrated. An uncertain but correct "same" becomes "related" and creates a new Goal. That is the right direction to fail. As the next sections argue, over-merging corrupts the recommender, while under-merging only splits its evidence. Still, the threshold should apply to a probability calibrated on labeled data, not to what the model says about itself.

## A five-stage dedup pipeline keyed on registry identity

The recommended pipeline keeps everything Kel has and adds a normalization stage in front and a clustering guard behind.

| Stage | What it does | Where it attaches | Main source |
|---|---|---|---|
| 0. Signature | LLM extraction into (action lemma from a closed verb list, object type, entity IDs as package URLs like `pkg:npm/docx` or `owner/repo`, language, version range, residual qualifiers), stamped with extractor version | new step inside `find_or_create_goal`; signature stored on the control DB next to `goal_names` | slot filling ([arXiv:2011.00564](https://arxiv.org/html/2011.00564)) |
| 1. Entity linking | resolve library/tool mentions against the npm/PyPI/crates registries plus a Kel-maintained alias table; cache results; keep ambiguous links as candidate sets | new `goal_entities` table on A (control DB) | gap: built in-house |
| 2. Blocking | union of existing FTS+ANN+RRF (`generate_goal_candidates`) with an exact block on shared entity IDs and on alias strings | `identity_resolution.py:452` | JedAI schema-agnostic blocking ([VLDB'18](https://dl.acm.org/doi/10.14778/3229863.3236232)) |
| 3. Cluster-level judging | one LLM call per new Goal that sees each candidate *cluster* (canonical name, aliases, signature, accepted parents/children) and labels each: same, variant, specializes, generalizes, related, distinct | `judge_identity("goal")` prompt and schema | ComEM "select" strategy ([arXiv:2405.16884](https://arxiv.org/abs/2405.16884)); in-context clustering ([arXiv:2506.02509](https://arxiv.org/html/2506.02509v1)) |
| 4. Clustering guard + calibration | calibrated merge probability; the merge must not contradict any existing cluster member; periodic intransitive-triad audit; review queue for the uncertain band | `reconcile_goals`, `services/goal_review.py` | correlation clustering; ER-in-practice precision rule ([arXiv:2607.26298](https://arxiv.org/pdf/2607.26298)) |

**Signatures turn most decisions into rules.** When two signatures agree on action, object type, resolved entity IDs and version range, the pair is "same" by construction, and the LLM only needs to confirm it cheaply. When both sides have *resolved* entity IDs that differ (`pkg:npm/docx` vs `pkg:pypi/python-docx`), the pair is distinct unless one entity depends on or wraps the other. When action and entity agree but one version range contains the other ("upgrade Django" vs "upgrade Django to 5.x"), the verdict is specializes/generalizes: a DAG edge, not a merge. That gives Kel the three-way same / variant / parent-child distinction without a separate model. It also makes the new **variant** label concrete. A variant has the same action and entity but a *disjoint* qualifier ("to 4.2" vs "to 5.x"). Variants become siblings under a shared generalized parent, and they are never merged. A Fellegi–Sunter layer in the style of Splink could weight these slot agreements with EM-estimated m/u probabilities and explainable scores before the LLM runs ([Splink docs](https://moj-analytical-services.github.io/splink/topic_guides/theory/fellegi_sunter.html)). It is optional. At Kel's volume the rule table above probably covers most of the easy mass.

**Cluster-level judging beats pairwise judging on cost and consistency.** ComEM tested three strategies across 8 ER datasets and 10 LLMs: pairwise matching, comparing candidates to a probe, and selecting over the whole candidate set. Selecting alone wins because it enforces consistency across records. Their compound design filters cheaply first and then selects over the survivors, delegating most computation to medium-sized models ([arXiv:2405.16884](https://arxiv.org/abs/2405.16884)). LLM matchers need few or no training examples to match fine-tuned PLMs and generalize better to unseen entities, but no single prompt is best across datasets ([Peeters et al., arXiv:2310.11244](https://arxiv.org/abs/2310.11244)). Two operational cautions follow. Batching many decisions into one call raises the rate of malformed JSON as batch and output complexity grow ([Elastic Search Labs](https://www.elastic.co/search-labs/blog/elasticsearch-entity-resolution-llm-semantic-search)). The existing chain-exhaustion and retry semantics in `docs/dedup_and_identity.md` should therefore treat a schema failure exactly like an outage: retryable, with nothing written. Also, because the per-document goal cache only sees goals from the same document, it cannot catch cross-document duplicates like docx-js/docx. Stage 2's entity block is what guarantees those two Goals meet.

**Transitivity has to be earned.** The one practitioner source on this, which should be treated as **single-source**, reports that connected-components merging is safe when the pairwise matcher's precision exceeds about **0.9** and produces "mega-clusters" below about 0.5 ([arXiv:2607.26298](https://arxiv.org/pdf/2607.26298)). Kel merges by chaining (newer into older, repeatedly), so it inherits exactly that risk. Until the gold set shows the judge clears the bar, a new Goal should join a cluster only if the judge says "same" against the canonical *and* against no fewer than two other members or aliases, with none saying "distinct". A weekly audit should enumerate intransitive triads (A=B, B=C, A≠C) inside each entity block and send them to `goal_review.py`. The incremental-ER literature supports exactly this "match new against existing clusters, then repair by split" loop, including splitting earlier clusters when new evidence arrives ([Incremental multi-source ER, PMC7250616](https://pmc.ncbi.nlm.nih.gov/articles/PMC7250616/)). That fits Kel's invalidate-and-append rule, because a split is just another closed validity window.

**Incremental operation and cost.** Creation-time judging and the ±30-minute sweep should stay. One trigger should be added: whenever the alias table learns a new link (for example, that docx-js resolves to `pkg:npm/docx`), re-block only the Goals attached to either entity and run them through stage 3. That is a targeted repair, far cheaper than `reconcile-goals --all`. Cost falls on net. Signature extraction can share the extraction call that already produces the Goal. Registry lookups are cached per entity. One cluster-level judge call replaces k pairwise calls. Rule-decided pairs skip the LLM entirely. For labeling spend, the active-learning loop (score all candidates, send only those near the decision boundary to a human) is the standard budget control ([CIKM 2017](https://dl.acm.org/doi/10.1145/3132847.3132949); [BEACON, arXiv:2603.11391](https://arxiv.org/pdf/2603.11391)). Its label-budget figures come from product and publication records, not short goal text, so Kel has to measure its own curve. One cheap experiment is also worth running: in DSTC-11 intent induction, small distilled embeddings (MiniLM-class) with agglomerative clustering beat larger embedding models ([arXiv:2212.02021](https://arxiv.org/abs/2212.02021)). That finding comes from customer-service dialogue. Whether it transfers to Kel's technical goal strings is unknown.

**Why precision should outrank recall for Kel specifically.** This is an inference from Kel's own model, and no paper covers it. Under-merging costs relatively little in the recommender. Two duplicate Goals have near-identical embeddings, so the prior W·φ(g) in `docs/model_routing_plan.md` §3 gives them near-identical prior difficulty and specialty, and their evidence is partially pooled anyway. Over-merging costs a lot. Folding "upgrade Django to 5.x" into "upgrade Django" mixes two instance-difficulty distributions and inflates σ_ε[g], which the plan itself says makes cheap-first ladders look riskier (§3). A wrong merge also moves Procedures onto the wrong Goal, where retrieval surfaces them as correct. The asymmetry justifies a strict automatic-merge bar, with the gap closed by review and by the targeted re-blocking trigger.

## Merges become append-only redirects that cascade through one map

Every large production knowledge graph uses the same pattern. Wikidata, MusicBrainz and Freebase all keep one canonical survivor, turn the loser into a permanent redirect, and never reuse its ID. Wikidata policy says redirects must never be deleted or repurposed ([Wikidata RfC](https://www.wikidata.org/wiki/Wikidata:Requests_for_comment/Redirect_vs._deletion)). MusicBrainz forwards old IDs permanently ([MusicBrainz Merge](https://musicbrainz.org/doc/Merge)). Freebase separated stable MIDs from physical GUIDs precisely so that "topics are merged or split" without breaking external references ([Freebase concepts](https://developers.google.com/freebase/guide/basic_concepts)). The counter-example is `owl:sameAs`. Its logical transitivity propagates every property across a whole chain ([GraphDB](https://graphdb.ontotext.com/documentation/11.5/sameAs-background-information.html)), and the survey literature calls the resulting false equivalences "the sameAs problem" ([arXiv:1907.10528](https://arxiv.org/pdf/1907.10528)). DBpedia's response was to compute canonical cluster IDs as a separate, recomputable layer over raw identity assertions ([dbp-same-thing-service](https://github.com/dbpedia/dbp-same-thing-service)). One of its clusters holds 440 URIs compacted from 14,917 raw sameAs statements ([DBpedia tutorial](https://ceur-ws.org/Vol-3064/DBpedia-Technology-tutorial.pdf)).

### What `merge_goal` does today, and why it will not cascade simply

Measured against that pattern, the current merge is an eager rewrite. `merge_goal` and `_merge_goal_sharded` (`backend/app/services/identity_resolution.py:1167-1330`) update `procedures.achieves_goal_id` in place, and in sharded mode they do it on every shard in a loop that skips unreachable shards and relies on a later relink sweep. They re-insert the loser's `goal_relations` edges pointed at the survivor, then `DELETE` the originals. They also `DELETE` the loser's `goal_names` rows. When the loser's status becomes `merged`, the projection drainer deletes its `goal_search_index` row (`backend/app/services/search_projection.py:243`). No unmerge exists. This conflicts with Kel's own invalidate-and-append rule for relations and names. It turns a cross-shard merge into a fan-out write across every shard. Most importantly, it disconnects the recommender. `routing_observations` rows (`backend/db/120_model_routing.sql:66`) keep the loser's `goal_id` forever, which is correct, since they are a never-pruned log. But `store.goal_observations` filters on that exact ID, and `nightly_refit` builds `goal_meta` from `goal_search_index` and discards observations whose Goal is not there (`backend/app/routing/fit.py:305-316`, `build_joint_data` line 105). The loser's attempts therefore vanish from both the local and the joint fit.

### The recommended design

Add a bi-temporal **`goal_identity_map`** on control project A, next to `object_routes`, `goal_names` and `goal_relations`: `(goal_id, canonical_goal_id, merge_event_id, t_valid_from, t_invalid)`. A merge becomes one ChangeSet event of kind `goal_merge` carrying the loser, the survivor, the `identity_decisions` ID, the calibrated probability, and the **versioned pointer of every row it closes**. That is the pattern FHIR's patient merge uses, where `Provenance.entity[].what` records pre-merge version references ([Health Samurai, Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)). Readers resolve every Goal ID through the map as of the time they care about. Procedures keep the `achieves_goal_id` they were written with. "Procedures of Goal X" becomes `achieves_goal_id = ANY(members(X))`, and routing reads become `goal_id = ANY(members(X))`. The loser's `goal_names` row is closed and re-appended pointing at the canonical ID, so an exact lookup of "docx-js library" lands on the survivor without a judge call. The loser's projection row stays, marked as a redirect, and is excluded from search results. The trigger `sl_procedure_follow_merged_goal` stays, but its job changes from blocking to annotating: a late writer's link is resolved through the map instead of rejected.

That choice is what makes the cascade simple. **A merge is a single transaction on A** (map row, name redirect, relation re-point, event) plus one idempotent status flip on the loser's home shard, which is retried from `projection_outbox` if that shard is down. No Procedure, Claim or Evidence row moves, so there is no cross-shard fan-out and no "unreachable shard, repair later" branch. The design follows Freebase's split between a stable logical ID and physical identity, applied at the routing-table layer that `docs/sharding.md` already treats as authoritative. The honest gap: **no literature describes merging first-class graph nodes across physical shards**, and none says how to keep a routing-table update atomic with remote shard state. The design above sidesteps the question by making the remote write a non-authoritative flag, so the map on A is the only source of truth.

### DAG rules

Neo4j's `apoc.refactor.mergeNodes` unions relationships and leaves cycle safety to the caller ([APOC docs](https://neo4j.com/docs/apoc/current/overview/apoc.refactor/apoc.refactor.mergeNodes/)). Ontology-merging practice runs a separate repair pass because merges can introduce cycles ([IEEE survey on mapping/alignment/merging](https://ieeexplore.ieee.org/document/6216651/)). Kel already demotes an accepted edge that would close a cycle to `proposed` (`_move_goal_relations`). Three rules should be added. First, **refuse a "same" merge between two Goals already connected by an accepted SPECIALIZES path**. That verdict contradicts the DAG, so it goes to review as a possible `collapse_hierarchy`, an operation with its own audit semantics, never through `merge_goal`. Second, re-pointed edges are appended with the `merge_event_id`, and the originals are closed (`t_invalid`) rather than deleted. Third, run a local transitive reduction around the survivor after the merge, dropping a direct survivor→P edge when survivor→C→P exists. That step is an inference: no source ties transitive reduction to KG merge maintenance. Multiple parents are fine. The GLMM's μ(g) averages parent residuals over |P(g)|, so a merged Goal inheriting two parent sets is handled by the same formula, and diamonds still enter the likelihood once. The literature has nothing on invariants for multiple inheritance under merges. That is a gap.

### Derived data and statistics

**Never arithmetically combine aggregates at merge time.** FHIR's unmerge design says anything derived during the merged period "can no longer be trusted without review" and has consumers recompute on merge and unmerge events rather than patching in place ([Health Samurai](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)). For Kel, the `goal_merge` event enqueues four jobs: a projection refresh for both IDs (the outbox already does this), a `routing-local-refit` of the canonical Goal over all member observations, a `superseded` mark on the loser's `routing_posteriors` rows, and a goal-abstraction placement job. The nightly refit resolves `goal_id` through a snapshot of the map taken at fit start and stores the map version in `routing_params.meta`, so each fit is reproducible. Because the refit derives everything from the raw observations and Evidence rows, rerunning it is idempotent, and it is automatically correct after an unmerge.

### Unmerge

Unmerge closes the map row, appends a fresh loser row that reopens its validity window, and enqueues the same recomputations. The hard case is FHIR's "temporal gap": objects attached to the survivor after the merge have no pre-merge home. Kel avoids FHIR's worst branch, where the loser was hard-deleted and its ID must be reused or re-minted, because it never deletes. It still needs explicit policies on FHIR's other axes. The default recommended here is that post-merge attachments stay on the survivor and are flagged for steward review. To make reassignment possible, every write through a redirect should record the *requested* Goal ID alongside the resolved one. That means adding a `requested_goal_id` to `routing_observations`, and the same field on Procedure provenance. Unmerge also writes a **cannot-link** constraint, the equivalent of FHIR's "do-not-merge" Linkage, which `reconcile_goals` and stage 4 must respect so the automated matcher does not re-merge the pair. Informatica MDM's configurable cascade unmerge ([Informatica docs](https://docs.informatica.com/master-data-management/multidomain-mdm/10-5-hotfix-2/business-entity-services-guide/rest-business-entity-service-calls/rest-api-reference-for-business-entity-services/unmerge-records.html)) is the precedent for making propagation to children configurable rather than assumed. The detailed FHIR mechanics come from **one vendor design article**. It is the strongest instance-merge source available, but it is not peer-reviewed.

Survivor choice can stay "older ID wins", because it converges deterministically across workers. With a map in place, the survivor's ID is cosmetic. The canonical *display name* should follow MDM-style survivorship rules ([Profisee](https://profisee.com/blog/mdm-survivorship/)): prefer the registry-canonical entity name, then the most frequent alias.

## Benchmark tasks need two identity keys, not one

The SWE-bench family already publishes the fields canonical identity needs. SWE-rebench asserts unique `instance_id` values and builds images keyed on `(repo, base_commit)` ([arXiv:2505.20411](https://arxiv.org/pdf/2505.20411); [SWE-rebench-V2 card](https://huggingface.co/datasets/nebius/SWE-rebench-V2)). Kel's reader uses `dedup_key = repo@base_commit` (`backend/app/services/ingestion_sources/verified_solutions_hf.py:280`), and its docstring says the same code state reached by two PRs is one dedup target. **That key identifies a code state, not a task.** SWE-smith builds 50,137 synthetic tasks by injecting different bugs into 128 seed repositories ([arXiv:2504.21798](https://arxiv.org/pdf/2504.21798)), so a single code-state key would collapse many distinct SWE-smith tasks into one. The same holds for two genuinely different issues filed against the same commit. Kel should keep the code-state key for what it is good at: held-out exclusion, since `load_held_out` already excludes whole repositories for that reason, and contamination blocking. It should add a **task key** for identity: `(repo_canonical, base_commit, hash(sorted FAIL_TO_PASS ∪ PASS_TO_PASS test IDs), hash(normalized gold patch))`. Rows with equal task keys across suites are one canonical task with several suite memberships. Pairs that differ only in the problem-statement text go through MinHash over statement plus patch within the repository block. MinHash is expensive at pretraining scale ([LSHBloom, arXiv:2411.04257](https://arxiv.org/html/2411.04257v4)) but trivial at the scale of a benchmark corpus. Repository renames should go through an override table that rewrites only the clone URL and keeps the canonical key, as SWE-rebench-V2 does with `CLONE_REPOSITORY_OVERRIDES` ([agent-fleet PR #190](https://github.com/sii-system/agent-fleet/pull/190)).

This matters for the recommender, not just for tidiness. Plan correction 1 in `docs/model_routing_plan.md` §16 says ε[i] is identified only by instances that several models attempted. If the SWE-bench-extra and SWE-rebench copies of one task receive different `instance_key` values, ε is split, and a model's ability is counted twice on one piece of evidence. **The canonical task key must be the `instance_key` for every `public_import` row.** No published measurement exists of instance-level overlap between SWE-Gym and SWE-smith, or between SWE-bench-extra and SWE-rebench. SWE-Gym's companion `SWE-Bench-Fork` repository signals shared tooling lineage ([SWE-Gym paper](https://arxiv.org/pdf/2412.21139)). Multi-SWE-bench accounts for overlap only at the repository level (17 instances across five shared repositories) ([Multi-SWE-bench](https://github.com/multi-swe-bench/multi-swe-bench)). Kel will be measuring these overlaps for the first time, so the counts deserve a board note once the key exists.

**Contamination risk is a per-(task, model) quantity, not a per-task tag.** SWE-rebench controls it by construction, collecting issues created after a model's cutoff, and scores for some models fell sharply once memorization stopped helping ([arXiv:2505.20411](https://arxiv.org/pdf/2505.20411)). LiveCodeBench does the same by scoring only problems released after each model's cutoff ([arXiv:2403.07974](https://arxiv.org/abs/2403.07974)). The SWE-Bench Illusion paper found models name the buggy file path with up to 76% accuracy on SWE-bench repositories vs up to 53% elsewhere, and reproduce the fix with verbatim 5-grams up to 35% of the time on SWE-bench Verified/Full ([arXiv:2506.12286](https://arxiv.org/abs/2506.12286)). A further study reports 32.67% of successful patches involving solution leakage through the issue text ([arXiv:2512.10218](https://arxiv.org/html/2512.10218v2)). That figure comes from **the abstract only and was not verified against the full text**. Kel should store three task-level facts: the task's creation date, its suite exposure (whether it has appeared in a widely published suite), and a leakage flag from a cheap check of whether the gold patch's added lines appear in the issue text. It should compute contamination against each model's cutoff at fit time. n-gram and MinHash decontamination miss paraphrased leaks ([arXiv:2311.04850](https://arxiv.org/pdf/2311.04850)), so the flag is a floor, not a guarantee.

**Versions are separate artifacts, and validity is a living field.** SWE-rebench V1 and V2 are separate releases ([V2 paper](https://arxiv.org/pdf/2602.23866)). SWE-bench Verified is a 500-task human-screened subset ([OpenAI](https://openai.com/index/introducing-swe-bench-verified/)). Verified tasks later broke from dependency drift and were patched through GitHub issues rather than a changelog ([SWE-bench #484](https://github.com/SWE-bench/SWE-bench/issues/484)). Provenance therefore needs to be stored at `(suite, suite_version, dataset revision/URL)` granularity. A task's validity (whether the gold patch still passes) should be a bi-temporal row that periodic re-validation closes and re-appends. Evidence from an invalid window keeps its row but gets a lower check reliability.

**A benchmark task is an instance, not a Goal.** `docs/model_routing_plan.md` §3 proposes ingesting SWE-bench tasks "as leaf Goals". If every task gets its own leaf Goal holding one instance, the model cannot separate b[g] from ε[i], and only the DAG prior identifies them. The better mapping sends each task through the same dedup pipeline as a Goal, using an extraction template in the style of "root cause / solution plan" from issue-mining work ([Threads to Trajectories, arXiv:2604.25880](https://arxiv.org/html/2604.25880v1)), so that it attaches to a Goal shared with other instances ("fix a Django ORM query-compilation regression"). The task key then becomes the `instance_key` under that Goal. Suite taxonomies are useful signature slots but not Goal types. DS-1000's library and perturbation axes ([arXiv:2211.11501](https://arxiv.org/pdf/2211.11501)) and BigCodeBench's 723 function calls from 139 libraries ([arXiv:2406.15877](https://arxiv.org/html/2406.15877v2)) feed the entity slot of stage 0 directly. SWE-bench Verified's fix-time buckets belong in a difficulty covariate, not the taxonomy. **No published crosswalk from benchmark items to a coding-goal taxonomy exists, and no evaluation of LLM goal extraction on benchmark issues exists either.** Kel is first here, so the mapping needs its own gold set (see the evaluation plan).

## Scores enter the GLMM as observations, never as normalized numbers

The comparable per-goal evidence the recommender needs is not a normalized score. It is a **likelihood term**. Kel's GLMM (`docs/model_routing_plan.md` §3) is already a multidimensional hierarchical IRT. The field has converged on IRT for cross-benchmark comparison because it puts model ability and item difficulty on one latent scale and handles arbitrary missingness. The line runs from IRT leaderboards ([Rodriguez et al., ACL 2021](https://aclanthology.org/2021.acl-long.346/)) through tinyBenchmarks, which estimates full scores within about 2% from 100 items ([arXiv:2402.14992](https://www.alphaxiv.org/abs/2402.14992)), and metabench, where one latent factor explains 79.3% of variance ([arXiv:2407.12844](https://arxiv.org/html/2407.12844)), to Epoch's production ECI and its "Rosetta Stone" stitching of incomplete benchmark coverage ([epoch.ai/eci](https://epoch.ai/eci); [arXiv:2512.00193](https://arxiv.org/pdf/2512.00193)). Kel should import evidence in that spirit, in the order below.

| Evidence form | How it enters | Trust handling |
|---|---|---|
| Per-instance outcomes with scaffold (submission logs) | one `routing_observations` row per (task key, model, scaffold, attempt), `check_kind='benchmark'` | full weight; ε[i] shared across all models on that task |
| n samples with c correct per task | c/n as n Bernoulli attempts on the same `instance_key` | never convert to pass@k; the Chen et al. estimator ([arXiv:2107.03374](https://arxiv.org/pdf/2107.03374)) is for reporting only |
| Aggregate pass@1 with known suite size N | binomial likelihood over the suite's instances, marginalizing ε, as §3 already plans | the implied N already carries the uncertainty; no Wilson step is needed inside a Bayesian fit |
| Aggregate pass@k (k>1), no n/c | exclude from θ, or a separately fitted pass@k link | **gap:** no published method recovers pass@1 from pass@k without n and c |
| Vendor-reported aggregate, harness undisclosed | route as `self_report` with a per-vendor reporter reliability term (§5, Dawid–Skene) and scaffold `undisclosed` | reporter effect absorbs systematic optimism |
| External index (ECI-style) for a model with no instance data | a noisy measurement of θ[m,0] with a fitted loading | prior only; outweighed as instance data arrives |

**Scaffold is not optional.** A third-party audit reports up to **15 points** of scaffold-only variation on SWE-bench Verified, and Terminal-Bench 2 pass@1 moving from 69.7% to 77.0% on harness alone ([arXiv:2605.23950](https://arxiv.org/html/2605.23950)). That is larger than many model-to-model gaps. Kel's γ[s] + δ[m,s] terms are the right slot. Undisclosed harnesses should share one `undisclosed` level with a wide prior rather than borrow a vendor default. Two dedicated 2026 papers on harness confounding exist ([arXiv:2609.11987](https://arxiv.org/abs/2609.11987); [arXiv:2609.09218](https://arxiv.org/abs/2609.09218)), but their methods were not read, so the 15-point figure rests mainly on **one audit**. **Contamination enters as a covariate**, κ·contam(i, m), with κ fitted, or, following LiveCodeBench, by excluding pre-cutoff exposed tasks from θ while keeping them for b[g]. Kel should fit both variants and let held-out calibration choose.

**What to avoid, and why.** Human- or random-baseline normalization can invert rankings when the baseline underperforms random ([Agarwal et al., arXiv:2108.13264](https://arxiv.org/abs/2108.13264)), and coding agents have no stable baseline anyway. Min-max and cross-benchmark z-scores are sensitive to outliers and to whichever models happen to be in the reference pool ([OpenSearch](https://opensearch.org/blog/introducing-the-z-score-normalization-technique-for-hybrid-search/)). HELM's own documentation says mean win rate keeps only ordinal information ([HELM](https://crfm.stanford.edu/helm/)). Arena-style Bradley–Terry ratings break under a non-stationary, silently deprecated model pool ([Leaderboard Illusion, arXiv:2504.20879](https://arxiv.org/pdf/2504.20879)). None of these should feed θ. IQM with stratified bootstrap remains the right tool for Kel's *own* multi-task harness reports in Band 3, not for the recommender.

### What 1802.04538 actually implies for Kel

Singh et al. parsed 204,264 LaTeX tables from 107,795 arXiv papers into a "performance improvement graph" of noisy pairwise paper-vs-paper claims. They found **PageRank variants significantly beat tournament methods**, including a gradient-descent maximum-likelihood "exponential tournament". Their best sigmoid-weighted PageRank reached Recall@10 of 19.35%, against 7.38% for a citation-count baseline ([ar5iv:1802.04538](https://ar5iv.labs.arxiv.org/html/1802.04538)). The diagnosis matters more than the winner. The graph had disconnected components and unequal comparison counts, and **more than half of the tournament methods' top-ranked papers were sinks**, papers nobody had yet compared against. Leaderboard quality tracked connectivity: Spearman 0.94 on well-connected SQuAD vs 0.23 on MIT-300. Rank Centrality's random-walk estimator matches Bradley–Terry–Luce MLE on BTL-generated data ([Negahban, Oh & Shah, Operations Research](https://pubsonline.informs.org/doi/10.1287/opre.2016.1534)). Read together, the two results suggest PageRank's edge came from the graph's structure rather than from any superiority of the method. An unregularized MLE degenerates on sparse, disconnected data. That is a synthesis across two sources that were never directly compared, and should be read as such.

Five implications follow for Kel. First, **do not build a comparison graph from leaderboard rankings at all.** Kel has absolute per-instance outcomes, and a hierarchical IRT with shrinkage is the principled cure for the sparsity that sank the tournament methods. Second, the sink bias has a direct analogue in a new model with three lucky observations, and the plan's chance constraint on the posterior (§6) is what stops it topping a ladder. The evaluation should check this explicitly. Third, **measure connectivity.** For each Goal cluster, compute the connected components of the bipartite model–instance graph. A model in a component that shares no instance with the incumbents is ranked by the prior alone, and `recommend_models` should say so in its "why". Where the evidence cannot separate units, ties should be reported rather than an order forced, as the partial-ranking work argues ([Communications Physics, arXiv:2501.02505](https://www.nature.com/articles/s42005-025-02461-y)). Fourth, Singh's **REI outlier cutoff** (drop claims implying more than 100% relative improvement, which fewer than 0.5% of genuine edges show) becomes a posterior-predictive screen on `routing-import`. An aggregate that lands in the far tail of the model's predictive distribution for that (model, suite, scaffold) is quarantined for review, not fitted. Fifth, and most consequential, **the follow-up lineage shows the hard part is attaching the right number to the right condition.** AxCell's full (task, dataset, metric, score) extraction F1 was 25.8, against 61.9 for the triple alone ([ar5iv:2004.14356](https://ar5iv.labs.arxiv.org/html/2004.14356)). TDMS-IE reported a steeper drop, but those figures come from a secondary summary and are not verified ([arXiv:1906.09317](https://arxiv.org/abs/1906.09317)). In 2024, LLMs still identified leaderboards well and extracted result values poorly ([SciLead, arXiv:2409.12656](https://arxiv.org/pdf/2409.12656)). Singh's corpus held **14,947 distinct metric strings**. So every `public_import` row should require suite, suite_version, split, metric, k, n, scaffold, date and source URL. A row missing scaffold or suite_version drops to the self-report tier. Papers with Code, the closed taxonomy most extractors linked to, shut down on 24 July 2025, leaving only an archive ([Coursera](https://www.coursera.org/articles/papers-with-code)). Kel should therefore keep its own small closed vocabulary of suites and check kinds and not depend on any external taxonomy.

## Measure with B-cubed on a gold set built from disagreements

**Metrics.** B-cubed should be primary. It is the lowest-error estimator among pairwise, cluster-level and B-cubed metrics, and it correctly penalizes damage to large clusters, where pairwise F1 is "overly optimistic" ([arXiv:2404.05622](https://arxiv.org/html/2404.05622); [arXiv:1509.04238](https://arxiv.org/pdf/1509.04238)). Pairwise precision stays as the operational gate on auto-merges. **Gold sets.** Four are needed. G1 is roughly 600–1,000 Goal pairs drawn from `identity_decisions` strata: high embedding similarity judged "different" (the docx class), moderate similarity judged "same" (over-merge candidates), low-confidence "same" demoted to related, and specializes/generalizes verdicts. Each is labeled with the six stage-3 labels by two annotators, with kappa reported. G1 also gets an adversarial slice built from registry alias pairs, version variants and look-alike packages. G2 is about 50 fully clustered entity blocks, for B-cubed. G3 is cross-suite task pairs sampled by code-state key, for task-key precision. G4 is the recommender's held-out calibration set, which `docs/model_routing_plan.md` §12 already defines. No public gold set for software goal statements exists, and no weak-supervision result exists for short technical text, so these are Kel's to build.

**Targets** (proposed, not taken from the literature): auto-merge pairwise precision ≥ 0.95 on G1, above the ~0.9 transitivity floor from a single source; B-cubed precision ≥ 0.97 and recall ≥ 0.85 on G2 at launch, with recall raised as review clears the uncertain band; alias-slice recall ≥ 0.95; **zero** ancestor–descendant merges; fewer than 2% of merges unmerged per quarter. Kel can also run an extensional check that no general ER source offers. Refit the GLMM with and without a batch of merges and compare held-out log-likelihood. A merge that lowers predictive fit, for example by inflating σ_ε, is evidence of over-merging from the recommender's side.

## Conclusion

The research changes where Kel's effort belongs. Both halves of the question looked like similarity problems ("how close is close enough") and ranking problems ("which aggregation is best"). Both turn out to be **identity-and-provenance problems**. The Goal-dedup failures come from missing entity identity (what package is this?), not from the embedding threshold. The benchmark-normalization failures that the 1802.04538 lineage kept rediscovering come from missing condition identity (which suite version, harness, k and split does this number belong to?), not from choosing PageRank over MLE. Kel's GLMM already solves the aggregation question better than any leaderboard method in that lineage. It can only do so if tasks, Goals and scores reach it with stable keys.

The single most urgent finding is architectural, not statistical. Kel's merge path currently cuts the recommender off from evidence, and its sharded merge touches every shard. Moving identity into one append-only map on the control database fixes both, makes unmerge cheap, and turns the "cascade" into ordinary recomputation. The honest open ground is also clear: package-registry entity linking inside goal dedup, merge invariants for multiply-inherited task DAGs, atomic cross-shard merges, a benchmark-to-goal crosswalk, and recovering pass@1 from bare pass@k all lack published solutions. Kel's gold sets and overlap measurements would be first-of-kind evidence on each.
