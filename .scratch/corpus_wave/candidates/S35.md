# S35 — Design a bounded stateful repository-maintenance workflow

- **Source:** github.com/github/gh-aw `/.github/aw/maintainer.md` @ `main@957471c2` · MIT
- **Locator:** "Repository Maintenance Workflows" §§"Operating principles" / "Survey the repository before choosing a strategy"
- Distills githubnext/agentics Repo-Assist into reusable design principles. Complements S34 (an instance).

## problem
Generic "do maintenance" automation either does nothing useful or floods maintainers with low-value comments and PRs.

## goal
Design a maintenance workflow that makes useful progress without consuming disproportionate maintainer attention.

## preconditions
- A target repo; the intent (broad automation vs a narrow explicit request).

## steps
1. Survey the repo first — project shape (languages, manifests, monorepo boundaries, build/deploy), repository policy (`AGENTS.md`, `CONTRIBUTING.md`, `CODEOWNERS`, protected paths), activity pattern (arrival/closure rates, contributors, existing bots).
2. From the survey, mine candidate intents (skip the survey for a narrow explicit request unless evidence disambiguates).
3. Prefer a small, valuable action over broad cleanup.
4. Stay silent on an issue/PR unless there is something accurate and actionable to add.
5. Read `AGENTS.md`/`CONTRIBUTING.md` before changing files; preserve public APIs; no new deps without a tracked maintainer approval.
6. Create small draft PRs — one concern, clear rationale, validation results.
7. Never merge the workflow's own PRs.
8. Treat a whole-run `noop` as exceptional — inspect the bounded work queue before concluding there's nothing to do.

## decision points
- Broad request → survey-first to derive intents. Narrow request → act directly.
- Candidate action is large/risky → downgrade to a proposal/discussion, not a PR.

## postconditions
- Either a small single-concern draft PR with validation, an accurate targeted comment, or a justified `noop`.

## verification
- Output is bounded and single-concern; rationale + validation results attached; no self-merges.

## failure/recovery
- Maintainers ignore/close outputs repeatedly → the value bar is too low; tighten "accurate and actionable".

## implementation
