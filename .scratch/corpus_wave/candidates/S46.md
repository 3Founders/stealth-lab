# S46 — Harden authentication (OWASP Authentication Cheat Sheet)

- **Source:** github.com/OWASP/CheatSheetSeries `/cheatsheets/Authentication_Cheat_Sheet.md` @ `master@b8586414` · CC-BY-SA 4.0 (attribute "OWASP CheatSheetSeries contributors")
- **Locator:** §§"Implement Proper Password Strength Controls" / "Protect Against Automated Attacks" / "Authentication and Error Messages"

## problem
Auth implementations leak account existence, allow weak passwords, and are brute-forceable.

## goal
Bring a login system up to OWASP's baseline against brute-force, credential stuffing, and user enumeration.

## preconditions
- A web app with user authentication; TLS infrastructure available.

## steps
1. **Password length:** treat as weak if `< 8` chars with MFA enabled, or `< 15` chars without MFA.
2. **Max length + charset:** allow at least 64 chars for passphrases; "Allow usage of all characters including unicode and whitespace".
3. **Blocklist:** "Block common and previously breached passwords" (e.g. Pwned Passwords API).
4. **Transport:** "Login page and all subsequent authenticated pages must be exclusively accessed over TLS".
5. **Lockout:** threshold-based lockout after failed attempts; "Counter of failed logins should be associated with the account itself".
6. **Error messages:** return a generic response ("Login failed; Invalid user ID or password") for every failure mode; keep response time constant for unknown-user vs bad-password.

## decision points
- MFA present → the 8-char floor applies; otherwise 15.
- Lockout risks DoS-by-lockout → prefer throttling/CAPTCHA escalation over hard lockout for public apps.

## postconditions
- Passwords meet the length/charset/blocklist rules; all auth traffic is TLS; failed logins are counted per-account and rate-limited; error responses are indistinguishable.

## verification
- Test invalid credentials: identical error text AND near-constant response time for bad-user vs bad-password; breached password is rejected; non-TLS auth request is refused/redirected.

## failure/recovery
- Timing side-channel remains → do the same password-hash work even for unknown users (dummy hash).

## implementation
Application code + a breached-password service + TLS config; deterministic checks. Provider: the web app.

## source evidence
