## TL;DR — what's already built vs. what's missing

This is the single most important finding, and it reframes the whole task: **StealthLab already has a materially complete Procedure dedup pipeline** (`app/services/dedup.py` + `app/services/skill_ingestion.py::check_novelty`), a **partial Implementation capability-ranking pipeline** (`app/services/capabilities.py::compare_implementations`), and **zero Claim-equivalence pipeline** (only manual `SUPERSEDES`/`CONTRADICTS` edges, asserted by a caller, never detected). The three recommendations below are sized against those real gaps, not a blank slate.

|---|---|---|---|
| 1. Procedures | minimal/canonical | Embedding pre-filter + lexical/category gates + complete-linkage clustering + admin merge, already wired at both write-time (`check_novelty`) and batch time (`run_dedup_sweep`) | `procedures` isn't in `run_dedup_sweep`'s default table tuple even though `find_duplicate_clusters` already special-cases it; no cross-encoder/LLM-judge second opinion before an automated merge |

Claims | collapse dup, separate contradiction | `CONTRADICTS`/`SUPERSEDES` edges exist as a **write-time, caller-asserted, never auto-detected** relation; `claim_belief.py` (frozen, do not touch) already treats independence groups correctly | Nothing computes "these two claims are the same fact" (equivalence) or "these two claims are incompatible" (contradiction) from text — both require a human/pipeline to already know and call `relate_claims()` explicitly |

## Problem 1 — Procedure deduplication (target: minimal canonical set)

### What the literature says

**Embedding threshold + clustering (SemDeDup).** SemDeDup (Meta AI, Abbas et al., 2023) is the primary citable source for "embed, cluster, cut by cosine similarity" as a production-proven technique for removing *semantic* (not exact-string) near-duplicates at scale: it embeds each item with a pretrained model, k-means-clusters the embedding space, then computes pairwise cosine similarity *within* each cluster and removes near-duplicates above a distance threshold — published thresholds in the paper's own ablations are stated in *distance* terms (e.g. one open implementation reports τ=0.15 distance with k=1000 clusters), and the paper reports removing up to 50% of a dataset with minimal downstream performance loss.
Source: [arXiv:2303.09540](https://arxiv.org/abs/2303.09540), code: [github.com/facebookresearch/SemDeDup](https://github.com/facebookresearch/SemDeDup).

**Exact/near-exact dedup at the corpus level (MinHash / SimHash).** Lee et al., "Deduplicating Training Data Makes Language Models Better" (Google, ACL 2022) is the primary source for MinHash-based approximate Jaccard matching over n-gram sets for large-scale document dedup, plus exact-substring dedup via suffix arrays (50-token threshold). SimHash with a Hamming-distance cutoff of 4 over 6-grams was used for the same purpose in the BigScience ROOTS corpus pipeline.
Sources: [arXiv:2107.06499](https://arxiv.org/abs/2107.06499) / [ACL Anthology 2022.acl-long.577](https://aclanthology.org/2022.acl-long.577/); ROOTS: [arXiv:2303.03915](https://arxiv.org/pdf/2303.03915). Both techniques target *documents*, not short structured records like a procedure's (goal + steps); they are cited here because they are the field's reference implementations for "threshold over an approximate-similarity sketch," which is the same shape of decision this repo already makes with cosine similarity.

**HDBSCAN — a documented failure mode for exact/near-duplicate detection specifically.** Practical write-ups report that HDBSCAN, because it clusters by general semantic similarity/density rather than strict near-identity, produces clusters "with substantial non-duplicate content" when used for duplicate detection on short texts (tweets); a fixed-radius method (DBSCAN with a small max distance, or a hard cosine threshold) tracked manually-identified duplicates far better than HDBSCAN's density-adaptive clusters. This is a real, citable caution against reaching for HDBSCAN specifically for *dedup* (it is well-suited to *topic discovery*, a different task).
Source: [MachineLearningMastery — Clustering Unstructured Text with LLM Embeddings and HDBSCAN](https://machinelearningmastery.com/clustering-unstructured-text-with-llm-embeddings-and-hdbscan/) (methodology + citation of the underlying duplicate-detection comparison).

**Cross-encoder re-ranking (retrieve-then-rerank).** Sentence-Transformers' own documentation states the standard production pattern directly: use a bi-encoder to retrieve candidates (e.g. top-100 nearest neighbors by cosine similarity), then a cross-encoder — which sees both texts jointly through one transformer forward pass and outputs a single relevance score — to re-rank/confirm. The library ships pretrained cross-encoders specifically fine-tuned for duplicate-question detection (`cross-encoder/quora-distilroberta-base`) with the explicit design note that cross-encoders "are best deployed after an initial filtering using a sentence transformer model" because they don't scale to all-pairs comparison.
Sources: [SBERT Retrieve & Re-Rank docs](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html), [SBERT Quora Duplicate Questions cross-encoder training docs](https://sbert.net/examples/cross_encoder/training/quora_duplicate_questions/README.html). Note: the SBERT docs describe the *architecture and pretrained model name* precisely but do **not** publish a specific accuracy/AP number on that page — do not cite a number for this pair that wasn't independently verified.

**Graph-based canonicalization (union-find / golden record).** This repo's own `dedup.py` already implements this pattern, and does it *better* than naive union-find: it uses **complete-linkage** clustering (a candidate joins a cluster only if it exceeds the threshold against *every* existing member, not just its nearest neighbor) specifically because plain transitive union-find produces "chaining" (A~B~C~D merge into one cluster even when A and D aren't actually similar) — this is a real, own-repo-confirmed failure mode, not a hypothetical (see `dedup.py` module docstring and `_title_diff_is_trivial`'s worked example: "Blue Account..." vs "Purple Account..." scoring 0.95 cosine similarity despite being different products). This is consistent with the general record-linkage literature's warning that transitive closure over noisy pairwise links over-merges (see Fellegi-Sunter discussion in Problem 3 below, which is the same underlying concern).

**LLM-as-judge pairwise equivalence.** Not something this pass found a single canonical paper for as applied to "procedure equivalence" specifically — there is no published literature on runbook/recipe/procedure-equivalence detection as a named subfield. The closest published framing is the **paraphrase ≈ bidirectional entailment** equivalence used for claims (Problem 3), which is the more rigorous formal basis; an LLM-as-judge pairwise call over (goal, steps, preconditions) is the practical implementation of that same idea when no NLI model is fine-tuned for the domain. Recommendation: treat LLM-as-judge as the fallback verifier for borderline cosine scores, not the primary signal — same posture this repo already takes with cross-encoders in the "hybrid" pattern above.

### What StealthLab already has (do not rebuild)

- `backend/app/services/skill_ingestion.py::check_novelty` (line ~643): admission-controller novelty check. Embeds the incoming goal, calls `find_applicable_procedures` for the single nearest match, and refuses ingestion if similarity ≥ `NOVELTY_THRESHOLD = 0.90` — explicitly the *same* 0.90 that `applicability.py`'s retrieval code treats as "confidently the same thing" (reused, not reinvented). This is a real, already-wired **write-time refusal gate**, i.e., it already does "detect equivalence before it enters storage."
- `backend/app/services/dedup.py`: the batch-reconciliation half. `find_duplicate_clusters(pool, table, scope, embedder)` computes pairwise pgvector cosine similarity server-side (`1 - (a.embedding <=> b.embedding)`), gates it through two purely lexical disqualifiers (`_title_diff_is_trivial` — symmetric word-set difference must be empty; `_categories_agree` — an explicit `category` property, when present on both sides, must match) before ever trusting the embedding score, then complete-linkage-clusters survivors at `FULL_MATCH_THRESHOLD` (imported from `reuse_detection.py`). `find_duplicate_clusters` **already has an explicit branch for `table == "procedures"`** (`name || ' ' || COALESCE(goal, '')` as the text to embed/compare) — the procedure case is coded, tested (`backend/tests/test_procedure_dedup_e2e.py`, `backend/tests/test_merge_cluster.py`), but not defaulted-on.
- `merge_cluster` performs the actual "golden record" selection: `canonical_rule="earliest"` (first-created survives — the right rule for accidental re-ingestion) or `"latest"` (right rule for supersession-shaped merges). The loser is never deleted — invalidated (`t_invalid` set) and linked to the survivor via a `SUPERSEDES` edge tagged `custom_edge_type='DUPLICATE_OF'`; edges pointing at the loser are rewired onto the survivor inside the same transaction. This is a correct, already-built implementation of "union-find + golden-record selection + tombstone-never-delete," matching every literature pattern above.
- **The one real gap**: `run_dedup_sweep`'s default `tables` tuple is `("task_nodes", "knowledge_nodes")` — `"procedures"` is not in it. So the batch reconciliation path that would catch two organically-extracted procedures that entered the graph independently (the case `check_novelty` structurally cannot catch — it "can reject an incoming near-duplicate but can never reconcile two rows that are already both persisted," per its own docstring) is coded and tested but **not turned on for procedures by default**. `skill_ingestion.py`'s own docstring names this exact gap explicitly: "procedures.py::merge_duplicate_procedures() / run_procedure_dedup_sweep() (Phase 5, memory-substrate map, gap #8)" — i.e. this gap is already tracked, just not closed.

### Recommendation (additive, no migration needed)

No schema change is required — `procedures.embedding VECTOR(1024)` already exists (`backend/db/19_procedures_embedding.sql`), and `find_duplicate_clusters`/`merge_cluster` already handle the `procedures` table generically. The concrete, additive piece of work is a **service-level wiring change**, not new infrastructure:

1. Add `"procedures"` to the default `tables` tuple `run_dedup_sweep` sweeps (or add a dedicated `run_procedure_dedup_sweep()` wrapper, as `skill_ingestion.py`'s own docstring already names it — either satisfies the same gap #8). Keep the existing `apply=False` dry-run default; nothing here needs to become auto-applying.
2. Optionally strengthen the merge decision for procedures specifically with a cross-encoder or LLM-as-judge second opinion **only at the borderline band** (e.g. cosine in [0.85, 0.90) — below `NOVELTY_THRESHOLD` but high enough to be a real candidate) before a cluster is presented to an admin for `apply=True` — this is the literature's "hybrid retrieve-then-rerank" pattern, and it costs nothing extra on the already-decided cases (≥0.90 auto-flags at write time via `check_novelty`; well below the floor never becomes a cluster). This is a pure Python addition inside `dedup.py`/`skill_ingestion.py`, no migration.
3. Leave `merge_cluster`'s transaction/tombstone/DUPLICATE_OF mechanics untouched — they already match every "golden record, never delete" pattern in the literature.

## Problem 2 — Implementation richness (target: many diverse executors per Procedure)

### Named patterns confirmed, with citations

- **HTN: compound task vs. primitive task, resolved via a "method".** This is a real, precisely-named distinction in classical planning, not a loose analogy. A **primitive task** (= action/operator) can be executed directly once its precondition holds in the current state; a **compound (abstract) task** must be refined via a **method** — "a predefined decomposition into subtasks that preserve ordering and constraint relationships" — and a single high-level/compound task may have *multiple* methods (multiple concrete decompositions) among which the planner chooses. Canonical sources: Erol, Hendler & Nau's UMCP formalization ([cs.umd.edu/~nau/papers/erol1994umcp.pdf](https://www.cs.umd.edu/~nau/papers/erol1994umcp.pdf)), Ghallab/Nau/Traverso's *Automated Planning* textbook (referenced throughout the HTN literature), and the general survey at [Wikipedia: Hierarchical task network](https://en.wikipedia.org/wiki/Hierarchical_task_network). This maps directly onto StealthLab's Procedure/Implementation split: a **Procedure is the compound task** (an abstract "way to accomplish a goal"), and each **Implementation is one method's grounding into a concrete, executable realization**.
- **RL/robotics: the options framework (policy vs. skill).** Sutton, Precup & Singh, "Between MDPs and SMDPs: A Framework for Temporal Abstraction in Reinforcement Learning" (*Artificial Intelligence*, vol. 112, 1999, [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0004370299000521)) formalizes an **option** as "a closed-loop policy for taking action over a period of time" that can be used interchangeably with a primitive action in planning/learning — the direct RL analogue of "one abstract action, many concrete realizing policies." This is the primary citable source for "policy vs. skill" framing; a *skill library* (multiple learned options achieving the same sub-goal, selected by context) is the direct RL-literature analogue of "many Implementations per Procedure."
- **LLM systems: cost-aware cascading (cheap-first-then-escalate).** FrugalGPT (Chen, Zaharia & Zou, Stanford, 2023, [arXiv:2305.05176](https://arxiv.org/abs/2305.05176)) is the primary source for the specific pattern requested: an **LLM cascade** sequentially queries cheaper models first and only escalates to a more expensive one when a learned quality-estimator (in the paper, DistilBERT-based) judges the cheap answer insufficient, via three components — an LLM router, a threshold-based quality estimator, and a cost-aware "stop judge." Reported result: matches GPT-4-level quality at up to 98% lower cost, or beats GPT-4 accuracy by 4% at equal cost.
- **LLM systems: learned routing (not cascading — one-shot binary choice).** RouteLLM (Ong et al., LMSYS, 2024, [arXiv:2406.18665](https://arxiv.org/abs/2406.18665), [github.com/lm-sys/RouteLLM](https://github.com/lm-sys/routellm)) is the primary source for training a router (via human preference data) to classify query complexity and route to a strong-vs-weak model up front, rather than cascading through multiple calls. Reported cost reductions: >85% on MT-Bench, 45% on MMLU, 35% on GSM8K vs. always using the strongest model, at comparable quality. This is the relevant citation if StealthLab ever wants a *pre-execution* implementation-selection classifier rather than a runtime try-cheap-then-escalate loop.
- **Agent frameworks: is "tool interface vs. multiple concrete providers, selected at runtime by cost/latency/success-rate" a formally named, shipped separation in a real OSS agent framework?** This pass did **not** find a framework (LangChain/LangGraph/AutoGen/CrewAI/Semantic Kernel) that ships this as a first-class, named abstraction with built-in cost/success-rate-based runtime selection across interchangeable providers for the *same* logical tool — routing/model-selection tooling (RouteLLM, LiteLLM-style model routers) exists as a separate layer bolted onto model *choice*, not onto arbitrary tool/skill implementations. **This is a genuine finding, not a gap in the search**: the closest real, shipped, and directly comparable thing is StealthLab's own `procedure_implementations` table plus `capabilities.py`'s Wilson-interval ranking (below) — worth stating plainly in any positioning material, per the existing competitive-sweep note in `.scratch/research/competitive-sweep-mem0-letta-zep-hipporag-awm.md` that this repo's trust-spine primitives (computed capability, evidence-gated) have no shipped analogue elsewhere.

### What StealthLab already has (do not rebuild)

- `backend/db/58_procedure_implementations_and_dependencies.sql`: a real, already-live many-to-many `procedure_implementations` table (482 real rows at the time that migration was written) with `role` (`primary`/`supporting`/`partial`/`verification`), `status` (`candidate`/`active`/`deprecated`/`disabled`/`quarantined`), `supported_capabilities`, `applicability`, `evidence_refs` — this **is** the HTN "multiple methods per compound task" relation, already schema-complete, bi-temporal (`t_valid`/`t_invalid`), and versioned (`implementation_version`/`implementation_version_constraint`).
- `backend/app/services/capabilities.py`: reuses the existing Wilson-lower-bound machinery from `procedure_extraction/capability.py` (`wilson_interval`, `band_for_p`, `route_for_p` — explicitly *not* the full `compute_capability`/`OutcomeRecord` gated ladder, because the `evidence` table has no `environment` column for implementation-targeted evidence, and the module's own docstring is explicit about refusing to fabricate one). `compare_implementations(pool, implementation_ids)` calls `get_implementation_capability` for each id and sorts descending by evidence-derived `p_estimate` — i.e., **success-rate-based ranking across multiple implementations of the same procedure already exists and is evidence-gated**, matching the "historical success rate" half of the requested design exactly.
- What's real and missing: **no cost or latency dimension anywhere in this path.** `compare_implementations` ranks purely by success probability; there is no analogue of FrugalGPT's cost-aware stop judge or RouteLLM's cost/quality trade-off. There is also no cascade/escalation *policy* object (try cheapest-with-acceptable-p_estimate first, escalate on failure) — only a ranked list a caller could choose to iterate, with no wiring that actually does so today.
- **Diversity is implicitly protected today by omission, not by design**: `run_dedup_sweep`'s default tuple (`task_nodes`, `knowledge_nodes`) does not include `implementations`, so nothing is currently at risk of over-merging distinct implementations into each other — but this is incidental (nobody added it), not an explicit guard. Worth a one-line comment in `dedup.py` saying implementations are intentionally excluded from complete-linkage dedup, so a future contributor extending the sweep doesn't wire it in by well-intentioned analogy to the procedures case.

### Recommendation (additive)

1. Add a `cost_hint` (numeric, nullable — e.g. relative $/call or a coarse tier enum) and `latency_hint` (nullable numeric, seconds) column to `procedure_implementations` via a new migration `73_procedure_implementation_cost_hints.sql` (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, additive, matches the immutable-migration convention — the next free number after `72_retrieval_index_freshness.sql`). Nullable by design, same posture as every other optional signal in this schema — a caller that never measured cost is not forced to fabricate one.
2. Add a pure function `rank_implementations_for_routing(capability_results, cost_hints, strategy="cheapest_acceptable" | "best_success")` in `capabilities.py` (or a new small module next to it) that composes the *existing* `compare_implementations` output with the new cost hint — a FrugalGPT-shaped cascade rule ("try the cheapest implementation whose Wilson lower bound clears a caller-supplied floor; escalate on failure") implemented as ordering logic only, no new evidence semantics, no touching `claim_belief.py`-adjacent code.
3. Do **not** add implementations to `run_dedup_sweep`'s tables — leave that a documented, deliberate omission (add the one-line comment above) so diversity is preserved by an explicit decision, not an accident.

## Problem 3 — Claim/fact semantic equivalence and contradiction (target: collapse dup, separate similarity from contradiction)

### What the literature says

**NLI 3-way classification is the standard, primary technique — and bidirectional entailment is the standard technique for paraphrase/equivalence specifically.** Natural Language Inference models classify a (premise, hypothesis) pair into `entailment` / `contradiction` / `neutral`. The standard extension to *equivalence* detection is **bidirectional entailment**: if premise entails hypothesis *and* hypothesis entails premise, the pair is a paraphrase (same fact); a one-directional entailment is a specialization/generalization relation (StealthLab's own `GENERALIZES`/`SPECIALIZES`), not identity; a `contradiction` label in either direction is a genuine conflict; `neutral` in both directions is "related but distinct," i.e. exactly the boundary the task asked for between similarity and contradiction. This is not a StealthLab-specific idea — the extraction-and-filtering-of-paraphrases-via-NLI line of work makes the connection explicit ("paraphrases are bidirectional entailments... contradictions receive low similarity scores"), see [arXiv:2111.07119](https://arxiv.org/pdf/2111.07119). Concrete, citable model names for the entailment/contradiction/neutral classifier itself: `roberta-large-mnli` (fine-tuned on MultiNLI) and the DeBERTa-v3 NLI family — `MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli` (trained on 885,242 NLI pairs across MultiNLI, Fever-NLI, ANLI, LingNLI, WANLI; documented as the best-performing open NLI model on HF Hub as of its release) and the `cross-encoder/nli-deberta-v3-{small,base,large}` family, which output exactly the 3-way (contradiction/entailment/neutral) score StealthLab would need. Sources: [huggingface.co/MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli](https://huggingface.co/MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli), [huggingface.co/cross-encoder/nli-deberta-v3-large](https://huggingface.co/cross-encoder/nli-deberta-v3-large).

**Fact-checking pipelines: claim decomposition + verification, at scale.** DeepMind's SAFE (Search-Augmented Factuality Evaluator, from "Long-form factuality in large language models," Wei/Yang et al., NeurIPS 2024, [arXiv:2403.18802](https://arxiv.org/pdf/2403.18802), code [github.com/google-deepmind/long-form-factuality](https://github.com/google-deepmind/long-form-factuality)) is the primary source for the specific pipeline shape "decompose a response into individual atomic facts → make each fact self-contained → check each against search results" — it reports ~72% agreement with human raters and, on disagreement cases, wins 76% of the time against human annotators, at ~20× lower cost than human annotation. This is directly relevant to StealthLab's atomic-Claim model: SAFE's "atomic fact" is the same unit of analysis as a StealthLab `Claim` (`subject`/`predicate`/`object` triple).

**Record linkage / entity resolution — Fellegi-Sunter, adapted to propositions.** The Fellegi-Sunter model (1969) is the founding statistical framework for record linkage: compare record pairs across fields, compute a likelihood ratio of match-probability to non-match-probability, classify each pair as link / non-link / possible-link-needing-review, with **blocking** used first to avoid the full cartesian product of comparisons. This generalizes cleanly to claim-pairs: block by subject/predicate (or by embedding-nearest-neighbor, StealthLab's existing pattern), then classify each blocked pair (via NLI, not a field-comparison vector) as equivalent / distinct / needs-review. Source: overview and modern implementations at [PMC9336505 — a two-step Fellegi-Sunter procedure](https://pmc.ncbi.nlm.nih.gov/articles/PMC9336505/), and the general survey ["(Almost) All of Entity Resolution," arXiv:2008.04443](https://arxiv.org/pdf/2008.04443).

**Agent memory systems — what each actually does about duplicate/contradictory memories:**
- **Mem0**: the Memory Updater retrieves the top semantically-similar existing memories via vector embeddings and hands them, plus the new candidate fact, to an LLM function-calling interface that decides per-candidate: `ADD` (genuinely new), `UPDATE` (augment with more recent/detailed info), `DELETE` (remove a memory the new fact contradicts), or `NOOP` (already present/irrelevant) — i.e. **contradiction handling in Mem0 is LLM-judgment-based and destructive (DELETE) rather than bi-temporal**; a documented community-reported failure mode is that this resolver "runs on text similarity rather than application-level scope and cannot distinguish between 'the user changed their mind' and 'the user has two preferences that both hold in different contexts.'" A separate graph variant, Mem0g, instead marks graph relationships invalid (supports temporal reasoning) rather than deleting — closer to StealthLab's own truth-maintenance posture. Sources: paper [arXiv:2504.19413](https://arxiv.org/abs/2504.19413), architecture writeups: [Dwarves Memo — Mem0 breakdown](https://memo.d.foundation/breakdown/mem0), [dev.to — Mem0 auto-resolves memory conflicts](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m), docs: [docs.mem0.ai/core-concepts/memory-operations/update](https://docs.mem0.ai/core-concepts/memory-operations/update).
- **Zep / Graphiti**: bi-temporal by construction — every edge (fact) carries both an event-time validity window (`t_valid`/`t_invalid`) and a system ingestion-time pair (`t'_created`/`t'_expired`). When new information is extracted that temporally overlaps and contradicts an existing edge, Graphiti **invalidates** the old edge (`t_invalid` set to the new edge's `t_valid`) rather than deleting it, "preserving historical accuracy without large-scale recomputation." This is architecturally the closest published system to StealthLab's own `truth_state` IN/OUT flip in `claims.py::relate_claims` — the material difference is that **Graphiti's invalidation is triggered automatically by its own temporal-extraction pipeline detecting an overlapping contradiction**, whereas StealthLab's `relate_claims(relation="CONTRADICTS")` is **only ever called explicitly by a caller who has already decided** two claims contradict — there is no automatic detector. Sources: paper [arXiv:2501.13956](https://arxiv.org/pdf/2501.13956), [Zep temporal knowledge graph explainer](https://www.getzep.com/ai-agents/temporal-knowledge-graph/), [Neo4j — Graphiti overview](https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/).
- Neither Mem0 nor Zep/Graphiti publishes a specific NLI-model-based equivalence detector by name — both use an LLM call (Mem0 explicitly; Graphiti's extraction step implicitly) rather than a dedicated fine-tuned NLI classifier. This is worth noting as a real gap in the field, not just in this repo: **nobody publishes "we run RoBERTa-MNLI bidirectionally to collapse claim duplicates"** — that specific technique is well-established in the general NLP paraphrase-detection literature (cited above) but this pass found no agent-memory production system citing it by name for this exact purpose. If StealthLab built it, it would be applying an established general technique to a use case the current agent-memory field handles more crudely (LLM judgment call, no formal 3-way separation of same-fact/related/contradictory).

### What StealthLab already has (do not rebuild, do not touch `claim_belief.py`)

- `backend/app/services/claims.py::RELATIONS = {"SUPERSEDES", "CONTRADICTS"}` and `relate_claims(...)`: writing a `CONTRADICTS` edge is **100% manual today** — `relation` is a required caller-supplied string, validated only against the fixed set; there is no text/embedding/NLI comparison anywhere in this function. It does the *consequence* of contradiction correctly (flips `truth_state` to `OUT`, recomputes belief via `claim_belief.recompute_claim_belief` — read-only call into the frozen module, not a modification of it — and propagates staleness to dependent procedures via `claim_impact.propagate_claim_change`), but it never *detects* that two claims conflict; something upstream (a human, a debate, an extraction pipeline) has to already know.
- `GENERAL_RELATIONS` (`SUPPORTS`, `REFINES`, `DEPENDS_ON`, `CONDITIONAL_ON`, `GENERALIZES`, `SPECIALIZES`, `DERIVED_FROM`, `INSTANTIATES`, `APPLIES_TO`) via `link_claims()`: this is exactly the "related but distinct" bucket the NLI `neutral` label (or a one-directional entailment, for `GENERALIZES`/`SPECIALIZES` specifically) would populate — the vocabulary already exists and is richer than a flat "equivalent/contradictory/unrelated" scheme; a Claim-equivalence detector should **write into this existing vocabulary**, not invent a new relation type.
- `knowledge_nodes.embedding VECTOR(1024)` already exists (`backend/db/01_ontology.sql`) and `capture_claim` already computes and stores an embedding for every claim it writes (this was itself a "REAL BUG FIXED" note in the current `claims.py` — claims used to be written with no embedding at all, making them invisible to retrieval; that is now fixed) — so an embedding-based pre-filter for claim-pairs has zero migration cost, the column is already populated for every live claim.
- `claim_belief.py`'s independence-group de-duplication (`COALESCE(independence_group, id::text)`) already solves a *different* but related problem — collapsing non-independent *evidence* so it isn't double-counted — and its module docstring is explicit that this logic must not be touched. **This is not the same mechanism as claim-equivalence** (evidence independence is about not double-counting corroboration for one claim; claim equivalence is about not splitting one fact's evidence across two differently-worded claim rows) — the recommendation below is additive and upstream of `claim_belief.py`, never inside it.

### Recommendation (additive, no `claim_belief.py` change, no destructive migration)

1. New migration `73_claim_equivalence_relation.sql` (or bundled with the implementation cost-hint migration above as `73`/`74` in sequence): add `'EQUIVALENT_TO'` support the same way `CONTRADICTS` already rides the existing `VALIDATED_BY` + `custom_edge_type` idiom — **no ALTER TYPE, no new column, no new table** (frozen-schema-compliant: `edge_type` enum stays untouched, exactly like `CONTRADICTS`/`DUPLICATE_OF` today). This is a one-line addition to `claims.py`'s `GENERAL_RELATIONS` set (or a small sibling set, `EQUIVALENCE_RELATIONS = {"EQUIVALENT_TO"}`), not a migration at all if the existing `link_claims()`/`GENERAL_RELATIONS` machinery is reused directly — flag this to whoever picks up the ticket: it may need **zero migration**, only a service-layer vocabulary addition.
2. New pure function `detect_claim_relation(claim_a_text, claim_b_text, nli_model=...) -> "equivalent" | "contradicts" | "related" | "unrelated"` (new module, e.g. `app/services/claim_equivalence.py`, mirroring `claim_evidence.py`'s naming precedent cited in `capabilities.py`'s own docstring) implementing: (a) embedding cosine pre-filter (reuse the existing `Embedder`/`to_pgvector` plumbing `claims.py` already uses) to shortlist candidate pairs cheaply; (b) for shortlisted pairs, a bidirectional NLI pass (`cross-encoder/nli-deberta-v3-base` or similar — pick a model per the cited HF cards above) — `entailment` both directions → `equivalent`; `contradiction` either direction → `contradicts`; otherwise `related`/`unrelated` by whether the pre-filter score cleared a lower bound. This function is **pure/offline-callable** (no DB, no tenant scope), matching this repo's existing pattern of keeping the scoring math (`compute_belief`, `wilson_interval`) separate from the write path that persists its result.
3. A thin async wrapper, `sync_claim_relations(pool, claim_id, candidate_ids, ...)`, that calls `detect_claim_relation` pairwise and then calls the **existing, unmodified** `relate_claims(relation="CONTRADICTS")` or `link_claims(relation="EQUIVALENT_TO"/other GENERAL_RELATIONS member)` for each detected pair — this wrapper is the only place that touches the DB, and it composes primitives that already exist rather than duplicating their transaction/belief-recompute/propagation logic. Suggested integration point: called from `capture_claim`'s existing candidate-retrieval step (it already computes an embedding for every new claim; the marginal cost is a nearest-neighbor query plus, for a small number of high-similarity survivors, one NLI forward pass) — but as an **optional, best-effort post-write step** (same "must not fail the write it rides on" posture `relate_claims`'s own belief-recompute already follows), never gating `capture_claim`'s return value.
4. Explicitly do **not** auto-apply `EQUIVALENT_TO` merges the way `dedup.py::merge_cluster` auto-merges procedures — a detected claim contradiction is exactly the kind of thing this repo's own Phase-31 posture (`claims.py`'s own comment: "borderline cases get reviewed, not auto-resolved") says should surface for review rather than be silently resolved. A `contradicts` detection is a strong candidate for feeding `knowledge_conflict.py`'s existing open-trigger/debate mechanism (already read by `has_open_conflict_trigger`) rather than calling `relate_claims` directly and unilaterally flipping `truth_state` — worth a design decision for whoever implements this, flagged here rather than resolved, since it touches the debate/approval surface this research task was told not to redesign.
