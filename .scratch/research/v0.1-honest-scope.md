## What v0.1 actually does today

A **local-first MCP server** you run on your own machine against your own
Postgres, fed by a Claude Code hook:

1. **Traces flow in.** Hook → redaction (client-side, before anything is
   written or sent anywhere) → `agent_traces`/`trace_events`.
2. **Episodes get assembled**, then **procedures get distilled** from them —
   scope + provenance required, nothing enters the graph without both.
3. **Reuse is retrievable, precisely — not as broadly as it once claimed.**
   `retrieve_precedent` returns prior solved patterns ranked by raw
   cosine similarity (name/id/similarity only — no confidence score, no
   provenance chain, corrected in `demo.md` 2026-08-27 after that wording
   was found to be simply wrong for this tool). A `procedures` match here
   is always a **verified, approved** one; a freshly-extracted candidate
   procedure will not show up here by design (a 2026-08-27 founder ruling
   rejected surfacing unverified procedures in this tool as a false-reuse
   risk — see the reuse-trust section below for what that means day one).
4. **Refusal is real, and it's the differentiator.** `check_procedure`
   (tool #9 as of `main`, `backend/app/mcp_server/server.py:797`) returns a
   genuine `ALLOW` / `WOULD_REFUSE` verdict naming the specific superseded
   claim (and a changeset id, when one exists). This landed as a real tool
   with 15 offline proving tests — it is not a stub or a demo-only path.
5. **It's audit mode, on purpose.** Every refusal is informational; nothing
   is blocked. Blocking enforcement is explicitly out of scope until Band 3
   (`demo.md` §4).

Full offline suite: **1505 passed / 115 skipped / 0 failed** (measured
directly on commit `870ba7c`, 2026-08-28 — supersedes the `1368` figure
`proj_status.md` still carries as of this writing, per the board's own
correction note on `d0818b4`; this number moved twice more, 1368→1465→1505,
in the few hours this doc was being written).

## The one thing most likely to surprise a first user: reuse needs earned trust first

`solve_task` and `check_procedure`'s automatic retrieval path default to
`require_verified=True`. A procedure only becomes "verified" — and only then
does it surface automatically — after it clears a real evidence bar:
**≥10 successes, 0 failures, ≥3 distinct contexts** (Wilson-lower-bound
capability bands, `procedure_extraction/capability.py`).

**On a fresh install, this means automatic reuse returns nothing at first.**
There's no backfill, no bootstrapped trust — v0.1 is fresh-start-honest by
design (`demo.md` §2.4). The system has to actually watch a procedure
succeed repeatedly, in enough distinct contexts, before it will offer it
back to you unprompted.

The escape hatch is `allow_unverified_procedures=True` on `solve_task`
(`server.py:458,537-546`): it opts a call into also considering procedures
this same extraction pass created but that haven't earned that evidence
yet. It's a deliberate "try a candidate on its own unverified merits"
choice, surfaced honestly as `UNVERIFIED — use at your own judgment`
(`server.py:639`) — not a way to make verification optional by default, and
not on unless you ask for it. **A new user who expects day-one "it already
knows my patterns" behavior will not get it; that behavior is earned over
repeated real use, not present out of the box.**

**Worth knowing: this flag was completely unreachable until today.**
Commit `f7262a5` (2026-08-28) found and fixed a real chicken-and-egg bug:
`find_applicable_procedures` ran a separate cold-start gate
(`should_disable_procedure_retrieval` — "disabled until ≥1 VERIFIED
procedure exists") *before* even checking `require_verified`, so passing
`allow_unverified_procedures=True` made no difference — nothing could ever
match, so nothing could ever accumulate the evidence needed to become
verified, so the gate never opened. Fixed as a one-line change
(`if require_verified and await should_disable_procedure_retrieval(...)`);
proven with real numbers the same day: `require_verified=True` still
correctly returns 0 matches (default preserved), `require_verified=False`
now returns 1 real match, and a real execution against it recorded both a
supporting and a contradicting evidence row. This is genuinely new — the
trace → procedure → reuse → evidence → capability loop had never run
end-to-end on real data before this commit.

**A second, separate, still-open gap surfaced by that same live run:**
procedure extraction is structurally blocked whenever a task description
names a specific file. Only `deterministic_v1` is registered as an
extractor today, and it sets a field called `capability_statement` to the
task's goal text verbatim; a separate validator
(`v4_capability_abstraction`) rejects any evidence token — e.g. a
filename — in that same field. So the ordinary way people phrase coding
tasks ("fix the bug in `src/geometry.py`") reliably produces
`extraction_skipped`, while the same task reworded without a filename
produces a real procedure. This was proven decisively (same repo, same
model, wording changed, outcome flipped) rather than inferred, and is
explicitly not fixed yet — flagged as CORE-B's call, not this lane's.

## Episode coverage is partial, and the repo says so

The episode segmenter that ships in `trace_worker.py` is built from a
**36-session, 28,969-line prototype study**
(`experiments/episode_assembly/FINDINGS.md`), not a formally validated
system — there is no gold-boundary precision/recall number anywhere,
because no gold boundaries exist to score against. The study's own stated
target was 70–80% agreement (matching human inter-annotator agreement on
task boundaries), not >90%.

Concretely, this means:
- **~18% of prompt-boundary episodes are trivial** (≤2 events) and get
  folded into their successor by a merge rule — real, but a real
  approximation, not a clean cut.
- **Oversize episodes (>200 events, no internal commit/test signal) are
  never subdivided** — they stay whole and get flagged
  `oversize_unsubdivided` in metadata rather than an invented cut being
  made up. If a session produces one of these, procedure extraction sees
  one very large, undifferentiated episode.
- **Idle-gap timing was tested and dropped as a signal entirely** — the
  literature's assumed bimodal gap distribution does not exist in real
  agent transcripts (measured, not assumed: fitted valleys landed 3 orders
  of magnitude below the ~1h the prior ticket expected). There is no
  temporal boundary rule anywhere in the shipped segmenter.
- The findings doc explicitly flags that **procedure-mining still needs its
  own option-span segmenter** over subgoal/bottleneck boundaries — a
  different segmentation problem, "currently owned by no ticket, not part
  of milestone 1." Episode boundaries and procedure boundaries are not the
  same thing yet.

None of this is a bug — it's a documented, measured tradeoff. But a user
should know that episode/procedure boundaries are a best-effort heuristic
tuned on one project's own session corpus, not a formally scored system.

One more data point, from a real run the same day this doc was written
(see "What isn't done yet" below): the free, no-model-calls ingestion path
(`scripts/run_ingestion.py`) doesn't even reach the segmenter — it stops at
`observations` and never calls `assemble_episodes()` at all. So today,
episode assembly only actually runs inside `solve_task`'s live-model path,
not the free/offline one; a user relying on the zero-cost ingestion script
alone will never see an episode row, independent of the coverage caveats
above.

## What isn't done yet

**Good news first, since it changed today: `bootstrap_demo.py` is fixed.**
An earlier draft of this doc (and `PRODUCTION_READINESS.md` before it) said
the script didn't implement the two-phase story at all. As of `main`
(`demo.md` §3, checklist items now `[x]`), it genuinely does: Phase A
extracts a real procedure with real preconditions derived from
`project_state()`; Phase B genuinely invalidates the claim behind one
precondition and `check_procedure` really flips `ALLOW` → `WOULD_REFUSE`,
citing it. This was independently checked against the raw database rows
(the `SUPERSEDES` edge, both claims' `truth_state`), not just the script's
own printed output, and run on a genuinely fresh disposable DB. `demo.md`'s
own real, engine-verified example is now in its §3, not a hypothetical.

**What's still genuinely open is narrower, and now precisely measured
rather than assumed:** `demo.md` §3's README-quickstart checklist item was
split in two on 2026-08-28 because half of it is done and half is
structurally blocked, not just untried:
- **Connection/infrastructure half — done.** Clean clone → `docker compose
  up -d --build` → 30/30 migrations on a fresh volume → a real Claude Code
  instance connected as the MCP client (not a stub) → auth checks pass
  (unauthenticated `POST /mcp` → 401, authenticated → 200) → all 9 tools
  resolve. (One doc bug found doing this: `--build` is load-bearing —
  without it, `docker compose up -d` after a `git pull` silently keeps
  running the stale image and looks like a pass when it isn't. Now fixed
  in `docker-compose.yml`'s own instructions.)
- **Reuse-demonstration half — still open.** "Solve one task, then solve a
  similar one and see it cite precedent" doesn't work yet on a fresh
  install, and the reason is now measured exactly: running the real,
  free ingestion path (`scripts/run_ingestion.py`, no model calls) over a
  real 1.1MB session trace (3813 collector events) gets to
  `agent_traces` 13 → `trace_events` 3813 → `observations` 2697, **then
  stops** — `episodes`, `knowledge_nodes`, `claim_sources`, `procedures`,
  and `evidence` all read 0. The break is specifically at
  **observation → claim**; episode assembly is bypassed entirely by this
  path (`run_ingestion.py` never calls `assemble_episodes`), and
  `extract_procedure()` today has exactly one live caller, `solve_task`
  (`server.py:719`) — so closing this gap needs either a real model call
  through `solve_task`, or a documented zero-cost path that doesn't exist
  yet. Give `bootstrap_demo.py` partial credit here, not a flat "still
  broken": it already proves the *decision* half of "reuse you can see"
  (a real extracted procedure, real preconditions, real refusal). What's
  missing specifically is precedent arriving from the agent's *own prior
  work* through the normal tool-use path, which is what this checklist row
  is actually for.

**A licensing contradiction, flagged as BLOCKING by the infra lane the same
day this doc was written, worth repeating here because it's exactly the
kind of thing that could overpromise to a first user:** `demo.md` states
"Apache-2.0" as v0.1's license; `packaging/pyproject.toml` says
`license = { text = "Proprietary" }`; and there is **no `LICENSE` file at
the repo root at all** — confirmed directly, `ls LICENSE*` finds nothing.
A public GitHub repo with no LICENSE file is legally all-rights-reserved by
default, which contradicts what `demo.md` tells a reader and disagrees with
`pyproject.toml` besides. This needs a founder ruling before it ships to
anyone who might rely on the stated license — do not repeat "Apache-2.0" as
settled fact until this is resolved.

## Explicit non-goals for v0.1 (per `demo.md` §4 — don't oversell these)

- Blocking enforcement of refusals (audit mode only until Band 3)
- `explain_failure`/`explain_decision` receipts UI
- Hosted, multi-tenant, or team-scoped use — single-user local only
- Crypto-shredded deletion; capability-based auto-routing thresholds
- Any client conformance beyond Claude Code + one OpenAI-compatible client

## Security/data posture, in one paragraph

Loopback-only by default; the bearer token is authentication, not
authorization — anyone holding it can call the ungated `apply_change_set`
write primitive or point `solve_task` at any path on the server's
filesystem, and (see above) that call isn't network/resource-isolated in
the shipped container today, only host-side. Redaction is a real, tested
choke point but a documented best-effort floor, not a guarantee — and as
of 2026-08-28 that floor has real-corpus evidence behind it, not just unit
tests: a real 3813-event session trace run through redaction produced zero
AWS-key-shaped matches, zero Anthropic-key-shaped matches, and zero SSH
references, with 5 rows caught by pattern redaction and 32 by the
sensitive-path exclusion. No telemetry, no training on user traces, no
hosted backend in v0.1 — the only network egress is to whichever embedding
provider you configure, with your own key. Full detail and threat model in
`SECURITY.md` and `DATA_STATEMENT.md`; nothing above should be treated as
superseding those documents — this is the plain-language summary, they're
the authoritative source. (The licensing status above is a legal question,
not covered by either of those documents — don't infer an answer from
them.)

# Secrets pass

**Verdict: NOT CLEAN. Real, live-looking credentials exist in local git
history. They are not currently reachable from `origin` (not on GitHub),
but they exist in this machine's local git object store and must be
treated as compromised.**

## What was checked

- Current working tree: all tracked files, plus the one untracked file
  present at scan time (`.scratch/export-research-final.json`).
- Full history on **every local branch, every `origin/*` remote-tracking
  branch, and `refs/stash`** (`git log --all -G'<pattern>' -- .`), not just
  the current tip — patterns covered AWS keys, GitHub/Slack/Stripe/OpenAI/
  Anthropic/Google/Groq/General Compute/Voyage key shapes, PEM private-key
  blocks, JWT-looking strings, credentialed Postgres URLs, and a generic
  `(api_key|secret|password|token) = <16+ chars>` sweep.
- 307 total commits across all refs — small enough to check exhaustively,
  not sampled.

## The real finding

Two commits — `5e2f9bd` ("make 1+3 better", 2026-08-11) and its child
`c00b72f` ("On main: WIP before pull") — committed a real `backend/.env`
containing:

- `DATABASE_URL` — a live Supabase connection string with a real username
  and password (`postgres.mlirwhlbjwrnyvfwiddc:AnujIIScUNSW@...`)
- `VOYAGE_API_KEY` — a real-shaped Voyage AI key (`pa-...`)
- `GENERAL_COMPUTE_API_KEY` — a real-shaped General Compute key (`gc_...`)
- (in the child commit) `ANTHROPIC_API_KEY` — a real-shaped Anthropic key
  (`sk-ant-api03-...`)
- (in the child commit) `GROQ_API_KEY` — a real-shaped Groq key (`gsk_...`)

**These two commits are reachable only from `refs/stash`** — verified by
walking every ref (`git for-each-ref`) and checking ancestry: not an
ancestor of any local branch, and not an ancestor of any `origin/*`
branch (`main`, every `lane/*`, every `research/*`). They were never
pushed. But `refs/stash` is a real ref backed by real objects in this
machine's `.git` — the secrets physically exist on disk right now, in a
stash entry shared across every worktree on this machine, not just a
dangling commit that will be garbage-collected imminently.

## What was ruled out (checked, not assumed)

- `backend/.env.example` (currently tracked) is placeholder-only — checked
  directly.
- Every other regex hit across the full history sweep was a confirmed false
  positive: redaction-module test fixtures using deliberately dummy
  secret-shaped values (`AKIAIOSFODNN7EXAMPLE` — AWS's own published
  example key, `ghp_aaaa...`, placeholder PEM blocks with `abc`/`...` for
  key bytes), local-dev Postgres URLs with non-secret defaults
  (`postgres:postgres`, `postgres:stealthlab`, `user:pass`), and one
  `api_key="not-needed-for-local"` literal (the Ollama local-model stub).
  None of these are real credentials.
- No `.env`, credentials file, `id_rsa`, or `secrets.json` was ever
  committed anywhere else in the 307-commit history besides the one commit
  above.
- The current tree has no tracked `.env`; `backend/.env` today is correctly
  gitignored and untracked.

## Recommendation (not executed — these are the founder's calls)

1. **Rotate all five credentials above now**, regardless of push status —
   Supabase DB password, Voyage key, General Compute key, Anthropic key,
   Groq key. Local-only exposure is still exposure (anyone with filesystem
   or backup access to this machine's `.git` can recover them via
   `git stash show`/`git fsck --unreachable`).
2. **Decide how to clean the stash entry.** This session did not drop or
   rewrite anything — the stash stack is shared across every worktree on
   this machine, and dropping/rewriting it isn't a call one lane should
   make unilaterally. Once credentials are rotated, the stash entry itself
   stops being sensitive (rotated secrets are useless to find), so cleanup
   becomes routine hygiene rather than urgent.
3. Going forward, a pre-commit secrets scan (gitleaks/trufflehog or
   similar) would have caught this at commit time instead of at a manual
   pass three weeks later — worth raising with whoever owns CI, outside
   this lane's file ownership.
