# Producing High-Performing Developer-Tool Demo Videos Programmatically (as of Sept 2026)

## Remotion: version, AI/Claude Code integration, rendering, licensing, captions, data-driven video

### Takeaway
Remotion is a React-based programmatic video framework, currently on the 4.0.4xx line (5.0 not yet released as of Sept 28, 2026) with an official Claude Code plugin and Agent Skills that let Claude scaffold and edit Remotion projects directly; it renders locally via CLI or at scale via Remotion Lambda, and has a headcount-based (not ARR-based) free/paid licensing split — companies with more than 3 people must buy a Company License. `@remotion/captions` provides a standard caption data shape usable for burned-in, data-driven captioned videos.

### Cited Findings
- The official Claude Code plugin is installed with `claude plugin marketplace add remotion-dev/claude-code-plugin` then `claude plugin install remotion@remotion`, followed by a Claude Code restart; once installed, asking Claude Code to "create or edit a Remotion video" auto-loads the relevant skills, and skills can be invoked directly, e.g. `/remotion-best-practices Make a promo video for a record store`. — [Remotion Claude Code plugin docs](https://www.remotion.dev/docs/ai/claude-code-plugin)
- Remotion also publishes standalone Agent Skills (for Claude Code, Codex, Kimi Code, Cursor, etc.) installable in a project via `npx remotion skills add`; skills include `/remotion-create` (scaffold a project/composition), `/remotion-markup` (best practices for Remotion React markup — compositions, animation, layout, typography, media, effects, audio, fonts, timing), `/remotion-docs` (fetch current Remotion docs pages as Markdown for API lookups), and a skill for map animations (static maps, animated routes/markers, 3D flyovers). — [Remotion Agent Skills docs](https://www.remotion.dev/docs/ai/skills), [remotion-dev/skills on GitHub](https://github.com/remotion-dev/skills)
- Remotion's "Prompting videos with coding agents" doc and "Building with Remotion and AI" landing page frame Remotion explicitly as the tool for agent-driven video generation. — [remotion.dev/docs/ai/coding-agents](https://www.remotion.dev/docs/ai/coding-agents), [remotion.dev/docs/ai/](https://www.remotion.dev/docs/ai/)
- Current npm version is 4.0.526 (published ~3 days before Sept 28, 2026), with the docs elsewhere referencing 4.0.507; the 4.0.4xx series ships at a near-daily cadence. Remotion 5.0 is planned with breaking changes documented but not yet released. — [npm remotion package](https://www.npmjs.com/package/remotion), [Remotion VERSION docs](https://www.remotion.dev/docs/version), [5.0 Migration doc](https://www.remotion.dev/docs/5-0-migration)
- The single largest 2026 Remotion development was "Agent Skills," which launched in January 2026, per a third-party tracker (not Remotion's own blog) — treat as a secondary characterization, not confirmed by Remotion directly in this research pass. — [autoae.online "Remotion in 2026" tracker (third-party)](https://autoae.online/blog/remotion-updates-2026)
- Licensing (official docs): the Free License covers "an organization or team of individuals with up to 3 people," for-profit orgs with ≤3 employees, non-profits, and people evaluating without commercial use. A Company License is required once headcount is 4+. Commercial use itself is broadly allowed under both license tiers; the restriction is specifically against "selling Remotion as a product itself or allowing people to circumvent cases where they would have to buy a license themselves" (e.g., rendering personalized videos from your own templates is fine; letting end users submit arbitrary Remotion projects for you to render is not). — [Remotion License FAQ](https://www.remotion.dev/docs/license/faq)
- Two paid plans, and they can be combined (with a shared $100/month minimum): **Remotion for Creators** — $25/month per person who writes Remotion code themselves or via agentic coding tools (for non-automated video production); **Remotion for Automators** — $0.01 per successful render with a $100/month minimum, for automated pipelines, video editors, prompt-to-video products, and other programmatic rendering (CLI/API calls). Developers who only build automations (not hand-authoring compositions) don't need Creators seats. — [Remotion License FAQ](https://www.remotion.dev/docs/license/faq), [Remotion License & Pricing](https://www.remotion.dev/docs/license/pricing) (pricing page content is client-rendered and could not be directly scraped; figures above are corroborated via the FAQ page and cross-checked against a third-party summary — see note below)
- Rendering options: locally via the Remotion CLI/Node APIs, or via **Remotion Lambda** (`@remotion/lambda`, `renderMediaOnLambda()` / `renderStillOnLambda()`) for distributed, parallel AWS-based rendering. Lambda is "recommended for most people" per Remotion's own comparison doc, citing best tradeoff of speed, ease of setup, maturity, total cost, and scalability; it bills by GB-seconds of execution time, so 10 parallel Lambdas running 1 minute each costs the same as 1 Lambda running 10 minutes — you get ~10x wall-clock speed for the same cost. Local rendering parallelizes only up to available CPU cores and can take hours for large batches (e.g., 1000 videos sequentially), and ties up a machine/server even when idle. — [Comparison of server-side rendering options](https://www.remotion.dev/docs/compare-ssr), [How much does Remotion Lambda cost?](https://www.remotion.dev/docs/lambda/cost-example), [Remotion Lambda docs](https://www.remotion.dev/docs/lambda)
- Lambda usage falls under the Automators pricing bucket ($0.01/render, $100/month minimum) per the License FAQ; there is no separately documented Lambda-specific license fee beyond AWS's own compute costs. — [Remotion License FAQ](https://www.remotion.dev/docs/license/faq)
- `@remotion/captions` defines a standard `Caption` type: `{ text: string; startMs: number; endMs: number; timestampMs: number | null; confidence: number | null; }`, enabling captions from different transcription sources (via `toCaptions()` converters) to be normalized into one shape usable across Remotion caption components. `createTikTokStyleCaptions()` formats captions into "pages" for TikTok/Reels-style word-group display. — [@remotion/captions API docs](https://www.remotion.dev/docs/captions/api), [Captions overview](https://www.remotion.dev/docs/captions/)
- Remotion supports fully data-driven video generation: build a React video template with props, then feed it JSON/API data (including a per-video captions JSON file) to programmatically render many personalized videos. — [terminalskills.io "Build Programmatic Videos with Remotion" (third-party)](https://terminalskills.io/use-cases/build-programmatic-videos-with-remotion), [@remotion/captions API docs](https://www.remotion.dev/docs/captions/api)

### Inferences
- For a startup's dev-tool demo video pipeline built with a coding agent, the natural setup is: install the Claude Code plugin/skills, author a data-driven Remotion composition (JSON props + captions JSON), render locally for one-offs/iteration, and switch to Remotion Lambda once you need to batch-render variants (e.g., per-feature or per-platform cuts) or need faster turnaround than local CPU parallelism allows.
- If the team (including agent-driven "renderers") stays at 3 people or fewer, Remotion is free; StealthLab-style small teams likely qualify for the Free License, but should re-check headcount before scaling render pipelines or hiring, since crossing to 4 people triggers a Company License (Automators plan is the relevant one for CI/agent-triggered rendering, at $0.01/render with a $100/month floor).

- Could not directly scrape `remotion.dev/docs/license/pricing` (client-rendered React content) to independently confirm the $25/seat and $0.01/render numbers beyond the FAQ page text — these are corroborated by the FAQ page's own quoted pricing language, so confidence is high, but a live-page visual check would be prudent before finalizing budget assumptions.

The official docs (headcount-based) should be treated as authoritative; the ARR-based claim appears to be either outdated, describing a different/older license version, or simply inaccurate. Flagging explicitly since the two sources disagree.

## Terminal recording: VHS, asciinema/agg, alternatives — deterministic, legible footage

### Takeaway
VHS (charmbracelet/vhs) is the standard tool for deterministic, scripted terminal recordings via declarative `.tape` files, output to GIF/MP4/WebM and scriptable in CI; asciinema+agg is a lighter-weight alternative (record real interactive sessions as text, convert to GIF via the gifski-based `agg`) but isn't inherently scripted/deterministic the way VHS is. For legibility (especially at small/mobile size), use a larger-than-default font size (documentation examples use `Set FontSize 40`, with 20 cited as a legibility floor for GitHub README/doc previews), a high-contrast theme (e.g. Catppuccin Mocha), and a Nerd Font monospace family.

### Cited Findings
- VHS lets you write a `.tape` script (a sequence of commands) that VHS "plays" against a virtual terminal to produce a recording without any live interactive session — this is what makes it deterministic and repeatable, unlike live screen recording. Core commands include `Type` (simulate keypresses/typing), `Set` (global terminal settings: font, window size, GIF output path, etc.), and `Screenshot` (capture a single PNG frame). — [charmbracelet/vhs GitHub](https://github.com/charmbracelet/vhs), [VHS demo.tape example](https://github.com/charmbracelet/vhs/blob/main/examples/demo.tape)
- VHS can output GIF, MP4, and WebM, and is designed to integrate into CI/CD pipelines for automated demo/doc generation. — [x-cmd VHS overview](https://www.x-cmd.com/pkg/vhs/), [tenthirtyam.org "How to Create Terminal Demos as Code with VHS" (third-party, Apr 2026)](https://tenthirtyam.org/dispatches/2026/04/16/how-to-create-terminal-demos-as-code-with-vhs-by-charm/)
- Font/theme controls in `.tape` files: `Set FontFamily`, `Set FontSize`, `Set Theme`, `Set Height`/`Set Width`, `Set LetterSpacing`, `Set LineHeight`. A documented legibility guideline: FontSize 20 is described as large enough to "stay readable in GitHub READMEs and docs previews," and an example documentation-oriented config uses `Set FontFamily "JetBrainsMono Nerd Font Mono"`, `Set FontSize 40`, `Set Theme "Catppuccin Mocha"`, `Set LineHeight 1.0`. — [x-cmd VHS overview / third-party VHS write-ups](https://www.x-cmd.com/pkg/vhs/)
- Guidance (third-party, practitioner-authored): "a good terminal GIF should teach, not distract" — font must be legible, pacing must feel intentional, and commands should reflect what a developer would actually type (i.e., realistic, not synthetic-looking input). — [x-cmd VHS overview (third-party)](https://www.x-cmd.com/pkg/vhs/)
- Asciinema records terminal sessions as text-based data (asciicast format) and is simple to install with "almost no configuration required," but needs a companion tool (`agg`) to convert to GIF. `agg` ("asciinema gif generator") uses the gifski library to produce optimized, high-quality GIFs with accurate frame timing. — [agg - asciinema docs](https://docs.asciinema.org/manual/agg/)
- Comparative note (third-party, Mastodon/HN commentary, treat as opinion not fact): VHS supports higher frame rates than other tools and is fully scriptable, making it well-suited to CI-generated documentation GIFs, with commentary praising the ability to script an entire demo, grab screenshots of specific frames, and get a cleaner GIF than `agg` typically produces. `t-rec` is mentioned as a further alternative that records the actual terminal window rather than session text. — [awesome-terminal-recorder GitHub list](https://github.com/orangekame3/awesome-terminal-recorder), [untrusted.website Mastodon post (third-party opinion)](https://untrusted.website/@mr_daemon/115461772387285967)

### Inferences
- For a reproducible, CI-friendly demo-video pipeline driven by a coding agent, VHS is the better default over asciinema/agg: the `.tape` script itself is the source of truth (versionable, diffable, agent-editable), whereas asciinema captures a live session that then needs post-hoc GIF conversion and isn't naturally "generated" by an agent without simulating a live terminal.
- For mobile/X-feed legibility, bias toward larger font sizes than the README-oriented FontSize-20 floor — a documentation example used FontSize 40 with a 1.0 line-height and a high-contrast theme (Catppuccin Mocha), which is a reasonable starting point for video meant to be watched at small size on a phone.

### Gaps
- No first-party VHS documentation page was directly fetched (findings come through aggregator/summary search results) — recommend fetching `github.com/charmbracelet/vhs#readme` directly before finalizing exact `.tape` syntax for scripts, since command names/flags should be verified against the current README rather than secondary summaries.
- No quantified comparison (e.g., render time, file size) between VHS and asciinema+agg was found.

## ffmpeg recipes: trimming, compositing, captions, exports, GitHub/X specs

### Takeaway
Standard ffmpeg filter chains handle trimming, split-screen compositing, and caption burn-in; order of filters matters (crop/scale before subtitles). GitHub README video embeds are capped at 10MB (free plans) / 100MB (paid plans) via drag-and-drop, only render on GitHub.com itself (not npm pages, IDE previews, offline viewers), and GIF remains the more broadly compatible fallback. X allows up to 140 seconds / 512MB for standard (non-Premium) accounts, recommends 1920×1080 (16:9) or 1080×1920 (9:16), and recommends 5,000–25,000 kbps bitrate (≥8,000 kbps suggested for 1080p to limit quality loss), MP4/MOV with H.264+AAC, up to 60fps (30fps safer for file size).

### Cited Findings
- Burn-in subtitles: `ffmpeg -i video.mp4 -vf "subtitles=subs.srt" -c:v libx264 -crf 22 -c:a copy out_burn.mp4`; styling can be customized via `force_style` (font size, color, position). — [FFmpeg subtitles filter guide (third-party)](https://www.ffmpeg-micro.com/blog/ffmpeg-subtitles-filter-guide)
- For 9:16 exports with burned captions, filter order matters: crop first, then scale to 1080x1920, then apply subtitles last — subtitle text renders based on frame dimensions at that point in the filter chain, so subtitles should come after scale: `ffmpeg -i input_video.mp4 -vf "crop=...,scale=1080:1920,subtitles=subs.srt" -c:v libx264 -c:a copy output.mp4`. — [FFmpeg subtitles filter guide (third-party)](https://www.ffmpeg-micro.com/blog/ffmpeg-subtitles-filter-guide)
- Frame extraction for automated QA: `ffmpeg -i video.mp4 -r 1 frame%d.png` (1 fps); can combine with `scale=640:-1` to resize while preserving aspect ratio, or `fps=1/5` for one frame every 5 seconds; `-q:v` controls JPEG quality (2 = high quality, 31 = lowest). — [Baeldung ffmpeg frame extraction](https://www.baeldung.com/linux/ffmpeg-extract-video-frames), [Gumlet ffmpeg guide (third-party)](https://www.gumlet.com/learn/ffmpeg-extract-frames/)
- A purpose-built "video-frames-skill" (open-source, Claude Code / Cursor / Windsurf agent skill) extracts frames via ffmpeg specifically for LLM/vision analysis, with scene-change detection, model-aware resizing/quality presets, an OCR mode with high-contrast preprocessing for text extraction, and timestamp overlays — directly applicable to automated "does the on-screen text overflow / is it legible" QA passes driven by a coding agent. — [mugnimaestra/video-frames-skill on GitHub](https://github.com/mugnimaestra/video-frames-skill)
- GitHub README video support: drag-and-drop video upload into a README (or issue/PR comment) is capped at 10MB on free GitHub plans and 100MB on paid plans; there is no true embedded video player in README.md — GitHub renders the video only on GitHub.com itself, and it does **not** display on npm package pages, offline Markdown viewers, or many IDE Markdown previews. Practical workarounds cited: link a YouTube thumbnail image that click-throughs to the real video, or use an animated GIF, which remains "the safer choice in 2026" for cross-platform compatibility. — [GitHub community discussion #4818 (official GitHub discussion forum)](https://github.com/orgs/community/discussions/4818)
- X (Twitter) video specs, 2026: max length 140 seconds (2:20) for free/standard accounts, up to 4 hours for X Premium; recommended resolution 1920×1080 (landscape) / 1080×1920 (vertical), max resolution 1920×1200, min 32×32; recommended bitrate 5,000–25,000 kbps, with ≥8,000 kbps suggested at 1080p to minimize quality loss; max file size 512MB standard / 16GB Premium (as of June 2026); supported formats MP4/MOV, H.264 video + AAC audio; up to 60fps supported, 30fps recommended if file size is a concern. — [nemovideo.com X video specs guide 2026 (third-party, aggregating platform specs)](https://www.nemovideo.com/blog/twitter-video-specs-guide-2026)
- X caption support: X does not offer auto-generated captions, but supports uploading a plaintext `.srt` caption file per video (via the desktop web upload flow: "Upload caption file (.srt)" under the video, then "Upload captions" to confirm). Viewers can toggle captions on/off if their device accessibility settings enable it. Verified/subscriber accounts can also add captions via X's Media Studio. — [X Help Center: "How to upload caption (.srt) file to Posts"](https://help.x.com/en/using-x/upload-caption-srt-file)

### Inferences
- Because X supports real SRT files (not just burned-in captions), a demo-video pipeline should produce both a burned-in-caption MP4 (for muted-autoplay legibility guarantee, since many viewers won't toggle captions) and a separate `.srt` sidecar to upload alongside it for accessibility and for viewers who prefer platform captions.
- For GitHub README distribution, given the 10MB free-plan cap and cross-viewer compatibility gaps for MP4, a GIF (or a short MP4 capped well under 10MB plus a GIF fallback) is the safer default; larger/longer demo content should live on X/YouTube with the README linking out via a thumbnail image.
- An automated QA step (agent-driven) is straightforward to build on top of `ffmpeg -vf fps=... ` frame extraction feeding into either OCR (for on-screen text legibility/overflow checks) or a vision-capable model call per sampled frame — the `video-frames-skill` project is a ready-made pattern for this specific use case.

### Gaps
- Did not verify exact numeric recommendations (bitrate ranges, file-size caps) directly against X's own official help pages beyond the SRT-upload page — the specs above are sourced from a third-party aggregator (nemovideo.com) rather than X's official media specs page; an official-source pass (e.g., `help.x.com` media best-practices pages, if they exist) is recommended before hard-committing to exact bitrate/resolution numbers in a production pipeline.
- No official ffmpeg.org documentation was directly fetched for the subtitle/crop/scale filter chain — recipes above come from third-party ffmpeg tutorial sites; commands are standard/well-established ffmpeg usage but should be smoke-tested against the exact ffmpeg version in use.
- No specific automated "contrast checking" tool or established methodology (beyond OCR/vision-model frame inspection) was found; this appears to be a build-it-yourself space rather than a documented standard practice.

## What makes dev-tool demo videos perform (hook, captions, split-screen, examples)

### Takeaway
Evidence (mostly third-party marketing/creator sources, not peer-reviewed) converges on: a visual hook in the first 1–3 seconds that works without sound, near-universal use of burned-in captions since most social video is watched muted, and video generally outperforming static/text content for conversion. Specific dev-tool launch-video case studies exist but come from a single third-party blog and should be treated as anecdotal examples, not benchmarked data.

### Cited Findings
- Meta-cited stat: 65% of people who watch the first three seconds of a video keep watching for at least 10 more seconds — underscoring the importance of the opening hook. — [CapCut "Short-Form Video Hooks" (third-party, citing Meta)](https://www.capcut.com/create/short-form-video-hooks-first-3-second-patterns)
- Up to 85% of video views on social platforms happen without sound, which is why burned-in (hard-coded) captions are preferred over relying on platform auto-captions — burned-in captions give creators control over emphasis/timing that platform captions don't. — [clicks.video "Silent-First Editing" (third-party)](https://www.clicks.video/blog/silent-first-editing-captions-text-overlays-and-visual-hooks-for-sound-off-viewing)
- Recommended practical test: watch the first five seconds of a video twice — once with audio, once muted — and confirm both versions make sense/land the hook on their own. — [CapCut hooks guide (third-party)](https://www.capcut.com/create/short-form-video-hooks)
- For dev-tool demos specifically, one practitioner example describes an "unattended rolling demo" video that relies on captions explaining each beat so the muted video is self-explanatory without narration. — [GitHub PR #10, grahamcrooks/FraudPOC (practitioner example, not a study)](https://github.com/grahamcrooks/FraudPOC/pull/10)
- Split-screen video is cited as effective specifically for before/after transformations and for comparing two features/products side by side, particularly for product launches and tech demos. — [Think Branded Media "Creating Impactful Split Screen Videos" (third-party, marketing-agency content)](https://thinkbrandedmedia.com/blog/creating-impactful-split-screen-videos-strategies-for-better-click-through-rates/)
- Landing pages with video average a 4.8% conversion rate vs. 2.9% without video; product demo videos "tend to land near double the conversion rate" of a plain text description; a good average video completion rate runs 70–80%; interactive video elements show 3.6x higher completion rate than passive video. — [Videowise "7 Ways to Increase Your Video Conversion Rate" (third-party, video-tooling vendor content)](https://videowise.com/blog/video-conversion-rate)
- Named dev-tool launch-video examples (single third-party source, "Flowjam" blog — treat as opinion/case-study, not independently verified performance data): "Atrium's launch" is characterized as UI-driven content without a founder's face on camera, using a script written "in the founder's voice" as voiceover — cited as a template for teams that can't shoot a founder on camera. "Kite's launch video" is characterized as a clean "what is this thing" structure: one sentence → demo → second sentence. — [Flowjam "15 Product Launch Video Examples That Actually Worked (2026)" (third-party)](https://www.flowjam.com/blog/product-launch-video-examples-2026)

### Inferences
- The strongest, most consistently corroborated tactical rules across sources are: (1) make the first 1–3 seconds work with sound off (visual hook, bold on-screen claim, or immediate product reveal), (2) always burn in captions rather than relying on platform auto-captions, and (3) test the muted version independently rather than assuming the voiceover carries the message.
- Split-screen before/after is well-supported as a format for comparative/transformation demos (e.g., "before this tool" vs. "after this tool," or manual workflow vs. agent-automated workflow) but the evidence is marketing-agency sourced, not academically rigorous.
- The specific completion-rate and conversion-rate statistics (4.8% vs 2.9%, 70–80% completion, 3.6x interactive lift) all come from video-tooling vendors with a commercial interest in these numbers looking favorable — treat as directional, not precise, and do not present as peer-reviewed.

### Gaps
- Could not find primary-source, platform-published data (e.g., an X/Twitter engineering blog post, or a peer-reviewed study) on dev-tool video completion rates specifically — all completion-rate and conversion-rate figures found are from marketing/video-SaaS vendor blogs, which is a real limitation on confidence.

Treat these two examples as illustrative anecdotes only, not vetted evidence.

## Alternatives to Remotion (Motion Canvas, Revideo, Manim) — when to use each

### Takeaway
Remotion (React/CSS, frame-by-frame MP4 rendering) is the right choice when the video is built from real UI, text, and screenshots and/or needs to render automatically/at scale — which matches a dev-tool demo-video use case well. Motion Canvas (TypeScript generators, live editor) suits handcrafted shape/diagram explainer animation; Revideo (MIT-licensed, TypeScript, headless `renderVideo()` API) is the closest Motion-Canvas-style alternative when automated/unlicensed batch rendering matters; Manim (Python) suits math/geometry-heavy technical explainers in the 3Blue1Brown style.

### Cited Findings
- "Use Remotion if your video is made of UI, text and screenshots, or needs to render automatically — it is React and CSS, rendered frame by frame to an MP4," and it is characterized as "the most capable and production-ready option" for building a video product or generating videos at scale. — [snapcn.dev "Remotion vs Motion Canvas (and Revideo)" (third-party comparison)](https://snapcn.dev/remotion-vs-motion-canvas)
- Motion Canvas: scenes authored as TypeScript generators in a live editor; well-suited to "explainer-style animation of shapes and diagrams" and "handcrafted animations and educational content." Motion Canvas is MIT-licensed. — [snapcn.dev comparison (third-party)](https://snapcn.dev/remotion-vs-motion-canvas)
- Revideo: MIT-licensed, TypeScript, scenes rendered to a video file via a headless `renderVideo()` API; positioned as the choice for teams that like the Motion-Canvas authoring style but need automated/batch rendering "without a licensing overhead," since the self-hosted Node.js rendering API is free and unrestricted. — [snapcn.dev comparison (third-party)](https://snapcn.dev/remotion-vs-motion-canvas)
- Manim: Python animation engine popularized by 3Blue1Brown-style math explainers; renders deterministic MP4s from code; recommended when the video is technical/mathematical and Python is preferred over TypeScript. — [snapcn.dev comparison (third-party)](https://snapcn.dev/remotion-vs-motion-canvas)

### Inferences
- For a dev-tool demo video built largely from terminal recordings (VHS output), UI screenshots, and text overlays — as opposed to abstract diagram animation or math — Remotion remains the best-fit tool, consistent with its own "AI/coding agent" positioning and its React/CSS/screenshot-friendly rendering model.
- If licensing cost/friction becomes a concern at higher headcounts (4+ people) purely for automated rendering, Revideo is worth prototyping as a fallback since it explicitly targets the same "batch/automated video generation" niche without Remotion's Company License requirement — though it would require re-authoring compositions in Revideo's API rather than Remotion's.

### Gaps
- All alternatives comparison findings come from a single third-party aggregator (snapcn.dev); no first-party Motion Canvas, Revideo, or Manim documentation was directly fetched to corroborate feature/licensing claims. The MIT-license claims for Motion Canvas and Revideo are plausible and commonly repeated but should be verified against each project's own LICENSE file before being relied on for a compliance decision.
- Did not find a rendering-speed or output-quality benchmark comparing Remotion, Motion Canvas, and Revideo for UI/screenshot-heavy content specifically.

## Automated QA of rendered video (frame extraction, overflow/contrast/timing, caption accessibility)

### Takeaway
There is no single documented standard tool for automated dev-tool-demo-video QA; the practical, buildable pattern is ffmpeg-based frame sampling (`fps` filter) feeding into either OCR or a vision-capable model for text/overflow/contrast checks, with a purpose-built open-source "video-frames-skill" agent skill already implementing this pattern for Claude Code-style agents. Caption accessibility on X is served by SRT sidecar upload (see ffmpeg/X section above) plus burned-in captions for muted viewing.

### Cited Findings
- `mugnimaestra/video-frames-skill` is an open-source Claude Code / Cursor / Windsurf agent skill that extracts frames via ffmpeg specifically for LLM/vision analysis, with scene-change detection, model-aware resizing and quality presets, an OCR mode with high-contrast preprocessing for text extraction, and automatic token-cost estimation for feeding frames to a vision model. — [mugnimaestra/video-frames-skill GitHub](https://github.com/mugnimaestra/video-frames-skill)
- Basic ffmpeg sampling for QA: `ffmpeg -i video.mp4 -r 1 frame%d.png` (1 fps) or `fps=1/5` (1 frame per 5 seconds), optionally with `scale=640:-1` to normalize frame size before analysis, and `-q:v 2` for high-quality still extraction. — [Baeldung ffmpeg frame extraction guide](https://www.baeldung.com/linux/ffmpeg-extract-video-frames)

### Inferences
- A practical automated-QA loop for an agent-produced demo video: render → sample frames at ~1 fps with ffmpeg → run each frame through a vision-capable model (or OCR mode) checking for (a) caption/text legibility and overflow against frame bounds, (b) contrast of burned-in text against background, (c) that captions are synced within an acceptable timing window vs. the SRT/caption JSON timestamps already produced by `@remotion/captions`. Since Remotion is React-based, timing/overflow checks could alternatively be done at the composition level (checking DOM/text-measurement against frame bounds before render) rather than post-hoc on rendered frames — this wasn't directly documented in sources found, but follows naturally from Remotion's React rendering model.

### Gaps
- No documented, established open-source tool specifically for "automated contrast checking" or "caption timing QA" of rendered video was found; this is a build-it-yourself area. Recommend prototyping the frame-sampling + vision-model-check loop described above rather than searching further for an off-the-shelf tool, given the search budget for this research pass.
