# Placement algorithms for hierarchical Goal/Procedure sharding

**Scope and terms.** This note models a Procedure as one logical object with a stable `procedure_id`, one authoritative home shard, optional replicas, and zero or more links to abstract Goals. A Goal remains canonical in the control/Goal database. A placement algorithm chooses the authoritative home; it does not by itself provide replication, cross-shard transactions, or semantic validation. Those are separate concerns.

**Source discipline.** Statements under **Cited Findings** are paraphrases of papers or vendor documentation with inline links. Statements under **Inferences** are design judgments for this use case; their supporting mechanisms are cited where relevant. “Home shard” means the primary writer/owner, not every replica.

## 1. How each strategy chooses a home shard

### Takeaway

The strategies divide into three broad families:

1. **Deterministic key-to-owner functions** — rendezvous/HRW, consistent-hash rings, and weighted variants. A router can compute a home from a key and a membership view without asking a directory for every object.
2. **Policy-driven mappings** — directory tables and range/prefix maps. They make placement explicit and can express Goal affinity, but introduce mapping state and migration coordination.
3. **Optimization and hierarchy layers** — graph partitioning, locality-aware assignment, root/tier partitioning, and hierarchical routing. These are best treated as assignment, routing, or rebalancing layers around a stable key-to-owner mechanism rather than as unqualified replacements for it.

The central design distinction is whether co-location with a Goal is a **hard placement key**, a **weighted preference**, or merely a **secondary index**. A single authoritative Procedure cannot be physically adjacent to every Goal to which it applies without either accepting a compromise, duplicating data, or maintaining additional indexes.

### Cited Findings

#### Rendezvous hashing / highest random weight (HRW)

- The original HRW mapping computes a name-based score for an object/server pair and selects the server with the highest score. The same object name and server set therefore produce the same mapping independently at clients, without a centralized lookup for each object. The paper specifically presents HRW as adapting when servers are added or removed. [Thaler and Ravishankar, “Using Name-Based Mappings to Increase Hit Rates”](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/02/HRW98.pdf)
- The original HRW model assumes that clients can use a common view of the server set and that the load associated with one object can be handled by one server. Those assumptions are important when a “key” is a very hot Goal rather than an independently balanced Procedure. [Thaler and Ravishankar, HRW paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/02/HRW98.pdf)
- A current IETF draft describes HRW as computing `Hash(object, server)`, ordering servers by that score, using the next score as a backup, and discussing weighted HRW. The draft is an engineering proposal, not a normative standard; it also warns that normalizing weights by the total can change scores for every server when one weight changes. [IETF weighted-HRW draft](https://datatracker.ietf.org/doc/html/draft-ietf-bess-weighted-hrw-00)

#### Consistent hashing and rings

- Karger et al. define consistent hashing as a function that changes minimally as its range or node set changes, and emphasize local control and the ability to operate without every client having a current, globally consistent view of the network. [Karger et al., “Consistent Hashing and Random Trees”](https://people.csail.mit.edu/karger/Papers/web.pdf)
- In a conventional ring, keys and nodes are mapped into a circular identifier space and a key is assigned to the next node in the ring. The Dynamo paper describes the same basic partition and preference-list model and adds virtual nodes so a physical node can occupy multiple ring positions. [DeCandia et al., “Dynamo: Amazon’s Highly Available Key-Value Store”](https://courses.cs.washington.edu/courses/cse452/22wi/papers/decandia-et-al-dynamo.pdf)
- Apache Cassandra documents the operational consequences: vnodes make incremental scale-out more even, while every additional token increases metadata and repair combinations. Its documentation also distinguishes partition ownership from replication: a key’s replicas are selected as distinct physical nodes, and a token-aware coordinator routes to the token range. [Cassandra Dynamo architecture](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html)
- Envoy’s ring-hash documentation describes hosts being placed on the ring multiple times in proportion to weight; with a suitably partitioned ring, adding or removing one host affects approximately `1/N` of requests. The documentation treats this as a property of a well-sized and well-distributed ring, not an unconditional guarantee. [Envoy supported load balancers](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers)

#### Weighted hashing

- A weighted ring represents a host with multiple virtual points proportional to its configured weight. More points improve the approximation of the requested ratio, but ring-size and point-distribution choices matter. [Envoy ring-hash documentation](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers)
- Weighted HRW can instead alter the score for each candidate. The IETF draft notes that the obvious normalized-weight formula can cause unnecessary movement when one server’s weight changes, and presents an alternative score intended to preserve the minimal-disruption property. This is evidence of a design tradeoff, not proof that every weighted-HRW implementation behaves identically. [IETF weighted-HRW draft](https://datatracker.ietf.org/doc/html/draft-ietf-bess-weighted-hrw-00)
- Envoy’s Maglev documentation gives a useful implementation comparison: a fixed lookup table can make selection fast and weighted, but its disruption characteristics differ from a ring; the documentation observes that Maglev can move more keys when hosts are removed even when it aims for minimal disruption. [Envoy supported load balancers](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers)

#### Directory tables and explicit lookup tables

- Oracle’s directory-based sharding documentation defines a directory table that maps sharding-key values to partitions and supports APIs/rules for adding keys and assigning subsequent keys to partitions. The directory table is automatically created with the root table, and child-table constraints require the directory key to be present. [Oracle “Creating Tables Sharded by Directory”](https://docs.oracle.com/en/database/oracle/oracle-database/26/shard/creating-tables-sharded-directory.html)
- The Farsite directory paper shows that a logically centralized directory need not be physically centralized: it distributes directory metadata, partitions it by tree-structured identifiers, dynamically moves metadata between machines, and uses leases to preserve namespace consistency. Its BFT-replicated single-group design also illustrates that replication alone does not remove the throughput ceiling of a single coordination group. [Douceur and Howell, “Distributed Directory Service in the Farsite File System”](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/douceur/douceur.pdf)
- The “Lookup Tables” database paper describes a mapping from a key to a set of partition IDs, with router-side lookup tables used to route queries. It also describes location dependencies that place related tuples together, and notes that lookup tables can be cached by routers. [Tatarowicz et al., “Lookup Tables: Fine-Grained Partitioning for Distributed Databases”](https://dspace.mit.edu/bitstream/handle/1721.1/137764/lookup_tables.pdf;jsessionid=1D1DE705877B4A0F7C9613CF81723FBA?sequence=2)
- A study of object placement (“Smash”) identifies the memory and availability cost of a central ID-to-location directory and separates lookup structures from maintenance structures. This supports treating directory size, write hotspots, and directory availability as first-class design issues rather than assuming a directory is free. [Liu et al., “Smash: Flexible, Fast, and Resource-efficient Placement and Lookup of Distributed Storage”](https://doi.org/10.1145/3589977)

#### Range and prefix partitioning

- PostgreSQL range partitioning uses non-overlapping ranges, with lower bounds inclusive and upper bounds exclusive; rows are routed to the partition whose bounds contain the partition key. PostgreSQL also supports subpartitioning, while warning that excessive partition counts can increase planning overhead. [PostgreSQL table partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)
- MongoDB documents that range sharding groups nearby shard-key values into chunks/shards, which helps range-targeted reads but can hurt read/write performance when the key choice is poor. Its balancer migrates ranges and manages chunk distribution. [MongoDB ranged sharding](https://www.mongodb.com/docs/manual/core/ranged-sharding/)
- RavenDB’s prefix sharding is a concrete implementation of explicit prefix routing: the most-specific matching prefix wins, a prefix can map to one or multiple shards, and unmatched documents fall back to the normal hash-based distribution. Its documentation also notes that adding a shard to an existing prefix does not automatically reallocate all of the prefix’s buckets. [RavenDB “Sharding by prefix”](https://docs.ravendb.net/7.2/sharding/administration/sharding-by-prefix)
- Google Spanner dynamically splits and merges key ranges in response to size and traffic and redistributes splits across resources. Its pre-splitting guidance recommends split points for anticipated load and explains that split/rebalance operations are not instantaneous. [Google Cloud Spanner pre-splitting overview](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview)

#### Graph partitioning

- Golab et al. reduce distributed data placement to graph partitioning: graph partitioning is NP-hard, but METIS-style approximations can produce nearly optimal placements quickly; their formulation explicitly extends to load balancing and replication. [Golab et al., “Distributed Data Placement via Graph Partitioning”](https://ar5iv.labs.arxiv.org/html/1312.0285)
- Schism represents database tuples as graph nodes and co-accessed tuples as weighted edges, then uses a balanced graph partition to reduce cross-partition transactions. It also produces a fine-grained mapping that requires lookup metadata and compares the result with range and hash alternatives. [“Schism: A Workload-Driven Approach to Database Replication and Partitioning”](https://15799.courses.cs.cmu.edu/fall2013/static/papers/schism-vldb2010.pdf)
- A dynamic graph-partitioning paper notes that static partitioners such as METIS generally require a global graph and that repeated recomputation can be expensive as a graph changes; dynamic schemes trade quality and batching against responsiveness. [Huang et al., “Lightweight Edge-Oriented Partitioning and Replication for Large-Scale Dynamic Graphs”](http://www.vldb.org/pvldb/vol9/p540-huang.pdf)

#### Locality-aware assignment

- Bigtable exposes tablets as dynamically managed row ranges and explicitly notes that clients can improve locality through key design; related keys placed contiguously can reduce the number of machines contacted. [Chang et al., “Bigtable: A Distributed Storage System for Structured Data”](https://static.usenix.org/event/osdi06/tech/chang/chang.pdf)
- Akkio is a locality-management service that decides where and when to migrate data. Its µ-shard abstraction is application-defined, contains related data, and is assigned to a unique shard; the paper distinguishes this from opaque key-range or hash partitioning. [Annamalai et al., “Sharding the Shards: Managing Datastore Locality at Scale with Akkio”](https://www.usenix.org/system/files/osdi18-annamalai.pdf)
- MongoDB zones associate shard-key ranges with one or more shards and use the balancer to migrate chunks only into eligible shards. The documentation lists geographic proximity and hardware capability as use cases, while making the shard-key prefix a constraint. [MongoDB zone sharding](https://www.mongodb.com/docs/v8.0/core/zone-sharding/)
- Spanner’s schema guidance says splits hold contiguous primary-key ranges and that it prefers boundaries near parent rows to preserve row-tree locality; it separately warns that operations spanning splits are more expensive. [Google Cloud Spanner schema optimization](https://docs.cloud.google.com/spanner/docs/whitepapers/optimizing-schema-design)

#### Tiered, root-partitioned, and hierarchical mechanisms

- “Tiered” and “root-partitioned placement” are not one canonical algorithm. They combine at least two independent choices: a storage/compute tier (hot versus cold) and a hierarchy of ownership groups. A procedure’s canonical home should remain explicit if a copy is promoted, demoted, cached, or replicated.
- Hierarchical DHT work describes a two-level lookup: a top-level overlay first finds the responsible group, then an intra-group overlay finds the responsible peer. The design reports local join/leave and key-migration effects, fault isolation, physical-network adaptation, and hierarchical storage/access-control benefits. [“Hierarchical Peer-to-peer Systems”](https://www.eurecom.fr/en/publication/1186/download/ce-felbpa-030826.pdf)
- Farsite uses recursive path leases so a root server deals with immediate child servers rather than every interested server; this is a routing/consistency mechanism layered over distributed directory metadata, not a replacement for deciding which leaf owns an object. [Farsite directory paper](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/douceur/douceur.pdf)
- HBase illustrates the control-plane/data-plane boundary: RegionServers hold data and `hbase:meta` records region locations, while the Master controls assignment, balancing, failover, and splits. HBase documents steady-state client operation without the Master in older versions, but newer client registries can put the Master in the critical path for location changes. [HBase Master architecture](https://hbase.apache.org/docs/architecture/master/) and [HBase catalog tables](https://hbase.apache.org/docs/architecture/catalog-tables/)
- Megastore uses independently replicated entity groups and lets applications choose locality/placement while keeping transactions within an entity group. That is evidence for hierarchical or locality-aware placement, but it is not evidence that every Procedure should be tied to one abstract Goal’s physical location. [MegaSTORE paper](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/36971.pdf)

### Inferences

#### A useful common model

Let `P` be a new Procedure, `G` a linked Goal, `S` the live physical shards, `w(s)` a capacity or policy weight, and `B` a fixed set of logical buckets. A base placement function can be written as `home(P) = owner(bucket(P))`.

- **Design judgment:** Use `procedure_id` as the default base key. It gives every independently created Procedure a stable, evenly distributed identity and avoids making a popular abstract Goal the physical hot spot.
- **Design judgment:** Keep `goal_id` in the Procedure’s relational metadata and, optionally, in a bounded affinity key or candidate constraint. A Goal is a semantic parent, not automatically a physical shard.
- **Design judgment:** Treat the following as separate records: canonical Procedure row; `procedure_goals` relation; secondary Goal-to-Procedure index; replica set; and placement epoch. This separation lets placement remain stable when a Procedure applies to multiple Goals.
- **Design judgment:** Make `home` and replication orthogonal. A deterministic hash can identify an owner, but it cannot recreate data lost with a single home shard. Dynamo and Cassandra both separate partition ownership from a preference list of distinct replicas. [Dynamo paper](https://courses.cs.washington.edu/courses/cse452/22wi/papers/decandia-et-al-dynamo.pdf) [Cassandra architecture](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html)

#### Strategy-specific home decisions

- **Rendezvous/HRW — `argmax` scoring.** Compute a score for every eligible physical shard from `(procedure_id, shard_id)` and choose the highest; use the next scores as ordered backups. Capacity can be incorporated as a stable shard weight, but the semantic Goal should not replace `procedure_id` by default. The design is attractive when the router can calculate locally and the shard membership view is replicated. [HRW paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/02/HRW98.pdf)
- **Consistent hash ring — successor lookup.** Hash `procedure_id`, walk to the next live token owner, and select additional distinct physical nodes for replicas. A ring with vnodes gives finer ownership granularity than one token per physical shard and is a natural fit when a mature membership/failure-detection layer already exists. [Karger et al.](https://people.csail.mit.edu/karger/Papers/web.pdf) [Cassandra architecture](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html)
- **Weighted hash — weighted owner.** Either place more virtual points on higher-capacity shards or use weighted HRW. Keep the weight tied to durable capacity/operational policy; use a separate affinity score for Goal locality so changing a capacity weight does not unexpectedly change semantic ownership. [Envoy ring-hash documentation](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers)
- **Directory — explicit mapping.** Allocate a new `procedure_id -> partition/shard` entry, then write the Procedure to the assigned shard. A directory can enforce a Goal-family policy, tenant boundary, or capacity reservation that a pure hash cannot express. [Oracle directory sharding](https://docs.oracle.com/en/database/oracle/oracle-database/26/shard/creating-tables-sharded-directory.html)
- **Range/prefix — ordered key lookup.** Compute a `placement_key`, find the matching range or longest matching prefix, and route to its owner. A `goal_family/` prefix is a reasonable coarse affinity mechanism; a raw `goal_id/` prefix maximizes Goal co-location but can create hot ranges. [RavenDB prefix sharding](https://docs.ravendb.net/7.2/sharding/administration/sharding-by-prefix) [PostgreSQL range partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)
- **Graph partition — learned partition label.** Build a graph whose nodes are Procedures and whose edges represent co-access, Goal affinity, or dependency costs; partition it into balanced groups and assign each new Procedure the label of its group. For a live system, use a periodic model plus a small online greedy/least-load rule, or store the label in a lookup table. [Golab et al.](https://ar5iv.labs.arxiv.org/html/1312.0285) [Schism paper](https://15799.courses.cs.cmu.edu/fall2013/static/papers/schism-vldb2010.pdf)
- **Locality-aware assignment — constrained cost minimization.** First discard shards that violate hard constraints (tenant, failure domain, capability, or legal boundary), then choose the shard minimizing a score such as `estimated_load + network_cost + goal_affinity_cost`. This is a policy layer that can wrap HRW, a ring, or a directory. [MongoDB zone sharding](https://www.mongodb.com/docs/v8.0/core/zone-sharding/) [Akkio paper](https://www.usenix.org/system/files/osdi18-annamalai.pdf)
- **Root-partitioned placement — two-stage keying.** First map a bounded `goal_family` or placement class to a root partition, then map `procedure_id` (or a subkey) to a leaf shard within that partition. This preserves coarse semantic locality while allowing a large Goal family to spread across leaves. Hierarchical DHT work supplies the routing precedent; the exact two-stage formula is a design choice. [Hierarchical DHT paper](https://www.eurecom.fr/en/publication/1186/download/ce-felbpa-030826.pdf)
- **Hierarchical routing — two-level directory.** Resolve a Goal family or namespace to a group, then resolve the Procedure to a physical shard using a local directory, ring, or HRW. The top level is a routing index; it need not own the Procedure row. Farsite’s recursive leases and HBase’s region metadata show why root/control metadata needs explicit consistency and failover treatment. [Farsite paper](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/douceur/douceur.pdf) [HBase catalog tables](https://hbase.apache.org/docs/architecture/catalog-tables/)

## 2. Lifecycle, Goal relationships, rebalancing, growth, and control-database failure

### Takeaway

The hard semantic issue is not hashing a key; it is representing a Procedure that has one home but several Goal relationships. The cleanest model is a canonical Procedure plus a separate many-to-many Goal index. Pure hash/ring strategies maximize data-plane independence; directories and range maps maximize explicitness; graph/locality strategies optimize relationships but need a control plane; hierarchy is useful only when there is a real group/region/tenant dimension.

For growth from one to 100 physical shards, a stable logical-bucket layer is the most robust common abstraction: the Procedure’s bucket does not change when physical ownership changes. For a control-database outage, existing Procedure reads can continue only if every router/shard has a valid cached placement view and the required Goal/applicability data; new placement, Goal changes, and rebalancing should normally pause or queue rather than invent a home.

### Cited Findings

- Range, prefix, and directory systems all expose a mapping state that must be updated when ranges, prefixes, partitions, or shard assignments change. PostgreSQL routes by partition bounds; RavenDB documents explicit reallocation when a prefix’s shard set changes; MongoDB’s balancer migrates chunks and respects zones. [PostgreSQL](https://www.postgresql.org/docs/current/ddl-partitioning.html) [RavenDB](https://docs.ravendb.net/7.2/sharding/administration/sharding-by-prefix) [MongoDB zones](https://www.mongodb.com/docs/v8.0/core/zone-sharding/)
- Vnode/token systems reduce the amount of data moved when a node joins or leaves, but they add token metadata and repair work; the reduction is a property of the ownership structure, not a guarantee that every Procedure remains in place. [Cassandra vnode documentation](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html) [Envoy ring-hash documentation](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers)
- Spanner documents dynamic split/merge/rebalance behavior and warns that split/rebalance work can temporarily fall behind traffic, increasing latency or causing queued requests. This is direct evidence that even a managed range strategy needs backpressure and migration state. [Spanner pre-splitting overview](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview)
- Farsite and HBase show two different answers to central metadata failure: distribute directory metadata with leases and failover protocols, or keep data/metadata in the data plane while a Master performs assignments and repairs. HBase’s current documentation explicitly notes that newer client location handling can put the Master in the critical path. [Farsite paper](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/douceur/douceur.pdf) [HBase Master](https://hbase.apache.org/docs/architecture/master/) [HBase catalog](https://hbase.apache.org/docs/architecture/catalog-tables/)
- AWS’s reliability guidance separates control-plane administration from data-plane service and recommends that existing data-plane operation continue from previously distributed state during a control-plane impairment. It also recommends caching critical control-plane data in data-plane-accessible stores. [AWS REL11-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_withstand_component_failures_avoid_control_plane.html)
- The Lookup Tables paper shows that a key can map to a set of partition IDs and that location dependencies can deliberately co-locate related tuples. This is a useful precedent for explicit secondary indexes, but it also demonstrates that flexible placement requires routing metadata. [Lookup Tables paper](https://dspace.mit.edu/bitstream/handle/1721.1/137764/lookup_tables.pdf;jsessionid=1D1DE705877B4A0F7C9613CF81723FBA?sequence=2)
- Database routers commonly distinguish a single-shard route from multi-shard or broadcast routes when the predicate cannot identify one partition. This is directly relevant to a Procedure applicable to multiple Goals: a query over all applicable Goals may need a set of shards, even if the Procedure row has one home. [Apache ShardingSphere routing documentation](https://shardingsphere.apache.org/document/current/en/reference/sharding/route/)

### Inferences

The following matrix is **design judgment** for the stated architecture. It uses the source-grounded mechanisms above but does not claim that the literature prescribes one winner for this semantic workload.

| Strategy | New Procedure and one specific Goal | Multiple applicable Goals | Rebalancing | Growth from 1 to 100 shards | Abstract/control DB failure |
|---|---|---|---|---|---|
| **Rendezvous / HRW** | Compute `argmax_s HRW(procedure_id, s)`; optionally restrict candidates to an affinity class. If strict co-location is required, hash `goal_id` instead, but expect a hot-Goal risk. | Choose a primary Goal or a bounded affinity class for the home. Keep additional Goal links in a relation/index; do not let the union of Goals silently redefine the home. | Membership changes affect only keys whose selected owner changes; use capacity-aware candidates or migration throttling. | Direct HRW membership changes cause movement at every growth step. Pre-create stable buckets and assign bucket ownership, or accept cumulative movement. | A replicated/cached shard view permits local routing for existing Procedures. Stale membership can send traffic to a dead shard; fresh Goal-dependent writes/validation should pause or use an explicit snapshot policy. |
| **Consistent hash ring** | Hash `procedure_id` and choose the clockwise successor; hash `goal_id` only when Goal co-location is a hard requirement. | One home plus per-Goal secondary indexes, or an explicit primary Goal. A multi-Goal query can fan out to indexed shards. | Vnodes make add/remove movement smaller than naïve modulo hashing; changing ring membership still requires streaming moved ranges/keys. | Start with many logical vnodes owned by one physical shard, then transfer vnode ranges as physical shards join. | Cached token maps/gossip can keep data-plane reads working; a control outage prevents new ring changes but need not block existing reads. Goal semantics still need a cached Goal snapshot. |
| **Weighted hash** | Use shard capacity/availability as weights, then apply a separate Goal-affinity constraint or penalty. | Combine affinity terms, select a primary Goal, or maintain secondary indexes. A weight is not a substitute for a relationship model. | Stable virtual points or carefully chosen weighted scores reduce unnecessary movement; naïve normalized weights can perturb many assignments. | Pre-provision virtual points/buckets and add physical shards by transferring a capacity-weighted subset. | Same outage behavior as the underlying hash/ring, but routers need a versioned weight/membership snapshot. |
| **Directory table** | Allocate and persist an explicit `procedure_id -> shard` mapping; a Goal-family directory can choose an affinity shard. | Store a many-to-many `procedure_goals` table and one canonical home, or explicitly replicate the Procedure if multiple homes are accepted. | Change mappings and move rows in a controlled migration; supports quotas and placement constraints better than pure hashing, but requires handoff/versioning. | Add directory entries and bulk-reassign selected keys/ranges; 1-to-100 growth usually entails a planned migration, not just a ring update. | New allocation, rebalancing, and Goal updates depend on the directory. | **Range / prefix** | Route by a non-overlapping range or longest prefix. `goal_family/` gives coarse co-location; raw `goal_id/` gives stronger but hotter co-location. | Use a primary Goal in the placement key and secondary Goal indexes. A Procedure cannot be in several disjoint ranges at once. | Split hot ranges, merge cold ranges, and migrate chunks; boundaries and range maps need versions and backpressure. | Create many logical ranges up front, initially owned by one physical shard, then split/move ranges as capacity arrives. This is a natural fit for the 1-to-100 path. | Cached range maps permit existing reads. New keys needing an unknown/new range, boundary changes, and Goal-policy changes are unavailable while the control DB is down. |
| **Graph partitioning** | Use a precomputed partition label, or place a new Procedure in the partition containing the most related Procedures; retain a deterministic fallback/directory. | Model multiple Goal edges and choose a balanced compromise, or duplicate relationship data. A single home cannot minimize every edge cut. | Recompute periodically or use bounded online reassignment; graph quality can require substantial movement and global graph knowledge. | Recompute a `k=100` partition as capacity grows, or add partitions and migrate bounded groups. This is a batch-heavy path. | Cached partition labels keep existing reads routable. New graph edges, retraining, and rebalancing wait for the control plane; a hash/least-load fallback is safer than pretending the stale graph is current. |
| **Locality-aware assignment** | Apply hard eligibility filters first, then minimize a cost over live shards using locality, load, capability, and Goal-family affinity. | Score all applicable affinities, choose a dominant Goal, or keep separate indexes; multi-Goal locality is a constrained optimization, not a free hash property. | Move on load/hotspot thresholds, preferably using bounded candidate choices and hysteresis. It can optimize latency but may cause churn if scores oscillate. | Give a new shard a bounded quota of each locality class; otherwise a strong affinity policy can keep all Procedures on the original shard. | Cached topology/scores support reads and conservative writes. Dynamic migration and fresh Goal affinity should pause or use a static fallback during control failure. |
| **Tiered / root-partitioned** | Map `goal_family` to a root, then map `procedure_id` to a leaf; use hot/cold tier as a storage/read optimization while retaining a canonical home. | Choose a primary root, then maintain secondary Goal indexes; split an overfull root rather than allowing one Goal family to dominate. | Split/rebalance roots first, leaves second, and promote/demote copies independently. A root table can become a new hotspot if not bounded. | A two-level tree (for example, ten roots by ten leaves) makes 1-to-100 growth conceptually regular, but root reassignment still needs migration. | Leaf-local deterministic routing can continue with a cached root/leaf map; fresh root assignment and hierarchy changes depend on the control plane. |
| **Hierarchical routing** | Resolve top-level `goal_family/namespace -> group`, then leaf `procedure_id -> physical shard`. The top directory is a route, not the Procedure’s data home. | Route a single-Goal relation to the leaf; multi-Goal lookup uses multiple secondary indexes or a deliberate fan-out. | Leaf changes are local; adding/removing a group can be localized, but stale top-level routes can strand a group. | Add groups before or alongside leaves and transfer only affected subtrees; this is most useful when physical geography/administration is a real dimension. | Cached top-level maps and leaf directories can preserve existing routes, but an unreplicated root directory is a routing SPOF. Farsite-style distributed directory/leases or a replicated catalog is needed for safe failover. |

#### Cross-cutting design rules

- **One home, many relationships.** **Design judgment:** Make `procedure_id -> home_shard` authoritative and model `procedure_id <-> goal_id` separately. The Lookup Tables precedent supports explicit key-to-partition-set mappings, while a router can use those mappings for a multi-shard query. [Lookup Tables paper](https://dspace.mit.edu/bitstream/handle/1721.1/137764/lookup_tables.pdf;jsessionid=1D1DE705877B4A0F7C9613CF81723FBA?sequence=2) [ShardingSphere routing](https://shardingsphere.apache.org/document/current/en/reference/sharding/route/)
- **Stable bucket identity.** **Design judgment:** Give each Procedure a stable logical bucket independent of physical shard count. Rebalance bucket ownership, not the Procedure’s semantic identity. Vnodes/tokens and dynamic split points are both precedents for making physical movement a separate operation. [Cassandra vnode documentation](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html) [Spanner pre-splitting](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview)
- **Control plane is not the data plane.** **Design judgment:** A control outage has at least three distinct effects: (a) existing Procedure reads may continue from a cached route; (b) writes requiring fresh Goal/applicability validation may need to queue or fail closed; and (c) migrations, Goal edits, and topology changes should pause. AWS explicitly recommends data-plane continuation and caching control-plane data for recovery. [AWS REL11-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_withstand_component_failures_avoid_control_plane.html)
- **Migration must be versioned.** **Design judgment:** Publish an ownership epoch, stream a bucket/range before changing the authoritative map, retain forwarding records during handoff, and only then retire the old owner. Spanner’s documented split/rebalance lag and Farsite’s leases both show that “the map changed” and “all data moved” are not instantaneous. [Spanner](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview) [Farsite](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/douceur/douceur.pdf)
- **Do not mistake ownership for durability.** **Design judgment:** If a Procedure must survive a physical shard failure, choose replicas from the same weighted/ring candidate set while keeping one canonical writer. The original Dynamo and Cassandra designs both make replication/preference lists distinct from the partition owner. [Dynamo paper](https://courses.cs.washington.edu/courses/cse452/22wi/papers/decandia-et-al-dynamo.pdf) [Cassandra architecture](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html)
- **Use hard constraints before soft affinities.** **Design judgment:** If tenant isolation, legal residency, capability, or failure-domain rules exist, filter them out before load/locality scoring. Otherwise a weighted score can trade a hard requirement for a small efficiency gain. MongoDB zones provide a concrete constrained-shard example. [MongoDB zone sharding](https://www.mongodb.com/docs/v8.0/core/zone-sharding/)

### Gaps

- The sources do not establish an optimal placement policy for this exact semantic workload; the right objective depends on Procedure size, read/write ratio, Goal fan-out, hot-Goal distribution, query patterns, and cross-shard transaction frequency.
- It is not specified whether a Procedure can be duplicated for multiple Goals, whether Goal links are immutable, or whether a single Procedure may change its primary Goal over time.
- The acceptable behavior during a Goal-database outage is unspecified: stale reads, queued writes, fail-closed validation, and emergency writes have different correctness consequences.
- “Physical database shard” may mean independent PostgreSQL instances, independent replicas, or cells with different consistency/latency characteristics. The placement recommendation assumes independent primary homes plus separately selected replicas.
- The target rebalancing objective is unspecified: minimum moved bytes, minimum moved Procedure count, bounded cross-shard traffic, or a weighted combination.
- No source gives a direct benchmark for a central abstract-Goal database plus 100 semantic Procedure shards; the cited systems establish mechanisms and tradeoffs, not an end-to-end answer for this schema.
- Graph partitioning and locality-aware assignment require workload traces or a declared affinity heuristic; without those, their “optimal” partitions are speculative.
- A 1-to-100 growth test needs a stated data volume, shard capacity, and acceptable migration window before movement or latency tradeoffs can be quantified.

## 3. Candidate algorithms and recommendation

### Takeaway

**Recommended default: bucketized weighted rendezvous hashing with a replicated, versioned placement catalog.** Keep the canonical Procedure row on one shard, use `procedure_id` (optionally a bounded Goal-family class) to select a stable logical bucket, and use weighted HRW or a ring only to map buckets to physical shards. Add a separate `procedure_goals` relation/index and select replicas independently.

Use a **weighted consistent-hash ring** when a mature ring/membership layer and vnode operations are already available. Use a **directory/lookup table** when explicit Goal-family placement, auditability, and policy overrides matter more than data-plane independence. Use **range/prefix** when Goal-family range locality is a dominant query requirement. Use **graph/locality optimization** as a periodic co-planner around the stable base mapping, not as the only online home algorithm. Use **hierarchical routing/root partitioning** when there are genuine groups, regions, or administrative cells; 100 shards alone do not require that complexity.

### Cited Findings

- HRW supplies a deterministic, locally computable object-to-server mapping and can adapt to server-set changes without a central per-object directory. [HRW paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/02/HRW98.pdf)
- Consistent hashing and vnodes reduce movement relative to naïve modulo hashing, while adding ownership metadata and repair complexity. [Karger et al.](https://people.csail.mit.edu/karger/Papers/web.pdf) [Cassandra architecture](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html)
- Explicit directories and lookup tables can express arbitrary fine-grained placement and related-data co-location, but require routing metadata and coordinated updates. [Oracle directory sharding](https://docs.oracle.com/en/database/oracle/oracle-database/26/shard/creating-tables-sharded-directory.html) [Lookup Tables paper](https://dspace.mit.edu/bitstream/handle/1721.1/137764/lookup_tables.pdf;jsessionid=1D1DE705877B4A0F7C9613CF81723FBA?sequence=2)
- Graph partitioning can reduce communication under a known workload, but the objective is NP-hard and practical systems use approximations or periodic recomputation. [Golab et al.](https://ar5iv.labs.arxiv.org/html/1312.0285) [Schism paper](https://15799.courses.cs.cmu.edu/fall2013/static/papers/schism-vldb2010.pdf)
- Spanner demonstrates a range/split approach in which splits are dynamically split/merged and redistributed; MongoDB zones demonstrate constrained locality/placement. Their mechanisms are useful precedents but are not proof that raw semantic Goal IDs are good shard keys. [Spanner](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview) [MongoDB zones](https://www.mongodb.com/docs/v8.0/core/zone-sharding/)
- AWS’s control-plane guidance supports caching and retaining data-plane operation when the control plane is impaired; HBase shows why a central placement/master service can become a critical path when clients need fresh region locations. [AWS](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_withstand_component_failures_avoid_control_plane.html) [HBase Master](https://hbase.apache.org/docs/architecture/master/)

### Inferences

#### Recommended placement model

**Design judgment — use this as the default candidate:**

1. Create a stable logical bucket set `B` larger than 100 if practical (for example, 100, 1,024, or several thousand logical buckets), so physical rebalancing has finer granularity than “one Procedure per shard.” The exact `|B|` should be chosen from expected data volume and migration cost, not fixed by the fact that there are 100 physical shards.
2. Compute `bucket = H(procedure_id)` (or a stable, explicitly versioned `H(placement_key)`). A default placement key should not be a model embedding or mutable semantic score; it should be stable across re-extraction and version changes.
3. Compute a physical owner with weighted HRW over `(bucket, shard_id, shard_weight)`, or use a ring successor. Publish a compact, versioned `bucket -> physical shard` catalog to routers and shard agents.
4. Store the canonical Procedure on that owner. Select distinct replica homes from subsequent HRW scores or ring successors; do not infer replication merely from the existence of a home map.
5. Store `procedure_goals` separately. For every Goal link, maintain a secondary index that points to the Procedure’s home. A materialized read model may duplicate searchable text or a cached Procedure summary, but the authoritative Procedure row should have one writer.
6. Store `placement_epoch` and `bucket_id` with the Procedure (or in a versioned side record) so migrations and stale routes are diagnosable.

This is a **hybrid**, not a claim that one published algorithm supplies the whole design: HRW supplies deterministic local ownership, the bucket layer supplies stable growth, the directory supplies explicit epochs/overrides and cached routing, and the relation table supplies multi-Goal semantics.

#### How it answers the requested cases

- **New Procedure with no Goal or an ordinary specific Goal:** validate the Goal if the control plane is available, compute the stable bucket from `procedure_id`, choose the current weighted owner, write the Procedure, and publish/update the Goal index. The base path does not require a Goal-to-shard lookup, which prevents the central Goal catalog from becoming a per-write routing dependency.
- **Strict co-location with one Goal:** use a bounded `goal_family`/Goal shard class as an affinity constraint or make `goal_id` part of the placement key only for Procedures whose policy explicitly requires it. Add a per-Goal quota/split threshold so a popular Goal cannot monopolize a shard. A raw `goal_id` hash is simple but can create a hot partition; a `goal_family` prefix is usually a safer default for a large heterogeneous catalog.
- **Multiple applicable Goals:** choose one `primary_goal_id` or one placement class for the canonical home, and keep all other links in `procedure_goals`. A query asking “which Procedures apply to Goals G1…Gn?” can fan out through the Goal indexes; it does not require moving or duplicating the canonical Procedure. If a product requirement demands physically duplicated material for every Goal, treat those copies as explicitly versioned read models with a defined source of truth.
- **Rebalancing:** recompute only bucket ownership for added/removed capacity, then move one bucket/epoch at a time. Keep the old owner serving reads through a forwarding record until the new owner has the data and the epoch is durably published. This is the same separation of ownership and data movement visible in token/range systems, but it gives this architecture a stable semantic key. [Cassandra vnode documentation](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html) [Spanner pre-splitting](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview)
- **Growth from 1 to 100:** initially map every logical bucket to the one physical shard. As physical shards join, assign each a weighted subset of buckets and migrate those buckets; no Procedure key or client-side hash formula needs to change. If the deployment starts directly with all 100 physical shards, pre-splitting the logical bucket space still gives the rebalancer a safe unit of movement. Spanner’s pre-split/split/merge model is a useful operational analogue. [Spanner pre-splitting](https://docs.cloud.google.com/spanner/docs/pre-splitting-overview)
- **Abstract/control database failure:** routers and shards retain the last signed/validated placement epoch, bucket-owner map, and the minimum Goal snapshot needed for cached reads. Existing Procedure reads can continue if their home and semantic dependencies are available. New Procedures, fresh applicability decisions, Goal mutations, and migrations should queue or fail closed unless the product explicitly defines a stale-Goal emergency mode. AWS’s separation of control-plane administration from data-plane service supports this fail-steady model. [AWS REL11-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_withstand_component_failures_avoid_control_plane.html)

#### Candidate ranking and tradeoffs

| Candidate | Suitability for this use case | Main strengths | Main costs/risks |
|---|---|---|---|
| **Bucketized weighted HRW** | **Best default** | No per-Procedure directory lookup for the base route; deterministic; easy to explain; capacity-aware; stable growth through buckets; independent data-plane reads. | Bucket catalog/versioning still needs replication; affinity constraints can reduce balance; HRW membership changes can move keys unless bucketized; not an optimal graph partitioner. |
| **Weighted consistent-hash ring with vnodes** | Strong alternative | Mature ring model; fine-grained ownership; natural ordered backup selection; familiar operations in some databases. | Ring metadata, gossip/failure detection, vnode repair, and hot-token management add operational complexity; Goal affinity is not intrinsic. [Cassandra](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html) [Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers) |
| **Directory/lookup table over fixed buckets** | Best when policy/auditability dominates | Explicit Goal-family placement, tenant constraints, manual overrides, and simple audit questions; supports related-data placement. | Central directory is a write/migration dependency; mapping size and stale snapshots matter; 1-to-100 growth needs a planned data move; more failure modes than pure hashing. [Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/26/shard/creating-tables-sharded-directory.html) [Lookup Tables](https://dspace.mit.edu/bitstream/handle/1721.1/137764/lookup_tables.pdf;jsessionid=1D1DE705877B4A0F7C9613CF81723FBA?sequence=2) |
| **Range/prefix by Goal family** | Good for hierarchy/range locality | Co-locates related Goal families; supports range scans and human-auditable boundaries; split/merge gives controlled movement. | Hot prefixes/Goal families; awkward multi-Goal ownership; boundary-map control dependency; poor fit if Procedures are accessed mostly by independent IDs. [RavenDB](https://docs.ravendb.net/7.2/sharding/administration/sharding-by-prefix) [MongoDB ranges](https://www.mongodb.com/docs/manual/core/ranged-sharding/) |
| **Graph partitioner plus lookup labels** | Use as an offline/periodic optimizer | Can reduce cross-shard communication for known co-access patterns and balance partition weights. | Requires a workload graph and global recomputation; dynamic Goals and Procedures age the model; graph labels need a deterministic online fallback. [Golab et al.](https://ar5iv.labs.arxiv.org/html/1312.0285) [Schism](https://15799.courses.cs.cmu.edu/fall2013/static/papers/schism-vldb2010.pdf) |
| **Locality-aware weighted assignment** | Use as a policy wrapper | Combines capacity, geography, tenant, and access locality; can adapt to changing load. | Scores can oscillate and cause migration churn; requires telemetry and explicit hard constraints; stale scores are dangerous during control failure. [Akkio](https://www.usenix.org/system/files/osdi18-annamalai.pdf) [MongoDB zones](https://www.mongodb.com/docs/v8.0/core/zone-sharding/) |
| **Root-partitioned hierarchy** | Use when there are real cells/regions/tenants | Two-stage growth; coarse locality and administrative isolation; top-level routing can be cached. | Root table is a new hotspot/SPOF; extra hops and metadata; unnecessary complexity for 100 undifferentiated physical shards. [Hierarchical DHT](https://www.eurecom.fr/en/publication/1186/download/ce-felbpa-030826.pdf) |

[Kinesis paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2008/01/Kinesis.pdf) [Akkio paper](https://www.usenix.org/system/files/osdi18-annamalai.pdf) |

#### Situational recommendations

- **Choose bucketized weighted HRW** when the dominant requirements are 100-way distribution, minimal data-plane dependencies, simple auditability, and predictable growth.
- **Choose a weighted ring** when the organization already operates a ring-based database or needs ordered successor/preference lists and mature vnode tooling.
- **Choose a directory/lookup table** when a human or policy engine must be able to answer “why is this Procedure there?”, place a whole Goal family deliberately, or enforce constraints that hashing cannot express.
- **Choose range/prefix** when most access is by Goal family or ordered semantic ranges, and hot-family splitting can be managed.
- **Choose graph/locality** only after measuring co-access and cross-shard query patterns; use it to generate bucket/range assignments or periodic migrations, not as an unversioned oracle for every insert.
- **Choose hierarchy** when the 100 shards are grouped by geography, legal domain, tenant, or administrative cell and those groups are part of the availability model.
- **Keep tiering separate:** tier can affect caching, storage class, and read placement, while the canonical Procedure home remains one stable location.

#### Minimum validation plan before implementation

**Design judgment:** Benchmark the top candidates against the same synthetic and trace-derived workload:

- Procedure-size and read-rate skew, including a small number of very hot Goals.
- Goal fan-out from one to many and the fraction of Procedures with multiple applicable Goals.
- Cross-shard retrieval/join traffic and the cost of a Goal-index fan-out.
- 1-to-100 growth movement in bytes, rows, epochs, and peak read/write latency.
- One-shard failure, topology-weight change, stale placement map, and full abstract/control DB outage.
- Hot-family prefix behavior, graph rebalancing churn, and root-directory cache staleness.
- Recovery correctness: no lost Procedure, no split-brain writer, no stale Goal index silently presented as authoritative.

Acceptance should be numeric, as the repository’s engineering rules require: movement budget, skew bound, routing/control-plane lookup latency, and explicit behavior for each outage class. The cited papers support the mechanisms, but the final thresholds must come from these measurements.

### Gaps

- The central open decision is whether Goal affinity is a correctness requirement, a performance preference, or merely a way to organize secondary indexes. The recommendation assumes it is normally a preference.
- The number and size of logical buckets, the shard weighting formula, and the replica factor are unspecified; these determine the real movement and failure tradeoffs.
- The consistency model for `procedure_goals` and Goal snapshots during a control-plane outage is unspecified. A stale snapshot may be acceptable for retrieval metadata but unsafe for applicability or authorization.
- It is unclear whether the 100 physical shards are homogeneous, geographically distributed, or constrained by tenant/legal boundaries. Those facts could move range/prefix, locality, or hierarchy from optional to primary.
- No primary source found in this review directly compares all requested strategies on semantic Goal/Procedure placement with a central Goal database. The recommendation is therefore a reasoned synthesis, not a sourced universal optimum.
- Before selecting graph partitioning or dynamic locality assignment, obtain a representative trace of Procedure reads, Goal evaluations, and cross-shard transactions; without that, their objective functions are ungrounded.
