# Distributed PostgreSQL for Hierarchical Goal Sharding

## 1. Which distributed PostgreSQL pattern fits a control database plus about 100 Procedure shards?

### Takeaway

Use a **catalog/control-plane architecture with independently routed PostgreSQL data stores**: keep one canonical owner for each business object, keep global Goal identity, routing, hierarchy, migration state, and cross-shard audit in the control database, and make each Procedure shard locally transactional and independently recoverable. PostgreSQL FDWs can be useful for controlled read-through or migration work, but they should not be the canonical write path; Citus, CockroachDB, YugabyteDB, and Spanner solve different distributed-database problems and would be a platform migration rather than a small extension of the current design. [repository `docs/sharding.md`](../../../docs/sharding.md), [PostgreSQL `postgres_fdw`](https://www.postgresql.org/docs/current/postgres-fdw.html), [Citus metadata reference](https://docs.citusdata.com/en/v12.0/develop/api_metadata.html), [CockroachDB architecture](https://www.cockroachlabs.com/docs/stable/architecture/overview) (accessed 2026-09-24).

#### Native PostgreSQL: one cluster, multiple databases, or multiple schemas

- PostgreSQL’s native hierarchy is **cluster → database → schema → table**. A client connection specifies one database and cannot access more than one database in that connection; clients can open multiple connections instead. PostgreSQL explicitly recommends separate databases for unrelated projects and separate schemas inside one database for interrelated resources. [PostgreSQL 18.6, “Managing Databases: Overview”](https://www.postgresql.org/docs/current/manage-ag-overview.html) (release 2026-08-13; accessed 2026-09-24).
- Databases in one PostgreSQL cluster are isolated from one another at the user/security boundary, but they share cluster-level resources and WAL. PostgreSQL calls out the shared WAL as an important backup/recovery coupling when multiple databases are placed in one cluster. [PostgreSQL 18.6, “Managing Databases: Overview”](https://www.postgresql.org/docs/current/manage-ag-overview.html) (accessed 2026-09-24).
- Therefore, 100 databases in one PostgreSQL cluster provide namespace and authorization separation, not independent compute, network, storage, backup, or failure domains. Separate PostgreSQL clusters/instances are required when the operational objective is independent capacity or failure isolation. The first conclusion is an inference from PostgreSQL’s documented cluster/database hierarchy and shared WAL; the second is the architectural consequence, not a PostgreSQL guarantee quoted verbatim. [PostgreSQL 18.6, “Managing Databases: Overview”](https://www.postgresql.org/docs/current/manage-ag-overview.html) (accessed 2026-09-24).
- PostgreSQL describes schemas as namespace isolation inside a database rather than rigid database isolation. Therefore, when tables need ordinary joins, foreign keys, and one local transaction, keeping them in one database with separate schemas is the lower-complexity native choice; this is an architectural inference from the documented database boundary. [PostgreSQL 18.6, “Schemas”](https://www.postgresql.org/docs/current/ddl-schemas.html) and [“Managing Databases: Overview”](https://www.postgresql.org/docs/current/manage-ag-overview.html) (accessed 2026-09-24).
- **Assessment for this repo:** a native multi-database layout is appropriate when shards are managed as separate databases and the application explicitly routes by shard. It is inappropriate as a substitute for a distributed query planner, a global uniqueness mechanism, or a cross-database transaction system. The connection/database boundary and shared-cluster backup coupling are documented by PostgreSQL. [PostgreSQL 18.6, “Managing Databases: Overview”](https://www.postgresql.org/docs/current/manage-ag-overview.html) (accessed 2026-09-24).

#### PostgreSQL foreign-data wrappers

- `dblink` is the lower-level alternative: it opens persistent connections to remote PostgreSQL databases and executes queries or commands through functions. It is useful for explicit remote operations, but it supplies no declarative cross-database foreign-key or distributed-transaction layer. [PostgreSQL 18.6, “dblink”](https://www.postgresql.org/docs/current/dblink.html) and [`dblink`](https://www.postgresql.org/docs/current/contrib-dblink-function.html) (accessed 2026-09-24).
- `postgres_fdw` provides foreign-server and foreign-table definitions that proxy remote PostgreSQL tables; it can push some predicates to the remote server and can perform remote `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `COPY`, and `TRUNCATE` operations. It is a remote access layer, not a replacement canonical store. [PostgreSQL 18.6, `postgres_fdw`](https://www.postgresql.org/docs/current/postgres-fdw.html) (accessed 2026-09-24).
- A local transaction that uses a foreign table opens a corresponding remote transaction and savepoints. Remote transactions use `SERIALIZABLE` when the local transaction is `SERIALIZABLE`, otherwise `REPEATABLE READ`; multiple remote transactions are committed or aborted serially by default. PostgreSQL 18 explicitly states that `postgres_fdw` cannot prepare a remote transaction for two-phase commit. [PostgreSQL 18.6, `postgres_fdw`, “Transaction Management”](https://www.postgresql.org/docs/current/postgres-fdw.html#POSTGRES-FDW-TRANSACTION-MANAGEMENT) (accessed 2026-09-24).
- Constraints declared on a foreign table are not enforced by core PostgreSQL, and most foreign-data wrappers do not enforce them either. The local planner assumes the remote data satisfies the declared constraints; the operator is responsible for keeping the remote definition and data correct. [PostgreSQL 18.6, `CREATE FOREIGN TABLE`](https://www.postgresql.org/docs/current/sql-createforeigntable.html) (accessed 2026-09-24).
- Logical replication copies table data and changes, but it does not replicate database schema or DDL; sequence state is also not replicated. It is therefore not a self-contained Goal-replication or shard-migration mechanism unless schema deployment, sequence handling, conflict policy, and cutover are managed separately. [PostgreSQL 18.6, “Logical Replication”](https://www.postgresql.org/docs/current/logical-replication.html) and [“Logical Replication Restrictions”](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (accessed 2026-09-24).
- **Assessment:** use FDWs for controlled read-through, legacy federation, ad hoc inspection, or a migration bridge with explicit timeouts and circuit breakers. Do not put canonical Procedure writes behind an FDW, infer referential integrity from a foreign-table declaration, or use FDW remote transactions as if they supplied atomic cross-shard commits. Those conclusions follow from the documented remote-transaction and foreign-table-constraint behavior. [PostgreSQL 18.6, `postgres_fdw`](https://www.postgresql.org/docs/current/postgres-fdw.html) and [`CREATE FOREIGN TABLE`](https://www.postgresql.org/docs/current/sql-createforeigntable.html) (accessed 2026-09-24).

#### Declarative partitioning inside one PostgreSQL database

- A declarative partitioned table is a virtual parent with ordinary child tables; inserts are routed to a partition by the partition key, and partition pruning can avoid scanning irrelevant children. Dropping or detaching a partition can make bulk retention operations much faster than deleting rows. [PostgreSQL 18.6, “Table Partitioning”](https://www.postgresql.org/docs/current/ddl-partitioning.html) (accessed 2026-09-24).
- PostgreSQL’s native partitioning has meaningful constraint limits: a partitioned-table unique or primary-key constraint must include all partition-key columns; exclusion constraints have similar partition-key restrictions; and cross-partition restrictions cannot be enforced by the individual child indexes. Partition maintenance can also take strong parent locks, and attaching a partition can scan and lock the child. [PostgreSQL 18.6, “Table Partitioning,” limitations and maintenance](https://www.postgresql.org/docs/current/ddl-partitioning.html) (accessed 2026-09-24).
- PostgreSQL permits foreign tables as partitions, but the database operator must ensure that remote contents satisfy the partition rule. This combination does not turn a partitioned parent into a strongly consistent, independently recoverable network shard. [PostgreSQL 18.6, “Table Partitioning”](https://www.postgresql.org/docs/current/ddl-partitioning.html) and [`CREATE FOREIGN TABLE`](https://www.postgresql.org/docs/current/sql-createforeigntable.html) (accessed 2026-09-24).
- **Assessment:** use native partitioning inside a shard for time windows, retention, tenant subpartitions, or large append-only tables. Do not use 100 local partitions as a substitute for 100 independently provisioned databases when the requirement is network isolation, independent backup, or independent failure recovery. The first use follows PostgreSQL’s documented pruning/retention benefits; the second is an architectural distinction between local storage pieces and separate database services. [PostgreSQL 18.6, “Table Partitioning”](https://www.postgresql.org/docs/current/ddl-partitioning.html) (accessed 2026-09-24).

#### Citus: coordinator/worker extension model

- Citus uses a coordinator and workers. The coordinator plans and routes distributed SQL, while distributed-table data is stored in worker shards. `create_distributed_table()` creates shards based on a distribution column and records distribution metadata on the coordinator. [Citus 13.0.1, “Creating and Modifying Distributed Objects (DDL)”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html) (living page; accessed 2026-09-24).
- Citus maintains separate metadata for distributed tables, shard ranges, shard placements, worker nodes, and co-location groups: `pg_dist_partition`, `pg_dist_shard`, `pg_dist_placement`, `pg_dist_node`, and `pg_dist_colocation`. This is a concrete example of a catalog/control plane that is distinct from worker-owned business rows. [Citus 12.0 documentation, “Citus Tables and Views”](https://docs.citusdata.com/en/v12.0/develop/api_metadata.html) (living page; accessed 2026-09-24).
- Citus reference tables are single shards replicated to workers. Their writes use two-phase commit, which gives strong consistency but makes the reference table part of the distributed commit machinery. [Citus 13.0.1, “Reference Tables”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#reference-tables) (accessed 2026-09-24).
- Citus does not cross-reference uniqueness or referential integrity between workers. Foreign keys between colocated distributed tables must include the distribution column, and uniqueness/primary-key constraints must include it as well. A reference-table pattern is therefore not a free substitute for a global Goal identity constraint. [Citus 13.0.1, “Adding/Removing Constraints”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#addingremoving-constraints) (accessed 2026-09-24).
- Citus automatically propagates many DDL statements, but some DDL requires manual propagation and distribution-column changes are prohibited without a data move. Mixing parallel distributed operations with object propagation in one transaction has documented consistency/transaction tradeoffs. [Citus 13.0.1, “Modifying Tables”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#modifying-tables) (accessed 2026-09-24).
- Citus documents online shard rebalancing through logical replication, with a brief write lock while metadata promotes the subscriber shard. The coordinator’s metadata is small and can be streamed to a standby or backed up separately; worker nodes use PostgreSQL streaming replication. [Citus 13.0.1, “Cluster Management”](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html) (living page; accessed 2026-09-24).
- For its multi-tenant SaaS example, Citus gives 32–128 shards as a starting range for workloads below roughly 100 GB, while also warning that each distributed query opens connections per involved shard. This is workload-specific guidance, not a universal recommendation for 100 Procedure databases. [Citus 13.0.1, “Cluster Management”](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html) (accessed 2026-09-24).
- Citus multi-shard updates default to a one-phase commit protocol; two-phase commit can be selected, and two-phase commit introduces prepared transactions and manual recovery concerns. [Citus 13.0.1, “DML reference”](https://docs.citusdata.com/en/stable/develop/reference_dml.html) and [“Configuration Reference”](https://docs.citusdata.com/en/stable/develop/api_guc.html) (living pages; accessed 2026-09-24).
- **Assessment:** Citus is a good fit when the desired abstraction is one logical PostgreSQL cluster whose rows are automatically distributed and queried through a coordinator. It is a poor fit as a bolt-on for 100 already-independent Procedure databases, because it changes the routing, constraint, DDL, backup, and transaction model rather than merely adding a catalog table. The fit assessment is an inference from Citus’s documented coordinator, shard, constraint, DDL, and rebalancing model. [Citus 13.0.1, “DDL”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html), [“Cluster Management”](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html), and [“DML reference”](https://docs.citusdata.com/en/stable/develop/reference_dml.html) (accessed 2026-09-24).

#### Distributed SQL engines: CockroachDB, YugabyteDB, and Spanner

- CockroachDB presents a symmetric PostgreSQL-compatible SQL endpoint; data is divided into ranges, each replicated across nodes, and any node can route a request to the range’s leaseholder. Writes require consensus among range replicas, and the transaction layer supports cross-range and cross-table ACID transactions. [CockroachDB, “Architecture Overview”](https://www.cockroachlabs.com/docs/stable/architecture/overview) and [v26.2, “Transaction Layer”](https://www.cockroachlabs.com/docs/v26.2/architecture/transaction-layer) (accessed 2026-09-24).
- CockroachDB’s serializable transactions can require client-visible retry/restart handling, and its online schema changes run as background jobs rather than fully atomic multi-statement DDL transactions. These are operational tradeoffs even though normal data changes remain strongly consistent. [CockroachDB v26.2, “Transaction Layer”](https://www.cockroachlabs.com/docs/v26.2/architecture/transaction-layer) and [stable, “Online Schema Changes”](https://docs.cockroachlabs.com/docs/stable/online-schema-changes) (accessed 2026-09-24).
- CockroachDB full or incremental backups are consistent as of a timestamp and are intended primarily for disaster recovery; the service also exposes cluster/database/table backup scopes and backup jobs. [CockroachDB v26.1, “BACKUP”](https://www.cockroachlabs.com/docs/v26.1/backup) (accessed 2026-09-24).
- YugabyteDB splits tables into tablets, uses Raft replication for each tablet, and routes query-layer operations to the appropriate tablet. Its master service is a catalog manager and cluster orchestrator. [YugabyteDB, “Architecture”](https://docs.yugabyte.com/stable/architecture/) (accessed 2026-09-24).
- YugabyteDB supports ACID transactions spanning multiple rows and shards. It writes provisional records to participating tablets and maintains a transaction-status record so a transaction becomes visible atomically only after commit; this is an explicit distributed-systems cost, not a transparent extension of a local PostgreSQL transaction. [YugabyteDB v2026.1, “Distributed transactions”](https://docs.yugabyte.com/stable/architecture/transactions/distributed-txns/) (published 2025-11-15; accessed 2026-09-24).
- The Spanner paper’s locality model is instructive: interleaved tables form directories, directory rows and descendants are moved/ colocated as a unit, and the client schema declares locality relationships. The paper also describes Paxos replication and two-phase coordination when a transaction spans multiple Paxos groups. [Corbett et al., “Spanner: Google’s Globally-Distributed Database,” OSDI 2012, §§4.2 and 4.2.3](https://research.google.com/archive/spanner-osdi2012.pdf) (published 2012; accessed 2026-09-24).
- Current Cloud Spanner documentation describes tables as key ranges called splits, replicates each split across machines, uses consensus for writes, and requires extra two-phase coordination when a transaction touches multiple splits. It also recommends schema choices that avoid monotonically increasing write keys and use hash-based logical shards. [Cloud Spanner, “Life of reads and writes”](https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes) and [“Schema design best practices”](https://docs.cloud.google.com/spanner/docs/schema-design) (living pages; accessed 2026-09-24).
- **Assessment:** distributed SQL engines are appropriate when globally distributed ACID writes, automatic range/tablet rebalancing, and replicated failure handling are primary requirements. They are inappropriate for this repository as an incremental fix for a control DB plus separate Procedure databases: adopting one requires changing the storage engine, connection/routing behavior, schema/constraint assumptions, backup process, and operational ownership. That is an architectural inference from the engines’ documented range/tablet, consensus, distributed-transaction, and schema-change models. [CockroachDB, “Architecture Overview”](https://www.cockroachlabs.com/docs/stable/architecture/overview), [YugabyteDB, “Architecture”](https://docs.yugabyte.com/stable/architecture/), [Spanner paper](https://research.google.com/archive/spanner-osdi2012.pdf), and [Cloud Spanner current documentation](https://cloud.google.com/spanner/docs/whitepapers/life-of-reads-and-writes) (accessed 2026-09-24).

#### Catalog/control-plane and router architectures

- Vitess VSchema is an abstraction layer that presents underlying keyspaces/shards as one routed service. VSchema and routing rules live in a global topology; a combined serving graph is propagated to cells, and query routers use it for planning and routing. Rows receive a keyspace ID that remains stable while the key range is resharded. [Vitess v23.0, “VSchema”](https://vitess.io/docs/23.0/reference/features/vschema/) (last updated 2025-10-22; accessed 2026-09-24).
- Vitess distinguishes a canonical unsharded source for a reference table from copies maintained in sharded keyspaces. This is a useful precedent for a canonical central Goal directory plus optional read projections, but Vitess’s VReplication is a product-specific mechanism rather than a PostgreSQL primitive. [Vitess v23.0, “VSchema,” reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables) (accessed 2026-09-24).
- Vitess maintains a distinction between global VSchema/routing metadata and the per-shard physical schema, and provides commands to validate schema consistency across shards and keyspaces. [Vitess v23.0, “Schema Management”](https://vitess.io/docs/23.0/reference/features/schema-management/) (living page; accessed 2026-09-24).
- SPQR documents another PostgreSQL-oriented split: shards hold data, routers route PostgreSQL protocol traffic, a coordinator manages sharding metadata, and an etcd-backed QDB persists cluster metadata. Its documentation also calls out router availability and the need for multiple routers in production-style deployments. [SPQR, “Cluster Components”](https://docs.pg-sharding.tech/sharding/cluster_components/overview) and [“Router + Coordinator”](https://docs.pg-sharding.tech/deployment/router_coordinator) (living pages; accessed 2026-09-24).
- **Assessment:** the common control-plane pattern is: authoritative global metadata in a highly backed-up service; read-only routing/schema caches near workers; canonical data owned by the relevant shard; and explicit propagation/repair for metadata changes. Citus, Vitess, and SPQR are useful analogies, not reasons to add their routers or extensions to this repository. The pattern is an inference from the cited architecture descriptions. [Citus “Citus Tables and Views”](https://docs.citusdata.com/en/v12.0/develop/api_metadata.html), [Vitess “VSchema”](https://vitess.io/docs/23.0/reference/features/vschema/), and [SPQR “Cluster Components”](https://docs.pg-sharding.tech/sharding/cluster_components/overview) (accessed 2026-09-24).

### Inferences

- **Recommended target placement.** Make abstract/control Goals canonical in the control database, and keep canonical `procedures`, their local Claims, evidence, execution plans, and version rows on one owning shard, preferably colocated by `goal_id`. Keep `object_routes`, row routes, shard registry, hierarchy edges, identity decisions, global audit, migration manifests, leases, and projection/outbox state in the control database. The current repository still permits canonical Goal rows on knowledge shards; if that physical placement is retained, the control database must be the authoritative directory/index and the shard Goal row the single payload owner, not a second competing authority. This is the control-plane pattern documented by the repository, whose `docs/sharding.md` explicitly separates the control registry/routes/projections from canonical knowledge shards. [repository `docs/sharding.md:1-90`](../../../docs/sharding.md), [repository `backend/db/95_control_plane_shards_projections.sql:1-11,40-66`](../../../backend/db/95_control_plane_shards_projections.sql), [Citus metadata reference](https://docs.citusdata.com/en/v12.0/develop/api_metadata.html), [Vitess VSchema](https://vitess.io/docs/23.0/reference/features/vschema/) (accessed 2026-09-24).
- **One canonical home per row.** Store exactly one authoritative home shard for each Goal, Procedure family/version row, Claim, and other routed object. A route is metadata, not a second copy. The repository already follows this rule: canonical rows live on knowledge shards, `object_routes` maps IDs to homes, and projections carry the route. [repository `docs/sharding.md:5-25`](../../../docs/sharding.md), [repository `backend/db/95_control_plane_shards_projections.sql:40-66`](../../../backend/db/95_control_plane_shards_projections.sql) (lines cited; accessed 2026-09-24).
- **Local transactions, explicit cross-shard workflows.** A Procedure write, its local version row, and colocated evidence/claims should commit in one local shard transaction. A Goal-directory update and a Procedure write on another database must not be presented as one ordinary PostgreSQL transaction. Use an outbox/event, idempotency key, retryable state, and reconciliation job instead. This is an inference from PostgreSQL’s one-database connection model and `postgres_fdw`’s documented inability to prepare remote transactions for 2PC. [PostgreSQL database overview](https://www.postgresql.org/docs/current/manage-ag-overview.html), [`postgres_fdw` transaction management](https://www.postgresql.org/docs/current/postgres-fdw.html#POSTGRES-FDW-TRANSACTION-MANAGEMENT) (accessed 2026-09-24).
- **Cross-shard references.** Use stable IDs plus route metadata: for example, a Procedure row stores `goal_id`, `goal_version`, and optionally `goal_snapshot_hash`; the central directory resolves `goal_id` to the Goal’s home/version; the shard stores no cross-database foreign key. A local projection table may have a local FK to its own cache row, but that proves only local cache integrity, not central Goal existence. The repository’s migration 96 replaces physical cross-object FKs with route-aware validation and an explicit verifier, which is the appropriate precedent. [repository `backend/db/96_sharded_canonical_writes.sql:1-15,18-42,66-103`](../../../backend/db/96_sharded_canonical_writes.sql) (lines cited; accessed 2026-09-24).
- **Goal hierarchy is control-plane metadata.** Store `SPECIALIZES` or other abstract/specific edges in the control database with `specific_goal_id`, `abstract_goal_id`, status, provenance, confidence, and decision ID. Do not let a hierarchy edge silently determine physical placement unless a separate placement policy explicitly says so. This preserves multi-parent/asynchronous hierarchy semantics and avoids making every child Procedure depend on a recursive cross-shard graph. The repository’s sharding design says hierarchy is separate, optional, and never used for sharding. [repository `docs/sharding.md:3-25`](../../../docs/sharding.md), [repository `backend/db/95_control_plane_shards_projections.sql:83-101`](../../../backend/db/95_control_plane_shards_projections.sql) (lines cited; accessed 2026-09-24).
- **Routing metadata should be authoritative centrally and cached locally.** The control database should own `shard_id`, status/weight, DSN-environment name, capacity/health, object-to-home mappings, and schema/projection versions. A shard or service may cache route data, but a cache miss must be distinguishable from an outage. This follows the repository’s explicit `unavailable_shards` result and the coordinator/catalog pattern in Citus and Vitess. [repository `backend/app/services/shards.py:115-139,342-384`](../../../backend/app/services/shards.py), [Citus metadata reference](https://docs.citusdata.com/en/v12.0/develop/api_metadata.html), [Vitess VSchema](https://vitess.io/docs/23.0/reference/features/vschema/) (accessed 2026-09-24).
- **Identity and audit placement.** Keep global Goal identity decisions, exact-name/alias claims, merge decisions, and cross-shard audit events in the control database because they answer “which identity is global?” Keep execution evidence, Procedure provenance, and local audit context on the Procedure’s home shard for local transactionality; emit a central append-only event if a global audit view is required. This is an architectural inference from the need to separate global coordination from local ownership, not a vendor requirement. The repository already separates `identity_decisions` and `retrieval_decisions` in the control plane from shard-owned evidence. [repository `docs/sharding.md:7-12`](../../../docs/sharding.md), [repository `backend/db/95_control_plane_shards_projections.sql:104-134,229-266`](../../../backend/db/95_control_plane_shards_projections.sql) (lines cited; accessed 2026-09-24).
- **Migrations.** Use a migration manifest in the control database plus a per-shard migration ledger/checksum. Apply schema changes independently to every shard, with an expand/backfill/verify/contract sequence; do not assume logical replication carries DDL or sequences. Citus demonstrates that even a distributed PostgreSQL engine has DDL propagation exceptions, while PostgreSQL logical replication explicitly excludes schema and sequence state. [Citus “Modifying Tables”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#modifying-tables), [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (accessed 2026-09-24).
- **Backups and restore.** Back up the control database independently with PostgreSQL WAL/PITR and back up every data-shard cluster independently. Keep the route registry and migration/identity ledgers in the control backup, and rehearse a restore that checks every route and Goal reference before reopening writes. PostgreSQL’s PITR is cluster-level and WAL-based; `pg_dump` is not a substitute for PITR. [PostgreSQL 18.6, “Continuous Archiving and PITR”](https://www.postgresql.org/docs/current/continuous-archiving.html), [Citus cluster-management coordinator-failure guidance](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html) (accessed 2026-09-24).
- **Failure handling.** Mark shards `active`, `readonly`, `unhealthy`, or `retired`; stop new placement when necessary; use bounded connection backoff; return explicit partial/unavailable results; and never interpret an unreachable shard as “the object does not exist.” For a control-database outage, use a highly available control plane and cached routes; if global identity cannot be arbitrated safely, fail closed for new global Goal writes rather than creating duplicates. The repository’s `ShardPools`, `HydrationResult`, and `verify_routes` behavior is a concrete implementation of this rule. [repository `backend/app/services/shards.py:115-139,264-320,329-384,387-429`](../../../backend/app/services/shards.py) (lines cited; accessed 2026-09-24).
- **Recovery sequence.** Keep a failed shard non-writable, restore it to a known backup/WAL point, replay idempotent projection/audit events from a recorded cursor, compare row counts and hashes for routed objects, run the cross-shard reference verifier, and only then mark it readable/writable. This sequence is an operational inference from PostgreSQL PITR, Citus’s logical-replication rebalance/cutover model, and the repository’s route verifier. [PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html), [Citus cluster management](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html), [repository `backend/app/services/shards.py:387-429`](../../../backend/app/services/shards.py) (accessed 2026-09-24).
- **Patterns to reject for this repo now:** do not use a cross-database foreign key as if PostgreSQL could enforce it; do not put canonical writes behind `postgres_fdw`; do not require distributed 2PC for every Goal/Procedure operation; do not use local declarative partitions as independent network shards; do not adopt Citus merely to obtain 100 shards; and do not migrate to CockroachDB/YugabyteDB/Spanner without a separate platform decision and compatibility/migration program. These exclusions follow from the documented boundaries and operational models above. [PostgreSQL database overview](https://www.postgresql.org/docs/current/manage-ag-overview.html), [`postgres_fdw`](https://www.postgresql.org/docs/current/postgres-fdw.html), [PostgreSQL partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html), [Citus constraints](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#addingremoving-constraints), [Cockroach architecture](https://www.cockroachlabs.com/docs/stable/architecture/overview), and [Yugabyte architecture](https://docs.yugabyte.com/stable/architecture/) (accessed 2026-09-24).

### Gaps

- No source can determine whether the workload needs 100 physical database services, 100 schemas, 100 partitions, or fewer shards. The decision needs current row counts, QPS, read/write ratio, data size per shard, fan-out distribution, latency percentiles, and growth forecasts; Citus’s 32–128 range is explicitly workload-specific. [Citus cluster management](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html) (accessed 2026-09-24).
- The required RPO/RTO is unspecified. That determines whether the control database needs synchronous standby, asynchronous replicas, or a restored-from-backup degraded mode, and whether each shard needs local streaming replicas. PostgreSQL documents the WAL/PITR mechanism but not this project’s recovery objective. [PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html) (accessed 2026-09-24).
- The acceptable projection-lag window for Goal changes, merges, deprecations, and ACL changes is unknown. A read model may be acceptable for search but not for a permission-changing write; this requires a product/security decision rather than a database-source lookup. [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) and [Vitess reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables) (accessed 2026-09-24).
- No benchmark was found for 100 independently provisioned PostgreSQL shards with the repository’s vector, full-text, RLS, bitemporal, and audit workload. A controlled two- and multi-shard experiment should measure route-lookup cost, fan-out, migration duration, backup duration, restore time, and failure recovery before setting a hard shard count. The cited vendor documents establish mechanisms, not this workload’s performance. [PostgreSQL database overview](https://www.postgresql.org/docs/current/manage-ag-overview.html), [Citus cluster management](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html), [Cockroach backup](https://www.cockroachlabs.com/docs/v26.1/backup) (accessed 2026-09-24).

## 2. Should an abstract Goal be replicated into Procedure shards or referenced by ID from a central directory?

### Takeaway

Keep the abstract Goal **canonical and centrally registered**; Procedure shards should reference its stable `goal_id` and, for historical correctness, a `goal_version` or content hash. Replicate only a deliberately defined, read-only Goal projection into shards when local reads or joins justify the staleness and storage cost. A replicated Goal must never become a second identity, hierarchy, permission, merge, or audit authority. [repository `backend/db/83_goals.sql`](../../../backend/db/83_goals.sql), [repository `docs/sharding.md`](../../../docs/sharding.md), [Citus reference tables](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#reference-tables), [Vitess reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables) (accessed 2026-09-24).

### Cited Findings

- The repository already defines Goal as a stable-ID, lightweight object with bitemporal fields and a version, and says Procedure/Implementation relationships should point to that entity rather than rely on free-text matching. [repository `backend/db/83_goals.sql:1-18,25-37,65-119,178-201`](../../../backend/db/83_goals.sql) (lines cited; accessed 2026-09-24).
- The repository’s control-plane migration explicitly says the search indexes are rebuildable projections, not a second canonical store; projection rows carry stable IDs and home-shard metadata. [repository `backend/db/95_control_plane_shards_projections.sql:1-11,136-227`](../../../backend/db/95_control_plane_shards_projections.sql) (lines cited; accessed 2026-09-24).
- The repository’s current sharding design assigns each Goal one immutable `home_shard_id`, places Goal-local Procedures preferentially on that shard, and exposes cross-goal objects through projections. It also says hierarchy is separate and never determines placement. [repository `docs/sharding.md:1-25`](../../../docs/sharding.md) (lines cited; accessed 2026-09-24).
- The current service resolves exact Goal identity through the control-plane `goal_names`/projection indexes and then reads the canonical row from its home shard; remote Goal writes record a route before the canonical row is written. [repository `backend/app/services/goals.py:181-218,316-457`](../../../backend/app/services/goals.py) (lines cited; accessed 2026-09-24).
- The repository’s remote-write migration replaces physical cross-object foreign keys with route-aware validation, and adds a global exact-name table because a per-database unique index cannot see other shards. [repository `backend/db/96_sharded_canonical_writes.sql:1-15,18-42,127-179`](../../../backend/db/96_sharded_canonical_writes.sql) (lines cited; accessed 2026-09-24).
- PostgreSQL logical replication can provide ordered DML changes for a publication/subscription, but it does not replicate schema, DDL, or sequence state. A Goal projection therefore needs a separate schema/version and event protocol rather than an assumption that copying a table also copies the application contract. [PostgreSQL 18.6, “Logical Replication”](https://www.postgresql.org/docs/current/logical-replication.html) and [“Restrictions”](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (accessed 2026-09-24).
- Citus reference tables demonstrate a replicated read model with a single distributed source, but writes to those copies use 2PC. This is a useful design precedent for a small immutable snapshot, not evidence that a mutable Goal should be synchronously replicated everywhere. [Citus 13.0.1, “Reference Tables”](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#reference-tables) (accessed 2026-09-24).
- Vitess likewise describes a canonical unsharded source for a reference table and asynchronously maintained copies in sharded keyspaces. The important distinction is canonical source versus read copies. [Vitess v23.0, “VSchema,” reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables) (last updated 2025-10-22; accessed 2026-09-24).
- Distributed SQL engines solve atomic cross-shard references by embedding placement and transaction coordination inside the engine; that is a different contract from a UUID reference plus central directory. CockroachDB supports cross-range/cross-table transactions, while YugabyteDB uses provisional records and a transaction-status tablet; both add consensus machinery rather than making a replicated Goal ordinary local data. [CockroachDB v26.2, “Transaction Layer”](https://www.cockroachlabs.com/docs/v26.2/architecture/transaction-layer), [YugabyteDB v2026.1, “Distributed transactions”](https://docs.yugabyte.com/stable/architecture/transactions/distributed-txns/) (accessed 2026-09-24).

### Inferences

- **Use one Goal authority, not two.** For the target design, keep abstract/control Goal rows and their identity/alias uniqueness, lifecycle/version history, `merged_into_id`, hierarchy edges, ACL/visibility decisions, and global route `(goal_id → canonical home/version)` in the control database. If the current physical Goal-home-shard placement is retained, keep exactly one canonical payload row on that shard and make the control-plane directory authoritative for identity, route, and version; do not create a second mutable Goal row. A `goal_directory` view or table can expose either arrangement without duplicating authority. This follows the repository’s existing distinction between canonical goals and rebuildable projections. [repository `backend/db/83_goals.sql:65-119`](../../../backend/db/83_goals.sql), [repository `backend/db/95_control_plane_shards_projections.sql:1-11,40-66`](../../../backend/db/95_control_plane_shards_projections.sql), [repository `docs/sharding.md:5-25`](../../../docs/sharding.md) (lines cited; accessed 2026-09-24).
- **Procedure-shard schema sketch.** Keep the following as a logical contract, not a proposed product-code edit:
  - `procedures(..., goal_id uuid NOT NULL, goal_version integer NOT NULL, goal_snapshot_hash text NULL, ...)`
  - `procedure_goal_refs(goal_id uuid NOT NULL, goal_version integer NOT NULL, canonical_name text NOT NULL, status text NOT NULL, merged_into_id uuid NULL, source_event_id uuid NOT NULL, projected_at timestamptz NOT NULL, PRIMARY KEY (goal_id, goal_version))`
  - `control.goal_projection_outbox(event_id uuid PRIMARY KEY, goal_id uuid NOT NULL, goal_version integer NOT NULL, event_type text NOT NULL, payload jsonb NOT NULL, created_at timestamptz NOT NULL, published_at timestamptz NULL)`
  - `shard.goal_projection_inbox(event_id uuid PRIMARY KEY, goal_id uuid NOT NULL, goal_version integer NOT NULL, received_at timestamptz NOT NULL, applied_at timestamptz NULL)`
  - The Procedure row’s `goal_id` is a stable logical reference. `goal_version` preserves the Goal state observed when the Procedure was authored or executed; `goal_snapshot_hash` detects a stale or mismatched projection without making the shard authoritative. The versioned-reference choice is an inference from the repository’s bitemporal/versioned Goal model and the need for historical auditability. [repository `backend/db/83_goals.sql:25-37,104-111`](../../../backend/db/83_goals.sql), [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (accessed 2026-09-24).
- **Goal write and projection protocol.** Use an at-least-once, idempotent protocol:
  1. In one control-database transaction, reserve/resolve the Goal identity, append the canonical Goal version, append the Goal event to the outbox, and record the route. Do not attempt a remote Goal-row insert in the same transaction.
  2. A publisher delivers the event to each interested shard. A shard upserts the projection by `(goal_id, goal_version)`, rejects older versions, and records the event ID for replay suppression.
  3. A Procedure write validates the route and the minimum acceptable projection version, then writes the Procedure and its `goal_id`, `goal_version`, and hash in the Procedure shard’s local transaction.
  4. A background reconciler compares directory revisions, projection versions, route ownership, and actual Goal rows; it repairs missing/stale projections and reports unresolved references.
  5. Reads return the central canonical row when available; local projections may serve display, filtering, and local joins with an explicit freshness/lag signal.
  The outbox and idempotent-consumer pattern is an inference from the documented limitations of DDL-less logical replication and the repository’s existing projection-outbox discipline. [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html), [repository `docs/sharding.md:36-45`](../../../docs/sharding.md) (lines cited; accessed 2026-09-24).
- **Abstract Goal should be referenced by ID, not synchronously replicated as authority.** A mutable Goal can be deprecated, merged, re-scoped, or have its aliases/status changed; a full copy on every shard creates multiple possible truths unless every update is a carefully coordinated distributed transaction. The repository’s Goal lifecycle and bitemporal fields make that risk concrete. [repository `backend/db/83_goals.sql:85-92,104-111`](../../../backend/db/83_goals.sql) (lines cited; accessed 2026-09-24).
- **Replicate a projection only for a named read purpose.** A minimal projection containing `goal_id`, `version`, `status`, `merged_into_id`, normalized/display name, scope/visibility decision needed for filtering, and content hash is usually safer than copying every canonical JSON field. Include a projection schema version and source event ID. Full text, embeddings, and descriptions should be added only when a measured query needs them and the privacy policy permits replication. The preference for minimal, versioned read models is an inference from the canonical/projection distinction and PostgreSQL’s warning that replication does not carry schema or sequences. [repository `backend/db/95_control_plane_shards_projections.sql:136-227`](../../../backend/db/95_control_plane_shards_projections.sql), [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (accessed 2026-09-24).
- **Pin historical meaning.** A Procedure should continue to point to the same Goal identity even if the Goal is later merged or deprecated. At read time, resolve `merged_into_id` through the central directory; at execution/audit time, retain the pinned `goal_version` and, if policy requires, the exact snapshot/hash used. Do not rewrite every Procedure synchronously during a Goal merge. This preserves append-only/bitemporal meaning and turns a merge into an event/repair operation. The recommendation follows the repository’s invalidate-and-append/merge fields and the distributed-systems principle that a stable identity should not be silently replaced; it is an architectural inference rather than a vendor mandate. [repository `backend/db/83_goals.sql:85-111`](../../../backend/db/83_goals.sql), [Spanner paper on stable directories/locality and schema-change coordination](https://research.google.com/archive/spanner-osdi2012.pdf) (accessed 2026-09-24).
- **What may be replicated and what must not be:**
  - **May replicate:** immutable/versioned display snapshot, search projection, normalized name/alias projection, status/merge pointer, content hash, and a local route cache.
  - **Must remain central/audited:** canonical Goal row, global identity decisions, exact normalized-name uniqueness, alias ownership, hierarchy edges and their acceptance state, permission/visibility decisions, merge authority, and global event history.
  - **Must remain local to the Procedure shard:** Procedure row/version, local execution plan, evidence, claims colocated with the Procedure, and local provenance/audit context.
  - **May be duplicated only as an explicitly read-only projection:** any Goal description, embedding, expected outcome, or verification contract needed for local search/execution. Each copy needs a version/hash and a repair path. This allocation is an inference from the requested control-plane split and the canonical-source/reference-table precedents. [repository `docs/sharding.md:5-25,36-70`](../../../docs/sharding.md), [Citus reference tables](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#reference-tables), [Vitess reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables) (accessed 2026-09-24).
- **Security consequence.** Never replicate private/user-scoped Goal text into public-corpus shards merely to avoid a lookup. The repository’s sharding rules keep private/organization rows on the home/control shard and explicitly distinguish public placement from private data; a Goal projection must preserve that visibility boundary or remain on the authorized shard. [repository `docs/sharding.md:39-45,72-75`](../../../docs/sharding.md) (lines cited; accessed 2026-09-24).
- **Control-database failure policy.** If the directory is unavailable, a shard may serve a previously projected Goal for reads if its freshness policy permits, but a new global Goal identity write should fail closed or enter a durable pending queue. Never create a second Goal merely because the directory is unreachable. If a Procedure’s required Goal version is not present, expose a pending/unavailable state rather than accepting an unverifiable reference. This is an inference from the need for global identity arbitration and the repository’s explicit distinction between missing and unreachable shards. [repository `backend/app/services/shards.py:329-384,387-429`](../../../backend/app/services/shards.py) (lines cited; accessed 2026-09-24).
- **Migration policy for Goal projections.** Add a new projection column/table and version first on all shards, deploy readers that accept old and new forms, backfill by `goal_id`/event sequence, compare hashes and counts, then switch writers and only later remove old fields. Logical replication can carry DML but cannot be the schema deployment mechanism; Citus’s own DDL propagation caveats reinforce the need for an explicit migration state machine. [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html), [Citus DDL modification guidance](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#modifying-tables) (accessed 2026-09-24).
- **Bottom-line decision matrix:**
  - Central directory with canonical `goal_id`: **yes**.
  - Full mutable Goal copied to every Procedure shard: **no**.
  - Versioned read-only Goal projection on a shard: **yes, when justified and observable**.
  - Cross-database foreign key from Procedure to central Goal: **no**.
  - Local FK from Procedure to a local projection row: **acceptable, but insufficient by itself**.
  - Distributed transaction for every Goal merge/Procedure write: **no** in the current architecture.
  - FDW-based central Goal lookup on every request: **not the default**.
  These are recommendations inferred from the cited PostgreSQL/Citus/Vitess/repository behavior. [PostgreSQL `postgres_fdw`](https://www.postgresql.org/docs/current/postgres-fdw.html), [Citus reference tables](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#reference-tables), [Vitess reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables), [repository `docs/sharding.md`](../../../docs/sharding.md) (accessed 2026-09-24).

### Gaps

- The product has not yet specified the maximum acceptable staleness for a Goal projection during search, authorization, Procedure execution, and publication. Different consumers may require different policies; a single synchronous replication rule would be too strong without that answer. [Citus reference tables](https://docs.citusdata.com/en/stable/develop/reference_ddl.html#reference-tables), [PostgreSQL logical-replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (accessed 2026-09-24).
- The privacy classification of each Goal field is not supplied. It is therefore not yet possible to decide which description, expected-outcome, or embedding fields may be copied to public Procedure shards; this requires the repository’s data-rights policy, not a general database conclusion. [repository `docs/sharding.md:72-75`](../../../docs/sharding.md) (lines cited; accessed 2026-09-24).
- The desired semantics of a Goal merge during an in-flight Procedure write are unspecified. The design should choose among “new Procedures see the merged target,” “in-flight writes retain the pinned source until completion,” or “fail/retry pending writes”; each choice changes the state machine and audit record. [repository `backend/db/83_goals.sql:85-111`](../../../backend/db/83_goals.sql) (lines cited; accessed 2026-09-24).
- No workload-specific test has established whether a local Goal projection reduces latency enough to justify 100 copies, nor whether the projection’s size is small compared with Procedure data. Measure projection bytes, update rate, join rate, and fan-out before enabling it globally. [Citus cluster management](https://docs.citusdata.com/en/latest/admin_guide/cluster_management.html), [Vitess VSchema reference tables](https://vitess.io/docs/23.0/reference/features/vschema/#reference-tables) (accessed 2026-09-24).
