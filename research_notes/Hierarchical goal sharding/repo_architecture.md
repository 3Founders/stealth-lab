# Repository Architecture: Central Abstract Goals with Distributed Procedures

## 1. Current control/data-plane and placement model

### Takeaway
The repository already separates registry/routing/projection responsibilities from canonical knowledge storage, but it does not yet implement the requested topology: K000 is simultaneously the control database and the built-in canonical home, public Goals are distributed by weighted rendezvous hashing, and new Procedures/Claims prefer the Goal's shard. Goal hierarchy is explicitly excluded from physical placement. [docs/sharding.md#L3-L25](../../docs/sharding.md#L3-L25) [backend/db/95_control_plane_shards_projections.sql#L1-L15](../../backend/db/95_control_plane_shards_projections.sql#L1-L15) [backend/app/services/shards.py#L149-L171](../../backend/app/services/shards.py#L149-L171)

### Cited Findings
- **Control-plane registry:** `knowledge_shards` stores shard status, weight, an environment-variable name rather than a DSN, and optional `capacity_rows`; K000 is inserted as the built-in home shard. `object_routes` maps stable object IDs to home shards, while `goal_search_index`, `procedure_search_index`, and `claim_search_index` are rebuildable projections. [backend/db/95_control_plane_shards_projections.sql#L16-L51](../../backend/db/95_control_plane_shards_projections.sql#L16-L51) [backend/db/95_control_plane_shards_projections.sql#L136-L227](../../backend/db/95_control_plane_shards_projections.sql#L136-L227)
- **Control versus canonical storage:** migration 95 says the control tables are not a second canonical store; Goals, Procedures, and Claims remain canonical, with physical FKs unable to cross databases and application-level validation required for remote references. [backend/db/95_control_plane_shards_projections.sql#L4-L15](../../backend/db/95_control_plane_shards_projections.sql#L4-L15)
- **Current placement:** `choose_shard` is deterministic weighted HRW over writable shards; `choose_child_shard` returns a Goal's preferred shard when writable and otherwise falls back to HRW. [backend/app/services/shards.py#L142-L171](../../backend/app/services/shards.py#L142-L171)
- **Current Goal write path:** public Goal creation chooses a home, claims the global normalized name in `goal_names`, records the route, writes the canonical row on that shard, and queues/projects it. The remote sequence is multiple database operations rather than one distributed transaction. [backend/app/services/goals.py#L413-L471](../../backend/app/services/goals.py#L413-L471) [backend/app/services/goals.py#L487-L495](../../backend/app/services/goals.py#L487-L495)
- **Current Procedure write path:** `capture_procedure` resolves the Goal, calls `choose_child_shard` with the Goal's home, registers stable and row routes for a remote placement, writes the Procedure on the selected pool, and projects it. [backend/app/services/procedures.py#L251-L320](../../backend/app/services/procedures.py#L251-L320) [backend/app/services/procedures.py#L374-L477](../../backend/app/services/procedures.py#L374-L477)
- **Version and evidence locality:** a new version is written on the prior Procedure's home shard, and execution outcome/evidence writes are routed to that same shard. [backend/app/services/procedures.py#L604-L710](../../backend/app/services/procedures.py#L604-L710) [backend/app/services/procedures.py#L818-L830](../../backend/app/services/procedures.py#L818-L830) [docs/sharding.md#L61-L66](../../docs/sharding.md#L61-L66)
- **Visibility rule:** public placement can use remote shards, but private and organizational rows are forced to K000. [backend/app/services/shards.py#L39-L55](../../backend/app/services/shards.py#L39-L55) [docs/sharding.md#L72-L74](../../docs/sharding.md#L72-L74)
- **Identity and hierarchy:** `goal_names` is the global exact-name index, while `goal_relations` is a separate, optional, multi-parent hierarchy table whose rows start as `proposed` and are not used for sharding or required for retrieval. [backend/db/96_sharded_canonical_writes.sql#L127-L164](../../backend/db/96_sharded_canonical_writes.sql#L127-L164) [backend/db/95_control_plane_shards_projections.sql#L83-L102](../../backend/db/95_control_plane_shards_projections.sql#L83-L102) [backend/app/services/identity_resolution.py#L851-L870](../../backend/app/services/identity_resolution.py#L851-L870)
- **Retrieval shape:** the canonical retrieval path searches projections, hydrates only involved shards in one batch per shard, and reports unavailable shards distinctly from missing rows. Scan-oriented readers use fan-out helpers over K000 and every readable shard; lenient scans skip unavailable shards, while strict scans raise. [backend/app/services/retrieval_service.py#L8-L31](../../backend/app/services/retrieval_service.py#L8-L31) [backend/app/services/shards.py#L342-L384](../../backend/app/services/shards.py#L342-L384) [backend/app/services/shards.py#L432-L462](../../backend/app/services/shards.py#L432-L462)

### Inferences
- The requested design is a **policy split inside the existing routing substrate**, not a new sharding framework: retain the registry, stable-ID routes, projections, and outbox, but make Goal placement and Procedure placement different operations. A simple change to the Goal hash would not create a distinct abstract-Goal anchor or a 100-shard Procedure pool. [backend/app/services/shards.py#L51-L55](../../backend/app/services/shards.py#L51-L55) [backend/app/services/shards.py#L149-L171](../../backend/app/services/shards.py#L149-L171)
- K000 is already the natural control-plane authority for exact Goal identity, hierarchy metadata, identity decisions, and product/association tables; centralizing abstract Goals there would make those paths local, while Procedures and their execution lineage become the distributed data plane. [backend/db/95_control_plane_shards_projections.sql#L104-L134](../../backend/db/95_control_plane_shards_projections.sql#L104-L134) [backend/db/95_control_plane_shards_projections.sql#L136-L227](../../backend/db/95_control_plane_shards_projections.sql#L136-L227)
- A hot Goal-to-Procedure read should not fan out to 100 shards. The existing Procedure projection already carries `goal_id` and `home_shard_id`, but an authoritative reverse route/index is still needed so a central abstract Goal can enumerate its Procedures without scanning every data shard. [backend/app/services/search_projection.py#L109-L127](../../backend/app/services/search_projection.py#L109-L127) [backend/app/services/shards.py#L432-L462](../../backend/app/services/shards.py#L432-L462)
- The current relation model is suitable for semantic expansion and audit, but not as a physical placement signal: relation proposals are best-effort, can arrive after Goal creation, and may remain unaccepted. Placement therefore needs an explicit, durable Goal placement class or anchor record rather than an inference from `goal_relations`. [backend/app/services/identity_resolution.py#L851-L870](../../backend/app/services/identity_resolution.py#L851-L870) [backend/db/95_control_plane_shards_projections.sql#L83-L102](../../backend/db/95_control_plane_shards_projections.sql#L83-L102)

### Gaps
- The repository does not encode a 100-shard target. `capacity_rows` is registry metadata, but placement currently filters only on `status` and positive `weight`; no capacity threshold, target shard count, or 100-shard benchmark is enforced by the placement code. [backend/app/services/shards.py#L126-L160](../../backend/app/services/shards.py#L126-L160) [backend/db/95_control_plane_shards_projections.sql#L17-L33](../../backend/db/95_control_plane_shards_projections.sql#L17-L33)
- The current Goal hierarchy has no explicit `abstract`/`concrete` placement field. `goal_relations` can imply that a Goal is abstract, but its status is `proposed` by default and the relation writer is deliberately non-blocking. [backend/db/95_control_plane_shards_projections.sql#L83-L102](../../backend/db/95_control_plane_shards_projections.sql#L83-L102) [backend/app/services/identity_resolution.py#L851-L870](../../backend/app/services/identity_resolution.py#L851-L870)
- `get_goal` starts with a local `goals` query and does not route by `home_shard_id`; this is safe when Goals are centralized on K000 but is not a complete remote-Goal reader contract. [backend/app/services/goals.py#L575-L618](../../backend/app/services/goals.py#L575-L618)
- The documented fan-out readers are correct for a small number of shards, but the current implementation has no measured 100-shard latency, pool, or outage budget. [backend/app/services/shards.py#L437-L462](../../backend/app/services/shards.py#L437-L462) [backend/app/services/shards.py#L267-L321](../../backend/app/services/shards.py#L267-L321)

## 2. Target topology: abstract Goal anchors and distributed Procedures

### Takeaway
The recommended first target is a logical two-plane topology: K000 is the control plane and the mandatory canonical home for abstract Goals; public Procedures are deterministically distributed over 100 data shards by their stable Procedure identity, with versions, evidence, edges, and execution state remaining on the selected Procedure shard. Concrete Goals can remain centralized initially or receive a separate explicit placement policy; they must not be silently classified from an optional hierarchy edge. [backend/app/services/shards.py#L80-L92](../../backend/app/services/shards.py#L80-L92) [backend/app/services/shards.py#L149-L171](../../backend/app/services/shards.py#L149-L171) [backend/db/95_control_plane_shards_projections.sql#L83-L102](../../backend/db/95_control_plane_shards_projections.sql#L83-L102)

### Cited Findings
- **Reusable control-plane primitives:** stable object routes and version-row routes already distinguish logical Procedure identity from an individual version row. `home_pool(..., by_row_id=True)` uses `procedure_row_routes` for row-addressed reads and `object_routes` for stable-ID reads. [backend/db/95_control_plane_shards_projections.sql#L40-L50](../../backend/db/95_control_plane_shards_projections.sql#L40-L50) [backend/db/96_sharded_canonical_writes.sql#L44-L51](../../backend/db/96_sharded_canonical_writes.sql#L44-L51) [backend/app/services/shards.py#L80-L92](../../backend/app/services/shards.py#L80-L92)
- **Reusable placement primitive:** the existing HRW function is pure and accepts a caller-provided shard set. That makes it possible to pass exactly the 100 active data shards for Procedures while passing only K000 for centralized abstract Goals, without changing the hash algorithm. [backend/app/services/shards.py#L142-L171](../../backend/app/services/shards.py#L142-L171)
- **Reusable locality rule:** the current Procedure INSERT writes `achieves_goal_id` and `home_shard_id` together, so a central Goal reference and a distributed Procedure home can be represented in one canonical Procedure row once reference validation is made cross-database-safe. [backend/app/services/procedures.py#L374-L400](../../backend/app/services/procedures.py#L374-L400) [backend/app/services/procedures.py#L446-L451](../../backend/app/services/procedures.py#L446-L451)
- **Reusable reverse index shape:** `procedure_search_index` already stores `goal_id`, `procedure_row_id`, and `home_shard_id`; it can support candidate discovery, although it is a projection and must not be the only authoritative placement record. [backend/app/services/search_projection.py#L163-L199](../../backend/app/services/search_projection.py#L163-L199) [backend/app/services/search_projection.py#L109-L127](../../backend/app/services/search_projection.py#L109-L127)
- **Current cross-shard reference mechanism:** migration 96 replaces selected physical FKs with triggers that accept either a local object or a route, but the trigger queries the route table in the database where the write occurs. [backend/db/96_sharded_canonical_writes.sql#L18-L64](../../backend/db/96_sharded_canonical_writes.sql#L18-L64)
- **Current remote-route ownership:** migration 95 says routes and outbox entries for remote canonical objects are maintained by application code on the control database; the shard-side trigger deliberately returns without writing its local control tables. [backend/db/95_control_plane_shards_projections.sql#L268-L312](../../backend/db/95_control_plane_shards_projections.sql#L268-L312) [backend/app/services/shards.py#L235-L248](../../backend/app/services/shards.py#L235-L248)
- **Current hierarchy behavior:** identity resolution records proposed `SPECIALIZES` edges and does not require them for ingestion or retrieval. [backend/app/services/identity_resolution.py#L703-L715](../../backend/app/services/identity_resolution.py#L703-L715) [backend/app/services/identity_resolution.py#L851-L870](../../backend/app/services/identity_resolution.py#L851-L870)

### Inferences
- **Control plane (K000):** keep the shard registry, `object_routes`, `procedure_row_routes`, Goal identity/name indexes, identity decisions, hierarchy relations, search projections, projection outbox, and placement-intent/repair metadata together. Abstract Goals should be canonical K000 rows and should have an explicit invariant such as `placement_class = 'abstract_anchor'`. This uses the current control-plane boundary without duplicating canonical Goals on data shards. [backend/db/95_control_plane_shards_projections.sql#L16-L51](../../backend/db/95_control_plane_shards_projections.sql#L16-L51) [backend/db/95_control_plane_shards_projections.sql#L104-L134](../../backend/db/95_control_plane_shards_projections.sql#L104-L134)
- **Data plane (100 shards):** for each new public Procedure, generate the stable `procedure_id`, select `choose_shard(procedure_id, active_data_shards)`, and do not pass the abstract Goal's K000 home as a preferred shard. Keep the logical Procedure's versions, Procedure-targeted evidence, edges, execution-plan data, and lifecycle counters on that selected shard. This preserves the current version/evidence locality while removing Goal-locality placement. [backend/app/services/shards.py#L163-L171](../../backend/app/services/shards.py#L163-L171) [backend/app/services/procedures.py#L604-L710](../../backend/app/services/procedures.py#L604-L710) [backend/app/services/procedures.py#L818-L830](../../backend/app/services/procedures.py#L818-L830)
- **Goal reference anchors:** introduce a replicated, non-authoritative `goal_anchor_refs` (or equivalent) table on every data shard containing at least `goal_id`, authoritative `home_shard_id`, validity/status, and update generation. Install/update the anchor before a remote Procedure write; change `sl_ref_exists` to accept the local anchor. This is necessary because a PostgreSQL trigger on a remote database cannot read the K000 control database's `object_routes` table. [backend/db/96_sharded_canonical_writes.sql#L19-L40](../../backend/db/96_sharded_canonical_writes.sql#L19-L40) [backend/db/95_control_plane_shards_projections.sql#L286-L299](../../backend/db/95_control_plane_shards_projections.sql#L286-L299)
- **Procedure write sequence:** (1) resolve or create the abstract Goal on K000 and obtain its stable ID; (2) compute the Procedure shard from `procedure_id`; (3) reserve a durable placement intent and verify the Goal anchor on the target shard; (4) write the canonical Procedure/version and its local execution/evidence rows; (5) publish `object_routes`, `procedure_row_routes`, and the projection outbox entry; (6) retry or compensate from the durable intent. The current code already has pieces of steps 1, 2, 4, and 5, but its multi-database sequence is not a single transaction. [backend/app/services/goals.py#L413-L471](../../backend/app/services/goals.py#L413-L471) [backend/app/services/procedures.py#L303-L320](../../backend/app/services/procedures.py#L303-L320) [backend/app/services/procedures.py#L467-L477](../../backend/app/services/procedures.py#L467-L477)
- **Reverse routing:** add an authoritative control-plane index such as `(goal_id, procedure_id, procedure_row_id, home_shard_id)`, or add `goal_id` to `procedure_row_routes` with an appropriate index. A Goal-to-Procedure read should query that index, group row IDs by `home_shard_id`, and hydrate one batch per involved data shard; the existing projection remains a rebuildable/search optimization. [backend/db/96_sharded_canonical_writes.sql#L44-L51](../../backend/db/96_sharded_canonical_writes.sql#L44-L51) [backend/app/services/shards.py#L342-L384](../../backend/app/services/shards.py#L342-L384) [backend/app/services/search_projection.py#L316-L346](../../backend/app/services/search_projection.py#L316-L346)
- **Claims and other children:** if a Claim is evidence for a Procedure, place it with that Procedure; if it belongs only to an abstract Goal, keep it on K000; otherwise give it an explicit data-plane policy. This avoids accidentally sending private or purely abstract material to public shards while retaining locality for Procedure evidence. [backend/app/services/claim_identity.py#L183-L223](../../backend/app/services/claim_identity.py#L183-L223) [backend/app/services/shards.py#L39-L55](../../backend/app/services/shards.py#L39-L55)
- **Hierarchy placement:** treat `goal_relations` as a semantic/control-plane graph, not a hash input. A relation may make a Goal eligible to be an abstract anchor only after an explicit policy accepts that classification; it should not move an existing Procedure or change its stable route. This preserves the repository's current non-compensatory separation between semantic identity and physical storage. [backend/db/95_control_plane_shards_projections.sql#L83-L102](../../backend/db/95_control_plane_shards_projections.sql#L83-L102) [backend/app/services/identity_resolution.py#L833-L848](../../backend/app/services/identity_resolution.py#L833-L848)
- **Private/org data:** keep private and organizational Goals, Procedures, Claims, and associated product data on K000 under the existing privacy rule unless a separate data-protection decision changes it. The 100-shard distribution should default to public canonical knowledge only. [backend/app/services/shards.py#L39-L55](../../backend/app/services/shards.py#L39-L55) [docs/sharding.md#L72-L74](../../docs/sharding.md#L72-L74)

### Gaps
- **Cross-database reference blocker:** the current route-aware trigger's fallback reads the local `object_routes` table, while remote route maintenance is explicitly performed on the control database. The cited E2E test proves a remote Goal with a colocated remote Procedure, not a K000 Goal with a remote Procedure; the latter needs an anchor/replication mechanism before it can be considered supported. [backend/db/96_sharded_canonical_writes.sql#L19-L40](../../backend/db/96_sharded_canonical_writes.sql#L19-L40) [backend/db/95_control_plane_shards_projections.sql#L286-L299](../../backend/db/95_control_plane_shards_projections.sql#L286-L299) [backend/tests/test_sharded_writes_e2e.py#L88-L126](../../backend/tests/test_sharded_writes_e2e.py#L88-L126)
- The current schema has no explicit Goal placement class, no replicated Goal reference anchor, and no authoritative reverse Goal-to-Procedure route index. The available fields and tables support the design but do not implement it. [backend/db/95_control_plane_shards_projections.sql#L83-L102](../../backend/db/95_control_plane_shards_projections.sql#L83-L102) [backend/db/96_sharded_canonical_writes.sql#L44-L51](../../backend/db/96_sharded_canonical_writes.sql#L44-L51)
- The current placement API has one public shard set and one `weight`; it cannot independently express “K000 is the only writable Goal anchor but not a public Procedure target.” A data-shard role/capability or an explicit caller-supplied data-shard set is required. [backend/app/services/shards.py#L51-L55](../../backend/app/services/shards.py#L51-L55) [backend/app/services/shards.py#L149-L171](../../backend/app/services/shards.py#L149-L171)
- The note does not assume that all concrete Goals should move off K000. The repository has no current policy or measured benefit for that split, so centralizing all Goals first is the lower-risk migration boundary; remote concrete Goals can be a later, separately tested policy. [backend/app/services/goals.py#L413-L471](../../backend/app/services/goals.py#L413-L471) [backend/app/services/shards.py#L80-L92](../../backend/app/services/shards.py#L80-L92)

## 3. Migration, failure, and validation requirements

### Takeaway
The safe order is: define the central-Goal/anchor contract, make cross-database references and control-plane foreign keys safe, switch Procedure placement to a distinct data-plane pool, then add capacity/pool/observability controls and 100-shard proving tests. Changing placement first would expose the current local-FK, local-reader, route-validation, and fan-out assumptions before the target has a durable consistency model. ### Cited Findings
- **Existing reference migration:** migration 96 removes selected physical FKs and installs route-aware triggers, but the fallback remains a local-table lookup and the migration is explicitly application-level rather than a distributed constraint. [backend/db/96_sharded_canonical_writes.sql#L1-L15](../../backend/db/96_sharded_canonical_writes.sql#L1-L15) [backend/db/96_sharded_canonical_writes.sql#L53-L103](../../backend/db/96_sharded_canonical_writes.sql#L53-L103)
- **Product/economy Goal references:** migration 110 retargets Benchmark, Solution, Evaluation, submission, usage, and credit Goal columns to physical `goals(id)` foreign keys. Keeping those association/control tables on K000 is compatible with centralized Goals; moving them to data shards is not. - **Procedure references still have physical FKs:** `procedure_submissions.parent_procedure_row_id` and `procedure_row_id`, `procedure_usage_events.procedure_row_id`, and `credit_ledger_events.procedure_row_id` reference local `procedures(id)` rows. [backend/app/services/shards.py#L115-L121](../../backend/app/services/shards.py#L115-L121) [backend/app/services/shards.py#L267-L321](../../backend/app/services/shards.py#L267-L321) [backend/app/services/shards.py#L342-L384](../../backend/app/services/shards.py#L342-L384) [backend/app/services/shards.py#L437-L454](../../backend/app/services/shards.py#L437-L454)

- **No automatic rebalance:** changing a shard status stops new placements only; existing objects retain their stored homes, and the documentation describes this as the rollover lever rather than a rebalancer. - **Current proving coverage:** the sharded E2E tests cover remote Goal persistence, colocated Procedure/evidence, route hydration, private K000 placement, rollover, and cross-shard Goal merge. They do not exercise a central abstract Goal with a Procedure on a different shard or a 100-shard fan-out. ### Inferences
- **Migration phase 1 — policy and schema:** add an explicit abstract-anchor classification, a data-shard capability/role, a durable placement-intent state, and a replicated Goal-anchor table. Keep the existing `object_routes` and `procedure_row_routes`; add the reverse Goal-to-Procedure index rather than replacing stable-ID routing. [backend/db/95_control_plane_shards_projections.sql#L16-L51](../../backend/db/95_control_plane_shards_projections.sql#L16-L51) [backend/db/96_sharded_canonical_writes.sql#L44-L51](../../backend/db/96_sharded_canonical_writes.sql#L44-L51)
- **Migration phase 2 — reference safety:** publish a Goal anchor to the selected Procedure shard before canonical Procedure insertion, make the trigger recognize that anchor, and fail closed if the anchor cannot be verified. Add repair for stale/missing anchors and route rows to the existing outbox/verification model. [backend/db/96_sharded_canonical_writes.sql#L19-L64](../../backend/db/96_sharded_canonical_writes.sql#L19-L64) [backend/app/services/search_projection.py#L244-L287](../../backend/app/services/search_projection.py#L244-L287)
