# Merging (and Un-merging) Duplicate Nodes in a Hierarchical, Versioned Knowledge Graph

## Canonicalization patterns: union-find, redirects, sameAs, and reversibility in large KGs

### Takeaway
Every large production KG (Wikidata, MusicBrainz, Freebase, DBpedia) converges on the same shape: pick one node as the **canonical survivor**, move/copy data onto it, and leave the obsolete node as a **permanent redirect/tombstone** rather than deleting it — the ID itself becomes an alias, never reused. `owl:sameAs`, by contrast, is a cautionary tale: its strict logical transitivity turns identity links into an uncontrolled union-find that silently over-merges and explodes combinatorially, which is why DBpedia had to build a dedicated clustering/canonicalization layer on top of it instead of relying on RDF/OWL inference directly.

### Cited Findings
- Wikidata merge is "a multistep process that pools data about items together in one recipient item, finally resulting in the redirection of the obsolete page to the recipient item" — statements/sitelinks/labels are moved onto the recipient, then the loser becomes a redirect. — [Help:Merge](https://www.wikidata.org/wiki/Help:Merge)
- Wikidata policy: "Administrators should not delete one item and leave the other, but turn one into a redirect to the other. Under no circumstances should redirects be deleted or repurposed for another object" — item IDs are treated as permanent, stable identifiers even post-merge. — [Wikidata:Requests for comment/Redirect vs. deletion](https://www.wikidata.org/wiki/Wikidata:Requests_for_comment/Redirect_vs._deletion)
- Deleting instead of redirecting is only acceptable if the item is <24h old and provably unreferenced elsewhere — otherwise redirect is mandatory because "there might still be references to a merged item's id from within Wikidata or from other webpages." — [Help:Redirects](https://www.wikidata.org/wiki/Help:Redirects)
- Undoing a Wikidata merge requires restoring the recipient item's pre-merge state *first*, then the merged item's pre-merge state, in that specific order, because sitelinks can only point to one item at a time; complicating this, bots auto-rewrite statements pointing at the now-redirected item within ~24 hours, so full reversal may need bot-operator intervention. — [Help:Merge](https://www.wikidata.org/wiki/Help:Merge)
- MusicBrainz: "Merging is an edit that merges two (or more) MusicBrainz entities (of the same type) into one... All references to the merged entities will now be redirected to the 'target' entity," and the old MBIDs (identifiers) forward permanently to the surviving entity so old links/tags still resolve. — [Merge - MusicBrainz](https://musicbrainz.org/doc/Merge)
- MusicBrainz explicitly classifies merge as a "Destructive Edit, because some data can be lost" — i.e., the project accepts merge is lossy on some attributes even though identifiers are preserved via redirect. — [Merge - MusicBrainz](https://musicbrainz.org/doc/Merge)
- Freebase used stable "MIDs" (Machine IDs, `/m/xxxxx`) distinct from a topic's internal GUID specifically so that "MIDs play a critical role when topics are merged or split, allowing external applications to track the logical topic even though the physical Freebase identity... may change" — an explicit stable-id-plus-indirection layer decoupled from physical storage identity. — [Freebase API Basic Concepts](https://developers.google.com/freebase/guide/basic_concepts)
- Real-world friction: TMDb users found that "simply reassigning MIDs doesn't automatically consolidate all associated data from different sources" when trying to merge duplicate pages that used Freebase MIDs — indirection alone doesn't guarantee correct data consolidation. — [TMDb Talk: Merging duplicate person pages](https://www.themoviedb.org/talk/53c60dd70e0a267fea001bc9)
- `owl:sameAs` is defined as symmetric and transitive; a chain of N nodes linked by `sameAs` implies N² sameAs statements and causes every property of any one node to be inferred onto every other node in the chain — an explosion in both inferred triples and unintended property propagation. — [GraphDB: Ontology mapping with owl:sameAs](https://graphdb.ontotext.com/documentation/11.5/sameAs-background-information.html)
- DBpedia's own "ID Management" system computes **connected components** over incoming `owl:sameAs` assertions (i.e., literal union-find/transitive closure), picks one representative member per component as the **Cluster ID / Global Identifier**, and maps every cluster member's URI to that canonical URI — effectively building a canonicalization layer *on top of* raw sameAs rather than trusting live OWL inference. — [DBpedia dbp-same-thing-service](https://github.com/dbpedia/dbp-same-thing-service)
- Concretely, DBpedia's "Barack Obama" identity cluster contains 440 distinct URIs connected by 7,615 edges, compacted from 14,917 raw `owl:sameAs` statements — illustrating how noisy/redundant raw identity assertions get in practice at scale. — [DBpedia Technology Tutorial](https://ceur-ws.org/Vol-3064/DBpedia-Technology-tutorial.pdf)
- Survey finding: raw `owl:sameAs` links in DBpedia/Freebase-era linked data are "frequently unreliable or over-applied," and because manual verification of millions of links is infeasible, false equivalences cascade through downstream reasoning and applications ("the sameAs problem"). — [The sameAs Problem: A Survey on Identity Management in the Web of Data](https://arxiv.org/pdf/1907.10528)
- Proposed fixes in the literature: weaker, non-transitive predicates (`skos:closeMatch`, `rdfs:seeAlso`), confidence-weighted identity links, context-scoped identity (equivalent only under a stated perspective), explicit provenance for *why* two nodes were declared identical, and **post-hoc clustering** (discover equivalence classes via similarity, don't hard-assert them) rather than eagerly asserting `sameAs` triples that are hard to walk back. — [The sameAs Problem survey](https://arxiv.org/pdf/1907.10528)
- Entity-resolution engineering pattern (general, not KG-specific): pipeline is blocking → pairwise scoring → clustering, and clustering is commonly done via **transitive closure / connected components over pairs above a match threshold** (a MapReduce-style union-find), which is the same underlying mechanism as DBpedia's sameAs clustering. — [Entity Resolution at Scale (Modern Data 101)](https://www.moderndata101.com/blogs/entity-resolution-at-scale-deduplication-strategies-for-knowledge-graph-construction)

### Inferences
- The consistent pattern across Wikidata/MusicBrainz/Freebase is: **stable opaque ID + redirect/tombstone row**, never delete-and-repoint in place. This is directly transferable to a Goal-graph design: a merged Goal's row should become a redirect record pointing at the canonical Goal, and the id must never be reassigned to a new, unrelated Goal later.
- `owl:sameAs`'s failure mode — treating identity assertions as instantly-transitive, eagerly-inferred, irreversible logical facts — is the wrong model for a system that wants merges to be *reversible and auditable*. The DBpedia and general entity-resolution answer (compute connected components as a **separate, recomputable canonicalization step**, keep raw evidence separate from the derived canonical mapping) is the better fit: keep a `merge_edges` / evidence table of pairwise merge decisions, and derive the canonical-representative map from it, rather than mutating identity in place. This makes "unmerge" a matter of retracting one edge and recomputing connected components, not reversing a cascade of writes.
- Freebase's MID vs GUID split is the direct precedent for "stable id at the API/reference layer, decoupled from physical/storage identity" — relevant to a sharded design where a Goal's public id should not need to change even if its canonical shard or physical row changes on merge.

### Gaps
- None of the sources give the *algorithm* Wikidata/MusicBrainz use server-side to reconcile concurrent edits mid-merge (e.g., two editors merging the same pair simultaneously) — only the user-facing policy is documented.

## Keeping a DAG valid after merges: cycles, ancestor/descendant merges, multiple inheritance

### Takeaway
The literature on this specific sub-problem (merging two nodes where one is an ancestor of the other in a DAG) is thin and mostly buried in domain-specific papers (causal graphs, phylogenetics) rather than general graph-engineering docs; the closest general-purpose guidance is Neo4j/APOC's node-merge tooling, which unions relationships and leaves cycle-safety to the caller, plus scattered "identification-elimination" techniques from schema-matching literature that explicitly detect and break cycles introduced by a merge.

### Cited Findings
- Neo4j's `apoc.refactor.mergeNodes([node1, node2, ...], {config})` merges a list of nodes onto the first node in the list: "all relationships are merged onto that node too," with per-property merge strategies `overwrite`, `discard`, or `combine`, and a `mergeRels` option to also merge relationships of the same type/direction into one. — [apoc.refactor.mergeNodes docs](https://neo4j.com/docs/apoc/current/overview/apoc.refactor/apoc.refactor.mergeNodes/)
- In schema/ontology-merging engineering practice, directly merging matched input nodes into their identified anchor nodes "may introduce cycles, violating the acyclic property," which is why systems run an explicit "identification-elimination" pass to detect and prevent cycle formation as part of the merge step, rather than assuming merges are automatically DAG-safe. — [general search finding, cycle-prevention in DAG node merging]
- A standard technique for ancestor/descendant reasoning during such merges is precomputing a **topological order** and, for each node in that order, propagating an ancestor-set forward to its descendants — i.e., maintain ancestor sets incrementally so an ancestor/descendant check (needed to detect "merge would create a cycle") is O(1)-ish per query instead of a fresh traversal. — [Find ancestors of each node in a DAG](https://algo.monster/liteproblems/2192)
- Causal-DAG-merging work explicitly treats "eliminate cycles" as a distinct, final clean-up phase applied *after* merging sub-DAGs learned independently — i.e., cycle removal is not automatic from the merge operation itself and is handled as post-processing. — [Learning causal graphs using variable grouping according to ancestral relationship](https://arxiv.org/pdf/2403.14125)

### Inferences
- None of the general-purpose graph-DB tooling (Neo4j/APOC included) has a built-in "refuse to merge if it would create a cycle" guard — that check is the *caller's* responsibility. For a Goal DAG, this means the merge service itself must run an ancestor-check (is target an ancestor of source, or vice versa?) before committing, since off-the-shelf merge primitives will happily union edges and let a cycle appear.
- Merging a node with its own ancestor is conceptually a **different operation than deduplication** — it's a claim that two levels of a subgoal hierarchy collapse into one (a "hypernym"/generalization collapse), not "these are the same fact recorded twice." Systems should likely reject or special-case ancestor↔descendant merges (e.g., require an explicit `collapse_hierarchy` action with different semantics/audit trail from `merge_duplicate`), rather than routing them through the same union-find style merge as sibling-duplicate merges.
- Maintaining a live ancestor-set index (as in the topological-order technique above) is the practical way to make the pre-merge cycle check cheap in a system with many merges, rather than doing a full graph traversal per merge request.

### Gaps
- Could not find primary literature specifically about "multiple inheritance" handling under node merges in a DAG (i.e., a node acquiring two or more parents as a result of a merge, and what invariants a versioned KG should hold about that). This looks like a genuine gap in publicly documented practice — most production KG merge docs (Wikidata, MusicBrainz) don't have a strict single-parent DAG constraint to begin with, so they don't need to solve this.
- Could not find a canonical, widely-cited "transitive reduction after merge" algorithm write-up in the sources retrieved; this is a well-known general graph-theory operation but no source here ties it specifically to post-merge KG maintenance. Treat "run transitive reduction after a merge that unions parent/child edge sets" as an inference, not a sourced claim.

## Event-sourced / bi-temporal merge representation: append-only events, read-time vs eager rewriting, MDM survivorship, and reversal

### Takeaway
The most directly applicable, deeply-documented precedent found is a healthcare (FHIR) design for **patient-record merge/unmerge** that models a merge as an **event with an attached provenance record listing pre-merge versioned references** — this is architecturally very close to a bi-temporal, append-only ChangeSet system, and it explicitly confronts the "what changed after the merge but before the unmerge" problem, which any bi-temporal Goal-graph merge design will also face. MDM vendor systems independently converge on the same idea: merges are audited, policy-driven (survivorship rules), and unmerge is a first-class, policy-configurable operation — not a raw undo.

### Cited Findings
- FHIR's merge design uses "an event/replace-reference pattern": the client submits a full transaction Bundle of every PUT/POST/DELETE the merge requires; the server wraps it in a `Task` + `Provenance` record and executes it atomically. The `Provenance.entity[].what` field stores **versioned references to the pre-merge state** (e.g., `Patient/anna-old/_history/2`), which is exactly the "close the old validity window, append new row, but keep a pointer back" bi-temporal idea. — [Designing $unmerge: Reversing the FHIR Patient Merge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- Unmerge is explicitly **not** "replay the merge transaction backwards": the client supplies a fresh reversal transaction Bundle (a *policy decision*, not a mechanical inverse), and the server validates + applies it atomically using optimistic-concurrency `ifMatch` headers, then records a new audit Provenance — "the unmerge does not invalidate the merge's audit trail; it builds on top of it." Both merge and unmerge Provenance records coexist permanently. — [Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- The central hard problem this design surfaces — directly relevant to any bi-temporal merge system — is the **"temporal gap"**: data written to the surviving/target node *after* the merge but *before* an unmerge has no corresponding pre-merge state to fall back to (e.g., "three Encounters posted to the target patient after merge but before unmerge have no counterpart on the source... the server cannot determine clinically which patient actually had these visits"). The FHIR design resolves this by making the client choose, per unmerge, across four explicit policy axes rather than trying to auto-resolve it. — [Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- The four policy axes it defines: (1) **field reassignment** — where do new attribute values added post-merge go on unmerge (default: stay on the surviving/target record, flagged for steward review); (2) **reference reassignment** — do new incoming references created after the merge move back to the source or stay on target; (3) **source restoration** — if the losing record was hard-deleted at merge time, either restore its original id (accepting a version gap), mint a new id with a mapping recorded in Provenance, or refuse the unmerge outright; (4) **downstream re-evaluation** — anything derived/recomputed during the merged period (aggregates, caches, cohort membership) "can no longer be trusted without review," so downstream consumers subscribe to `Task?code=unmerge` events to trigger recomputation. — [Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- The design supports a `preview: true` dry-run mode that returns the would-be `OperationOutcome` and resulting Provenance before the unmerge is actually authorized/committed — a pattern worth adopting for any high-stakes graph-merge operation. — [Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- Optional `Linkage` resources with a "do-not-merge" extension can be posted atomically alongside an unmerge to prevent the same pair from being silently re-merged by an automated matcher afterward. — [Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- MDM survivorship: "survivorship refers to the process of determining which data values should be retained... when conflicting or duplicate data records are merged," typically combining multiple strategies rather than one rule alone — **source-system trust** (prioritize the more-reliable source for a given attribute), **recency** (most recently updated value wins), **frequency** (value appearing most often across source systems wins), and **completeness** (prefer the more fully-populated record) — these rules are set by data governance, not automatically inferred. — [Profisee: MDM Survivorship](https://profisee.com/blog/mdm-survivorship/)
- Informatica MDM's `Unmerge Records` API "unmerges a root record into the individual root records that existed before the records were merged," explicitly restores all foreign keys that were repointed at merge time, and supports **cascade unmerge**: "when records in the parent object are unmerged, Informatica MDM Hub also unmerges affected records in the child base object" if cascade unmerge is enabled — i.e., unmerge is designed to propagate through a parent/child object hierarchy automatically when configured to. — [Informatica: Unmerge Records](https://docs.informatica.com/master-data-management/multidomain-mdm/10-5-hotfix-2/business-entity-services-guide/rest-business-entity-service-calls/rest-api-reference-for-business-entity-services/unmerge-records.html)
- General MDM design principle surfaced in search: "entity cleanup must be user-visible and reversible. If the system merges entities, the user must see why, accept/reject/edit it, and undo or split later" — merge/split decisions should be persisted as first-class audit records (source ids, target canonical id, reason, confidence, run/stage, approval state), not just destructive field overwrites. — [search synthesis citing MDM/entity-audit practice, fichero issue #1675](https://github.com/dtubb/fichero/issues/1675)

### Inferences
- The FHIR `Provenance.entity[].what` pattern (store a *versioned pointer* to the pre-merge state of each touched resource, inside the same event that performs the merge) maps directly onto "an update closes the old validity window and appends a new row": a Goal-merge ChangeSet should record, for every row it closes (Goal, Procedure, Evidence, routing stats, search index entry), the closed row's own bi-temporal version identifier — not just "this row was affected" — so an unmerge can precisely re-open exactly those versions rather than guessing.
- Read-time resolution through a canonical map (rather than eager, permanent rewriting of every reference) is what makes reversal tractable: if children/procedures/evidence still logically reference the *original* Goal id, and a canonical-lookup redirect table resolves reads to the current representative, then unmerging is "delete one row from the redirect table" instead of "walk every foreign key and rewrite it back." Eager rewriting (as MusicBrainz/Wikidata do, physically re-pointing every reference during the merge) is simpler to reason about at read time and matches how those systems' UIs work, but it is exactly what creates the FHIR "temporal gap" problem — new data written after an eager rewrite has no way to know it should have pointed at the pre-merge id. A **hybrid** — eager rewrite for the common/read-hot case, but always resolvable through a canonical map that is itself append-only and versioned, so any given point in time can be reconstructed — reconciles the "cascade simply" requirement (readers don't need to know about history) with the "reversible" requirement (the map is just data, and closing a canonical-map row is a normal bi-temporal update).
- The FHIR four-policy-axis structure is a strong template for a Goal-merge design doc: explicitly define (a) what happens to Procedures/Evidence/routing-stats *created after* the merge when computing an unmerge, (b) what happens to *new* Procedure/Evidence attachments that pointed at the canonical Goal post-merge, (c) whether merging hard-deletes vs. tombstones the loser Goal (the system's own "nothing is deleted" rule argues strongly for tombstone-only, sidestepping FHIR's hardest case), and (d) which derived aggregates (per-Goal capability/evidence scores, search index, routing statistics) must be flagged stale and recomputed on unmerge rather than trusted.
- Because this system already tombstones-not-deletes by design (per the system's bi-temporal invalidate-and-append rule), it structurally avoids FHIR's worst case (source hard-deleted at merge, forcing a choice between id-reuse and version-gap-acceptance on unmerge) — the source Goal row can simply have its validity window re-opened on unmerge, with a new row, same as any other bi-temporal correction. This is a genuine simplification available to this system that FHIR's general patient-merge design does not have.
- MDM cascade-unmerge (Informatica) is the precedent for "un-merging must propagate to child/attached objects" — directly analogous to needing Procedures/Evidence/subgoals to be un-repointed when a Goal-merge is reversed, and argues for making that cascade *configurable/optional* rather than assumed, since not all attached data may need to move back.

### Gaps
- Could not find primary-source detail on exactly how FHIR (or any surveyed system) treats the "downstream re-evaluation queue" mechanically at implementation level (e.g., is it a durable outbox, a subscription/webhook, a batch reconciliation job?) beyond "downstream consumers watch `Task?code=unmerge` subscriptions." Treat the mechanism as under-specified in the source.
- General event-sourcing/CQRS literature (Context Mapper, InfoQ Microservices articles) discusses "Merge Aggregates" as a named DDD refactoring pattern and aggregate/event-stream boundaries in general, but none of the retrieved sources gave a concrete worked example of merging two aggregate instances (as opposed to merging two bounded-context models at design time) with reversal — this is a gap; the FHIR case study above is a much stronger source for the actual instance-merge problem than generic CQRS literature.

## Cascading derived data: search indexes, aggregate statistics, caches; idempotent recomputation

### Takeaway
None of the sources found speak directly to "recomputing per-node aggregate statistics after a KG merge," but the adjacent, well-sourced material (MDM survivorship, FHIR's downstream-re-evaluation axis, DBpedia's cluster recomputation) converges on one principle: **treat every derived/aggregate value as invalidatable and recomputable from the append-only source-of-truth log, never as data that itself gets hand-patched during a merge.**

### Cited Findings
- FHIR unmerge design flags exactly this category explicitly as its fourth policy axis: "anything built during the merged period (re-derived radiation dose, recomputed cohort membership, third-party caches) can no longer be trusted without review" post-unmerge, and the proposed mechanism is downstream consumers subscribing to merge/unmerge task events to trigger their own recomputation rather than the merge operation itself trying to patch every derived value. — [Designing $unmerge](https://www.health-samurai.io/articles/designing-unmerge-fhir-patient)
- DBpedia's cluster/canonical-ID assignment is described as a batch computation over the full set of `owl:sameAs` input edges (connected components → representative selection) run as part of each release cycle, rather than incrementally patched in place — i.e., the canonical mapping itself is a derived, recomputable artifact, not hand-edited. — [DBpedia dbp-same-thing-service](https://github.com/dbpedia/dbp-same-thing-service); [DBpedia Technology Tutorial](https://ceur-ws.org/Vol-3064/DBpedia-Technology-tutorial.pdf)
- MDM survivorship rules (source-trust, recency, frequency, completeness) are themselves the mechanism for "correctly combining counts/values from merged records" in that domain — i.e., the merge doesn't simply sum/concatenate; a governed rule decides which value or combination survives per attribute. — [Profisee: MDM Survivorship](https://profisee.com/blog/mdm-survivorship/)

### Inferences
- For a "per-goal model performance evidence" style statistic, the FHIR/DBpedia pattern implies: don't try to arithmetically merge two precomputed aggregates at merge time (e.g., don't naively sum two success-rate numerators/denominators inline as part of the merge transaction, since this is fragile and hard to invalidate). Instead, mark the aggregate as stale for the canonical Goal, and recompute it from the underlying Evidence rows (which — by the bi-temporal design — already carry `target_version`/Goal-id provenance) using the same aggregation logic used everywhere else. This makes the recomputation idempotent (rerunning it is safe) and automatically correct after an unmerge, since it will simply see fewer/different Evidence rows once the canonical map changes back.
- Search-index entries and routing statistics should be treated the same way: the merge ChangeSet enqueues a re-index/re-route job keyed on the canonical Goal id (and, for unmerge, on both the reopened source id and the target id), rather than the merge transaction itself trying to synchronously patch index documents. This is consistent with "idempotent re-computation" being the safety property to design for, since retries, races, and partial failures during a merge cascade are inevitable at scale.

### Gaps
- No primary source found that specifically documents idempotency techniques for search-index cascade-on-merge (e.g., Elasticsearch/Lucene re-indexing on entity merge) or routing-statistics recomputation in a KG context. This appears to be an implementation detail vendors don't publish; treat "recompute from source-of-truth Evidence log, keyed by canonical id, triggered by the merge ChangeSet" as an inference/design recommendation, not a sourced fact.

## Distributed/sharded graphs: merging nodes across shards, routing stability

### Takeaway
Sourced material on sharded *graph* databases specifically merging cross-shard nodes is very thin; general sharded-database routing-table mechanics were found, but nothing graph-specific and nothing about the merge operation itself crossing shard boundaries. This is the weakest-sourced section of the survey — flag it as a genuine literature gap for the report writer.

### Cited Findings
- General sharded-database pattern: a central "shard catalogue" / router maintains a **routing table** mapping shard-key ranges/values to the physical shard holding that data, and clients/queries consult this routing table to locate the right shard; most sharded systems are shared-nothing (each shard is a fully independent node). — [Database Sharding Explained (Aerospike)](https://aerospike.com/blog/database-sharding-scalable-systems/); [MongoDB: Routing with mongos](https://www.mongodb.com/docs/manual/core/sharded-cluster-query-router/)
- For cross-shard aggregation queries specifically, systems like MongoDB designate a "merge" step that runs on a selected shard (or a dedicated router) to combine partial results from multiple shards — this is a query-time merge of *results*, not a merge of two persistent graph nodes across shards. — [Database Sharding Explained (Aerospike)](https://aerospike.com/blog/database-sharding-scalable-systems/)
- Freebase's MID (stable logical id) vs. GUID (physical identity) split is again the closest precedent found for "a reference should stay valid even if the referenced thing's physical location/identity changes," which is the essential requirement for cross-shard node merges. — [Freebase API Basic Concepts](https://developers.google.com/freebase/guide/basic_concepts)

### Inferences
- Given the system's own described architecture (goals placed on shards by id; a control DB holds a search index, object routes, goal names, and goal relations), a cross-shard merge is naturally handled as: (1) the control DB's object-routes table is the canonical "routing table" analogous to the sharded-DB catalogues found above; (2) a cross-shard merge only needs to update *one row* in that control-DB routing table (repoint the loser's route to resolve through the canonical id, or mark it a redirect) rather than physically moving data between shards; (3) the shard holding the loser Goal's row can be left untouched (its data stays where it is — the row becomes a tombstone/redirect in place), while all *new* reads/writes for that id get resolved to the canonical Goal via the control-DB route — this mirrors Wikidata's "the obsolete item becomes a redirect; never physically delete or move it" pattern, applied at the routing-table layer instead of within a single shard.
- This design would mean a cross-shard merge never requires cross-shard transactions for the bulk of attached data (Procedures/Evidence keep living on their original shard, referenced via the stable Goal id) — only the control-DB route/redirect entry and the two shards' own Goal-tombstone/Goal-redirect rows need to change, which is a small, boundable write-set and therefore easier to make atomic and reversible than a full cross-shard data migration.

### Gaps
- No primary source (vendor docs, papers) was found specifically discussing merging two *first-class graph nodes* that live on different physical shards in a graph database (Neo4j Fabric, TigerGraph, JanusGraph, etc.) — searches surfaced only generic relational/document-DB sharding routing mechanics. If the report needs a stronger citation here, a follow-up search specifically against Neo4j Fabric / TigerGraph / JanusGraph distributed-graph documentation is recommended (not covered in this pass).
- No source was found on how routing-table updates for a cross-shard merge are made atomic/consistent with the underlying shard state (e.g., two-phase commit vs. eventual consistency with a reconciliation job) — flagged as unresolved.

## Ontology/taxonomy merging literature and procedural/task-hierarchy-specific work

### Takeaway
Ontology *alignment* (matching before merging) is a mature academic subfield with a standard three-phase decomposition — match, merge, repair — and well-known technique families (terminological, structural, extensional, semantic), but no source found specifically addresses merging **procedural/task/skill hierarchies** (e.g., WikiHow-style how-to graphs) as a distinct sub-problem; this looks like a genuine literature gap rather than a search failure, and should be reported as such.

### Cited Findings
- The ontology-integration community standardly splits the problem into three sub-tasks: **matching** (find correspondences) as a necessary precursor to **merging** (produce one coherent combined ontology), with **repairing** either folded into matching or done as a separate step afterward. — [Survey on the literature of ontology mapping, alignment and merging (IEEE)](https://ieeexplore.ieee.org/document/6216651/)
- Ontology-alignment techniques are typically categorized as terminological (string/label similarity), structural (graph-topology similarity), extensional (instance-overlap similarity), and semantic (logic-based); iterative alignment algorithms tend to be more accurate but substantially more expensive than single-pass methods, and combining multiple similarity measures (as in systems like CtxMatch, S-Match, LogMap) generally outperforms any single measure. — [Ontology-Alignment Techniques: Survey and Analysis](https://www.researchgate.net/publication/288683728_Ontology-Alignment_Techniques_Survey_and_Analysis)
- A "target-driven" taxonomy-merging approach exists specifically for combining taxonomies for text-mining/classification purposes using a combined matching strategy — an example of taxonomy-specific (not just generic ontology) merge work, though not focused on task/procedure hierarchies. — [Target-driven merging of Taxonomies](https://arxiv.org/pdf/1012.4855)

### Inferences
- The match→merge→repair decomposition from ontology-alignment literature maps cleanly onto a practical Goal-merge pipeline: (1) a matching/candidate-detection stage (embedding similarity, string similarity, structural similarity of subgoal neighborhoods — directly reusing "terminological/structural/extensional" technique families) that *proposes* merge candidates; (2) the merge operation itself (the mechanics covered in the other sections of this report); (3) an explicit repair pass (the cycle-check / transitive-reduction / redirect-consistency work covered above) run either inline or as a follow-up audit.
- The complete absence of literature specifically on merging procedural/task/skill/how-to hierarchies (WikiHow-style DAGs) suggests this system's Goal-merge design is closer to novel/unopened territory than to a solved problem with an off-the-shelf recipe — general ontology-merge and MDM/KG-merge patterns are the best available transferable precedent, but none of them were built for a hierarchy whose nodes carry attached versioned Procedures/Evidence with capability scores, which is this system's distinguishing complexity.

## Overall design recommendations for this system (synthesis across all sections)

1. **Canonical representative + permanent redirect, never delete or reuse an id** (Wikidata/MusicBrainz/Freebase pattern). A merged Goal's row becomes a tombstone/redirect row pointing at the canonical Goal id; this is a natural fit for the system's existing bi-temporal invalidate-and-append rule — merging *is* just another kind of validity-window closure.
2. **Represent the merge as a ChangeSet event carrying versioned pre-merge pointers** for every row it touches (Goal, Procedure, Evidence, routing-stat, search-index entry, shard route) — the FHIR `Provenance.entity[].what` pattern — so an unmerge can precisely reopen exactly those versions instead of guessing.
3. **Keep the canonical mapping as its own append-only, recomputable table** (a union-find-derived table, à la DBpedia's cluster/representative computation), separate from eager reference-rewriting. Reads resolve through this table; an unmerge is "close this map row's validity window," not "reverse N writes."
4. **Reject or special-case merges between a node and its own ancestor/descendant** — this is conceptually a hierarchy-collapse ("hypernym"), not deduplication, and should not go through the same code path; require an explicit ancestor/descendant check before any merge commits, backed by a maintained ancestor-set index for cheap checking.
5. **Never arithmetically combine aggregates in place at merge time.** Mark derived data (capability scores, search-index entries, routing statistics) stale for the canonical id and recompute from the underlying Evidence/ChangeSet log — idempotent, safe to rerun, and automatically correct after an unmerge.
6. **Define explicit, named policies (not silent defaults) for the FHIR-style "temporal gap"**: what happens to Procedures/Evidence/children attached *after* a merge, if that merge is later undone. Since this system tombstones rather than hard-deletes, it can sidestep FHIR's worst case (id-reuse vs. version-gap) by simply reopening the source Goal's validity window on unmerge — a structural advantage over the FHIR precedent worth calling out explicitly in the design doc.
7. **For sharding**: treat the control DB's object-routes table as the single source of truth for merge/redirect state; a cross-shard merge should only require a small, boundable write to that table plus a tombstone row on each shard — not a cross-shard data migration — keeping the merge's blast radius small and its reversal cheap.
8. **Borrow the match → merge → repair structure from ontology-alignment literature** as the top-level pipeline shape, and budget for building novel tooling for the procedural/capability-scoring aspects, since no surveyed literature covers merging task/skill hierarchies with attached versioned evidence — this is this system's genuinely unsolved corner.
