# Canonicalizing and Deduplicating Benchmark Tasks Across Suites, and Mapping to a Goal/Skill Taxonomy (2020-2026)

## Cross-benchmark overlap and near-duplicate detection: exact keys, MinHash/LSH, n-gram, embedding, AST/code-clone

### Takeaway
The field has converged on a layered detection stack — exact key matching (repo + commit/instance id) for structurally identical tasks, MinHash/LSH and n-gram overlap for textual near-duplicates and train-test contamination, and embedding/AST-based clone detection for semantically or syntactically similar solutions — but there is no single tool applied uniformly across the SWE-bench-family or DS-1000/BigCodeBench/HumanEval ecosystems; most documented overlap numbers come from the papers introducing each successor dataset, not from an independent third-party audit, so overlap coverage across the full ingestion list is incomplete.

### Cited Findings
- SWE-rebench (and SWE-rebench V2) use `instance_id` as a unique task identifier for a commit pair, `repo` in canonical owner/name form, and `base_commit` as the pre-fix commit SHA; the pipeline asserts `df.instance_id.is_unique` on released parquets and a `git rev-parse HEAD == base_commit` check at image build time, i.e., `(repo, base_commit)` functions as the canonical identity key for dedup/build correctness — [SWE-rebench paper](https://arxiv.org/pdf/2505.20411); [nebius/SWE-rebench-V2 dataset card](https://huggingface.co/datasets/nebius/SWE-rebench-V2).
- SWE-rebench's stated contamination-control method is temporal filtering: it collects GitHub issues created *after* a given model's training cutoff rather than deduplicating text after the fact; scores for some models dropped sharply once memorization could no longer help, evidencing that earlier SWE-bench-family scores were partly memorization-driven — [SWE-rebench paper](https://arxiv.org/pdf/2505.20411).
- Multi-SWE-bench (ByteDance-Seed, 7 languages: Java, TypeScript, JavaScript, Go, Rust, C, C++; 1,632 instances curated from 2,456 candidates by 68 expert annotators) reports explicit overlap accounting against other benchmarks by repository identity: "five repository identities overlap with generalization benchmarks, covering 17 evaluation instances: three DeepSWE instances and 14 SWE-bench Multilingual instances" — [Multi-SWE-bench / SWE-smith-adjacent search result, citing the paper](https://github.com/multi-swe-bench/multi-swe-bench); dataset card at [ByteDance-Seed/Multi-SWE-bench (HF)](https://huggingface.co/datasets/ByteDance-Seed/Multi-SWE-bench).
- SWE-smith (50,137 synthetic task instances from 128 GitHub repos) is generated via a synthesis toolkit rather than mined 1:1 from real issues, which changes the dedup problem: instances are the same "seed" repo but different injected bugs, so exact-key (repo+commit) collisions with SWE-bench/SWE-Gym are expected and must be handled differently from accidental duplication — [SWE-smith paper](https://arxiv.org/pdf/2504.21798); [SWE-bench/SWE-smith dataset card](https://huggingface.co/datasets/SWE-bench/SWE-smith).
- SWE-Gym (491 full-size / SWE-Gym Lite 230 instances) draws from repos with tasks reported as "on average harder than those in SWE-bench," and ships companion repos `SWE-Gym/SWE-Bench-Fork` and `SWE-Gym/SWE-Bench-Package`, signaling shared lineage/tooling with SWE-bench's collection pipeline (forked repo snapshots) rather than independently-sourced repos — [SWE-Gym paper](https://arxiv.org/pdf/2412.21139); [SWE-Gym/SWE-Bench-Fork](https://github.com/SWE-Gym/SWE-Bench-Fork).
- No source found in this pass gives a direct, numeric SWE-Gym-vs-SWE-smith or SWE-Gym-vs-SWE-bench-extra overlap count; both papers describe pipeline lineage but not a measured instance-level overlap percentage — gap (see below).
- Contamination-detection literature standard practice: **n-gram overlap** is the dominant practical method — GPT-3's paper used a 13-gram overlap threshold, GPT-4's report used a 50-character overlap threshold, and "token- and word-level n-gram matching is the standard decontamination tool used in modern LLM training" — [Rethinking Benchmark and Contamination for Language Models with Rephrased Samples](https://arxiv.org/pdf/2311.04850); summarized via search in [Inference-Time Decontamination paper](https://arxiv.org/pdf/2406.13990).
- **MinHash+LSH** is described as the most popular scalable near-duplicate text-deduplication technique in LLM data pipelines, adopted by Qwen, CodeParrot, SantaCoder, StarCoder, and StarCoder v2; at scale (100B tokens) MinHash-LSH on a 96-core CPU cluster takes "multiple weeks," motivating GPU-accelerated alternatives — [LSHBloom: Internet-Scale Text Deduplication](https://arxiv.org/html/2411.04257v4); corroborated via search summary citing multiple sources.
- Both n-gram and MinHash decontamination have known failure modes: **false positives** (over-aggressive filtering that removes legitimately non-contaminated data, hurting generalizability) and **false negatives** (paraphrase/rephrase attacks evade n-gram matching, understating true contamination) — [Rethinking Benchmark and Contamination for Language Models with Rephrased Samples](https://arxiv.org/pdf/2311.04850).
- **LessLeak-Bench** (arXiv 2502.06215) is a first systematic investigation of data leakage across 83 software-engineering benchmarks; it reports language-level average leakage ratios of 4.8% (Python), 2.8% (Java), 0.7% (C/C++), and calls out extreme per-benchmark leakage: QuixBugs at 100.0% and BigCloneBench at 55.7% — [LessLeak-Bench](https://arxiv.org/pdf/2502.06215). The paper's methodology section (per search summaries) combines exact matching, n-gram analysis, embedding-based semantic similarity, and MinHash — but this agent could not extract the exact per-technique thresholds or the SWE-bench-specific overlap number from the PDF/abstract fetch; treat method-to-number mapping as unverified pending a direct read of the full paper.
- **The SWE-Bench Illusion** (arXiv 2506.12286, ICSE-SEIP / Microsoft Research) diagnoses memorization rather than deduplication directly, but its method is relevant to canonicalization: it probes whether models can name the buggy file path or reproduce the ground-truth function from the issue text alone, without repo access. Models hit up to 76% file-path accuracy on SWE-Bench-sourced repos vs. up to 53% on repos outside SWE-Bench; verbatim 5-gram reproduction of the fix function reached up to 35% on SWE-Bench Verified/Full vs. up to 18% on other coding benchmarks — [The SWE-Bench Illusion](https://arxiv.org/abs/2506.12286); [Microsoft Research listing](https://www.microsoft.com/en-us/research/publication/the-swe-bench-illusion-when-state-of-the-art-llms-remember-instead-of-reason/).
- A separate 2026 study, "Does SWE-Bench-Verified Test Agent Ability or Model Memory?", found "32.67% of successful patches involved solution leakage, with solutions directly present in issue text or comments" — [arXiv 2512.10218](https://arxiv.org/html/2512.10218v2) (found via search; not independently fetched in full — treat the 32.67% figure as reported-by-abstract, not independently verified against full text).
- HumanEval/MBPP-family: EvalPlus's HumanEval+ adds "80x more tests" and MBPP+ adds "35x more tests" than the originals to close false-negative gaps in the base test suites (a quality/verification axis, distinct from cross-suite dedup) — [EvalPlus Leaderboard](https://evalplus.github.io/leaderboard.html); [On Leakage of Code Generation Evaluation Datasets](https://arxiv.org/html/2407.07565v1) reports 65.4% of MBPP test-set instances flagged contaminated by a leakage-detection tool, and separately reports HumanEval (0.0988%) and MBPP (0.0878%) "source overlap" against large permissive code corpora (a weaker signal than direct test-set leak) — same source.
- MBPP/MBPP+ provenance chain: both MBPP and MBPP+ draw from a 399-task hand-verified subset of the 427-task "MBPP-sanitized" set, itself a curated subset of the original ~1,000-task MBPP — [search summary citing EvalPlus/MBPP+ sources](https://evalplus.github.io/leaderboard.html).
- Code-clone/near-duplicate detection for solutions and tests: standard technique families are (a) token/string-level near-duplicate detectors (e.g., Microsoft's open-sourced near-duplicate code detector, tokenizer-based, extended across Java/JS/C#/Python), (b) AST-based structural comparison (extracting syntactic structure, then density-based clustering to find near/exact duplicates), and (c) learned/graph approaches — GCN over AST graphs with hierarchical differential pooling, and hybrid BERT+AST-LSTM models (e.g., "MulCode") — for semantic clone detection. **BigCloneBench** and **OJClone** are the standard public evaluation datasets for this literature — [Code Clone Detection with Hierarchical Attentive Graph Embedding](https://www.worldscientific.com/doi/10.1142/S021819402150025X); [Gitor: Scalable Code Clone Detection by Building Global Sample Graph](https://arxiv.org/pdf/2311.08778); search summary on near-duplicate GitHub code and Microsoft's detector.
- LiveCodeBench avoids overlap/contamination detection entirely by construction: it timestamps problems by original contest release date (LeetCode/AtCoder/Codeforces) and evaluates each model only on problems released after that model's training cutoff, showing visible score drops after the cutoff for models like DeepSeek, GPT-4o, and Claude — [LiveCodeBench paper](https://arxiv.org/pdf/2403.07974); [LiveCodeBench leaderboard](https://livecodebench.github.io/leaderboard.html).

### Inferences
- For the ingestion pipeline's purposes, `(repo, base_commit)` (or `(repo, instance_id)` where instance_id already encodes the commit/PR) is the correct **first-pass exact key** across the whole SWE-bench family (SWE-bench, Verified, Lite, Pro, SWE-rebench, SWE-rebench V2, SWE-Gym, Multi-SWE-bench) since every major dataset in this family already publishes these fields and at least one paper (Multi-SWE-bench) demonstrates using repository identity as the basis for overlap accounting against sibling benchmarks.
- SWE-smith is the outlier: because it *synthesizes* bugs on top of shared base repos, `(repo, base_commit)` will collide with SWE-bench/SWE-Gym instances that share a seed repo even when the actual task (injected bug + fix) is distinct. A second-tier key (problem/patch hash of the diff, or of the FAIL_TO_PASS test set) is needed to distinguish "same repo, different synthetic task" from "same repo, same real issue."
- Because MinHash/LSH is expensive at pretraining-corpus scale but the ingestion pipeline's corpus (curated benchmark task text, not full pretraining data) is orders of magnitude smaller, MinHash/LSH over problem statements + solution patches is tractable here even though it's a bottleneck in the LLM-pretraining-decontamination literature.
- The documented overlap-detection precedent (Multi-SWE-bench vs. DeepSWE/SWE-bench Multilingual, both by repository identity) suggests the same technique — set-intersect on canonical repo id — is the cheapest way to get partial-credit dedup evidence across the ingestion list even before running any n-gram/embedding pass.
- Given SWE-Bench Illusion's and the 32.67%-leakage paper's findings, a "verified solution" ingested from SWE-bench Verified should be flagged with a contamination-risk provenance tag distinct from a "freshly collected, post-cutoff" task (SWE-rebench-style), since the two have measurably different memorization risk even when the surface task looks identical.

### Gaps
- No paper found gives a direct, numeric instance-level overlap count between SWE-Gym and SWE-smith, or between SWE-bench-extra and SWE-rebench/SWE-rebench V2 — these are exactly the pairs most relevant to the ingestion list and require either reading the SWE-smith/SWE-Gym papers' dataset-construction sections in full or running the dedup pipeline directly.
- LessLeak-Bench's precise per-technique methodology (which threshold triggers exact vs. n-gram vs. embedding vs. MinHash classification, and whether SWE-bench specifically appears in its 83-benchmark leakage table with a number) could not be extracted from the PDF/abstract fetch in this pass — the tool's text extraction failed on embedded figures/tables. A follow-up direct read of the HTML or a table-focused fetch of arXiv 2502.06215 is needed.
- No source found quantifies DS-1000/BigCodeBench overlap with HumanEval/MBPP at the individual-problem level (only cross-corpus contamination percentages for HumanEval/MBPP against pretraining text were found, not the DS-1000/BigCodeBench axis).
- No primary source found for Terminal-Bench's task-identity scheme or documented overlap with any other suite in this list.

## Task/skill taxonomies for coding: benchmark-specific categorizations, capability ontologies, skill annotation

### Takeaway
Per-benchmark taxonomies already exist and are usable as seed vocabularies (DS-1000's library/perturbation-type axis, BigCodeBench's domain/library/function-call axis, SWE-bench Verified's difficulty-by-fix-time axis), but there is no single cross-benchmark skill ontology in the literature that already spans SWE-bench-style repo tasks and DS-1000/BigCodeBench-style function-call tasks; general-purpose LLM capability taxonomies (2026) are the closest thing to a unifying scheme but are not coding-specific or benchmark-validated against this task list.
### Cited Findings
- **DS-1000** structures its 1,000 data-science problems along a **library axis** (covers NumPy, Pandas, Matplotlib, and other popular data-science libraries; problems are organized per-library) and a **perturbation-type axis** with four settings: *Origin* (original problem + tests + eval function), *Surface Perturbation* (question/code context paraphrased, reference solution unchanged), *Semantic Perturbation* (reference solution's semantics changed, difficulty held constant), and *Difficult Rewrite* (harder variants) — designed specifically to prevent solution recall via perturbation rather than only via train/test separation; e.g. on numpy-100, Codex-002 scored 72.5% (Origin) → 50.8% (Surface) → 23.6% (Semantic) — [DS-1000 paper](https://arxiv.org/pdf/2211.11501); [project site](https://ds1000-code-gen.github.io/).
- **BigCodeBench** organizes 1,140 tasks by **723 distinct function calls drawn from 139 libraries across 7 domains**; each function call is assigned to a domain-specific library, and per-task domain distribution is computed from the frequency of domain-specific libraries invoked. Reported domain-level capability gaps: models are comparatively strong in "computation and cryptography" domains and weak in "networking" — [BigCodeBench paper](https://arxiv.org/html/2406.15877v2); [ICLR 2025 proceedings version](https://proceedings.iclr.cc/paper_files/paper/2025/file/a6a90bcc2aa470c3871b2d39a67d26e8-Paper-Conference.pdf). Overall LLM top score is ~60% vs. 97% human performance on the "complex instructions + precise multi-function-call composition" task format.
- **SWE-bench Verified**'s taxonomy axis is difficulty-by-estimated-fix-time rather than a skill/domain label: annotators (93 experienced Python developers) rated each of 1,699 candidate samples, producing an "easy" bucket of 196 tasks estimated at <15 minutes to fix and a "hard" bucket of 45 tasks estimated at >1 hour; annotation also used severity-graded criteria (0-3 scale) on problem-statement clarity and FAIL_TO_PASS test validity, and any sample scoring severity ≥2 on any criterion was excluded from the final 500 — [OpenAI: Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/); corroborating detail via [Epoch AI benchmark page](https://epoch.ai/benchmarks/swe-bench-verified).
- General LLM capability taxonomy (not coding-specific, but structurally the most complete cross-domain scheme found): "From Isolated Tasks to Structured Capabilities" proposes a **multilayer taxonomy** of 14 cognitive capability domains and 91 subskills organized into Primitive, Constructed, and Integrative layers — [arXiv 2607.22182](https://arxiv.org/pdf/2607.22182).
- Skill-taxonomy-construction methodology (general, not coding-specific): a described five-stage pipeline — tag discovery, clustering, taxonomy construction where stable clusters seed an initial draft, then iterative expert refinement into major/sub-categories — is the closest documented general recipe for turning raw task tags into a hierarchy, matching the "cluster issues into goal types" approach the ingestion system would need — [search summary, no single primary paper pinned; corroborated in skill-decomposition literature such as](https://arxiv.org/html/2510.11313) (Automated Skill Decomposition Meets Expert Ontologies).
- Ontology-guided perturbation work for math/coding (a "general ontology of perturbations for math and coding questions") uses perturbed problem variants to probe specific capability axes rather than to label existing benchmark items — a complementary but distinct use of "ontology" from a goal/skill taxonomy for classification — [Evaluating LLMs' Mathematical and Coding Competency through Ontology-guided Interventions](https://arxiv.org/html/2401.09395).

### Inferences
- DS-1000's library-axis and BigCodeBench's domain/function-call axis are both effectively **"tool/library used" taxonomies**, not "type of engineering goal" taxonomies — they classify by *what APIs the solution touches*, which is a useful but orthogonal signal to a Goal taxonomy built from issue/problem intent (bug fix vs. feature add vs. refactor vs. performance vs. data transformation).
- SWE-bench Verified's difficulty label (estimated fix-time, human-annotated) is a good direct precedent for a "difficulty" field in the Goal schema, but it is *not* a skill/goal-type label — it should map to a separate difficulty attribute, not be conflated with the goal-type taxonomy.
- No benchmark in the ingestion list was found to ship a ready-made "goal type" (bug-fix / feature / refactor / perf / test-add) label at the per-instance level; this would need to be constructed (see next section) rather than imported.

### Gaps
- No source found for a published, coding-specific "skill ontology" that spans both SWE-bench-style (repo-level, issue-driven) and DS-1000/BigCodeBench-style (function-call, library-level) tasks under one hierarchy — this appears to be an open construction problem, not a solved-and-published one.
- No source found describing an existing LLM-assisted "skill annotation" pass specifically applied to SWE-bench, DS-1000, or BigCodeBench items (as opposed to general capability-taxonomy papers evaluated *on* benchmarks). If such annotated label sets exist (e.g., as a supplementary dataset release), they were not surfaced by this search pass.
- LiveCodeBench's and Terminal-Bench's internal task-categorization schemes (contest-problem categories, terminal-task categories) were not investigated in this pass beyond LiveCodeBench's temporal-window design; a follow-up should check LiveCodeBench's per-problem difficulty/category fields (LeetCode/Codeforces native difficulty tags) and Terminal-Bench's task taxonomy directly from their GitHub repos/dataset cards.

## Normalizing task metadata: repository identity, library/package ids, language, difficulty, test-quality flags

### Takeaway
Canonical repository identity in the SWE-bench family is handled operationally via owner/name strings plus explicit clone-URL override tables for renamed/migrated repos, and execution-based validation (build, apply patch, run tests) is the field-standard mechanism for producing test-quality/broken-instance flags — but this is enforced per-dataset by each maintainer's own pipeline, not via a shared normalization layer across suites.
### Cited Findings
- SWE-rebench-V2 maintains explicit handling for **upstream repository migrations**: a linked PR is titled "Fix SWE-rebench-v2 builds for migrated upstream repositories," and repository clone-source overrides are keyed by `(repo, base_commit)` in a `CLONE_REPOSITORY_OVERRIDES` table so that only the clone URL is rewritten while the canonical `(repo, base_commit)` identity is preserved — [sii-system/agent-fleet PR #190](https://github.com/sii-system/agent-fleet/pull/190); corroborated via SWE-rebench search summary.
- SWE-bench's own instance-validity process is execution-based: candidate instances are built into virtual environments, dependencies installed, the gold patch applied, and tests run; any candidate that fails at any step is removed before release — this is the mechanism that also produces "broken instance" and test-quality flags — [SWE-bench FAQ](https://www.swebench.com/SWE-bench/faq/); [SWE-bench paper](https://arxiv.org/pdf/2310.06770).
- SWE-bench Verified specifically documents post-release test failures traced to **outdated package dependencies and external service failures** in named instances (e.g., `astropy__astropy-7606`, `astropy__astropy-8707`, `astropy__astropy-8872`), and a separate cleanup where "some unit tests were removed which were outdated or were not previously intended to be included" — evidence of live-maintained, versioned test-quality flags rather than a frozen artifact — [GitHub issue #484, SWE-bench/SWE-bench](https://github.com/SWE-bench/SWE-bench/issues/484).
- SWE-bench's construction pipeline separately reports that of an initial larger candidate pool, 311 instances were excluded because "the golden patch could not be evaluated without errors or did not fix issues reliably" (flaky test suites, erroneous test-suite setup, timeouts), leaving 1,983 instances in what became the full SWE-bench dataset — [search summary citing SWE-bench-adjacent sources](https://www.swebench.com/SWE-bench/faq/).
- SWE-bench associates task instances with repository **version numbers**, and its environment-setup tooling is described as "generalized versioning scripts supporting versioning via script execution based on repository information like pyproject.toml and git tags" — i.e., language/package-version normalization is handled by parsing each repo's own version metadata rather than a shared external registry — [search summary, SWE-bench-adjacent sources].

### Inferences
- The `(repo, base_commit)` + clone-URL-override pattern used by SWE-rebench-V2 is directly reusable for the ingestion pipeline's repository-identity normalization: keep `(owner/name, base_commit)` as the immutable canonical key, and maintain a small override table mapping historically-recorded owner/name strings to current canonical clone URLs when upstream repos rename or migrate — this avoids silently treating a renamed repo's tasks as a different repository.
- Test-quality/broken-instance flags should be treated as a **living field**, not a one-time import: SWE-bench Verified's own astropy-instance failures surfaced *after* initial release due to external dependency drift, meaning the ingestion pipeline needs a re-validation hook (periodic re-run of FAIL_TO_PASS checks) rather than a single import-time check, consistent with this repo's bi-temporal invalidate-and-append semantics.
- No universal library/package canonical-id scheme was found in the literature (e.g., no evidence anyone maps BigCodeBench's 139 libraries and DS-1000's data-science libraries onto a shared package registry with version pinning) — this normalization step appears to be pipeline-specific work the ingestion system would need to build itself, likely keying off PyPI/npm package name + version constraint as the canonical id.

### Gaps
- No source found describing how DS-1000, BigCodeBench, HumanEval/MBPP variants, or LiveCodeBench handle repository/library identity normalization (these benchmarks are less repo-centric, so this may be a non-issue for them, but that was not directly confirmed).
- No source found on Terminal-Bench's metadata normalization practices at all.
- Exact current instance count and version history for SWE-bench Verified (beyond the astropy examples and the "500 verified" headline figure) — i.e., a full changelog — was not located; the search suggests updates happen via GitHub issues/PRs on `SWE-bench/SWE-bench` rather than a published changelog document.

## Linking benchmark items to goals: LLM-based goal extraction, issue clustering, evaluation of mappings

### Takeaway
LLM-based extraction and classification of GitHub issue content (root cause, solution plan, implementation progress, bug-vs-feature-request labels) is an active research area with working pipelines, and classical TF-IDF + K-Means clustering has been used to group issues into latent goal-like clusters, but no source found in this pass evaluates such a mapping specifically for linking coding-benchmark task instances (SWE-bench-style) to a formal goal taxonomy — the closest precedents are general GitHub-issue-mining papers, not benchmark-curation papers.
### Cited Findings
- A multi-LLM pipeline ("Threads to Trajectories") extracts community knowledge from GitHub issue discussions using separate LLM passes for label classification, code-block/link summarization, comment analysis, and classification of comment analyses into label-specific fields such as **root cause, solution plan, and implementation progress** — explicitly aimed at making issue-thread knowledge "explicit, organized, and machine-accessible ... to improve the reasoning processes of automated software engineering agents," i.e., the same downstream use case as this project's Goal extraction — [From Threads to Trajectories](https://arxiv.org/html/2604.25880v1).
- LLM-based classification has been applied to sort issue-tracker items into **bug report vs. feature request** categories, sometimes further transforming them into app-review-like forms for downstream analysis — [search summary; general GitHub-issue-classification literature].
- A documented clustering approach for issues: extract title+description text, vectorize with TF-IDF, reduce dimensionality via Truncated SVD (LSA), then apply K-Means (chosen because it suits "well-separated, high-dimensional data like TF-IDF representations," with the elbow method used to pick cluster count) — [search summary describing an issue-clustering approach; no single primary paper pinned in the search result].
- "What Characteristics Make ChatGPT Effective for Software Issue Resolution?" empirically studies task, project, and conversational signals in GitHub issues as predictors of LLM resolution success — a related but distinct question (predicting resolvability, not extracting/classifying the goal) — [arXiv 2506.22390](https://arxiv.org/pdf/2506.22390).

### Inferences
- No existing paper directly answers "how well does LLM-based goal extraction map benchmark task instances onto a goal taxonomy, and how was that evaluated" — this is a gap the ingestion system would be pioneering rather than following precedent for, though the multi-LLM "root cause / solution plan" extraction pattern from the Threads-to-Trajectories pipeline is directly adaptable as an extraction template for a Goal object (root cause ≈ "what's broken," solution plan ≈ "what the Goal's solution should do").
- TF-IDF+K-Means clustering is a viable cheap baseline for bootstrapping goal-type clusters (bug-fix / feature / refactor / etc.) before hand- or LLM-labeling cluster centroids, consistent with the general five-stage skill-taxonomy-construction pattern noted in the previous section (tag discovery → clustering → draft taxonomy → expert refinement).

### Gaps
- No evaluation methodology (precision/recall, human agreement, or downstream-task lift) for LLM-based goal-extraction-and-mapping was found in this pass; if it exists, it wasn't surfaced by the queries used here and would need a more targeted search (e.g., "issue-to-task-type classification evaluation accuracy" or searching specific venue proceedings like MSR/ICSE/FSE 2024-2026).
- No source found on using clustering/LLM-extraction specifically over SWE-bench/SWE-rebench/Multi-SWE-bench issue text (as opposed to generic open-source GitHub issue corpora).

## Benchmark maintainers' revision/deprecation practices and version tracking

### Takeaway
SWE-bench-family maintainers version and prune datasets through live GitHub issue/PR activity on the `SWE-bench/SWE-bench` repo and periodic dataset-card updates on Hugging Face rather than a formal changelog document; SWE-rebench and SWE-rebench V2 are explicitly versioned as separate dataset releases (V1 vs. V2) rather than in-place mutation, and newer/rolling benchmarks (LiveCodeBench) are versioned by release time-window rather than by dataset-wide revision number.
### Cited Findings
- SWE-bench Verified's known post-release defects (dependency/environment failures in named astropy instances, later removal of outdated unit tests) were tracked and fixed via GitHub issues against `SWE-bench/SWE-bench`, e.g., issue #484 "[Dataset & Code Fix] Resolve gold patch validation failures caused by environment and dependency mismatches (Astropy & PSF Requests)" — [GitHub issue #484](https://github.com/SWE-bench/SWE-bench/issues/484).
- SWE-rebench is explicitly released as sequential, separately-versioned datasets: `SWE-rebench` (V1) and `nebius/SWE-rebench-V2` as a distinct, newer Hugging Face dataset with its own card, rather than an in-place update of the original — [nebius/SWE-rebench-V2 dataset card](https://huggingface.co/datasets/nebius/SWE-rebench-V2); [SWE-rebench V2 paper](https://arxiv.org/pdf/2602.23866).
- LiveCodeBench's versioning model is inherently rolling/temporal: new problems are continuously added with release-date annotations, and evaluation is reported per time-window (e.g., "bimonthly") rather than as a single frozen benchmark version — deprecation is implicit (old windows remain but contamination-safe evaluation requires selecting windows after a given model's cutoff) — [LiveCodeBench paper](https://arxiv.org/pdf/2403.07974); [leaderboard](https://livecodebench.github.io/leaderboard.html).
- SWE-Bench Pro (Scale AI) is presented as a distinct, harder successor to SWE-bench Verified (731 public problems, much lower model scores: GPT-5 23.3%, Claude Opus 4.1 23.1%) with a further "SWE-Bench Pro Verified" revision paper, indicating the same verified/harden-then-reverify pattern seen in SWE-bench → SWE-bench Verified is being repeated one level up — [SWE-Bench Pro Verified paper](https://arxiv.org/pdf/2609.08149); [Scale SWE-Bench Pro leaderboard](https://labs.scale.com/leaderboard/swe_bench_pro).

### Inferences
- The practical implication for the ingestion pipeline: track benchmark provenance at (dataset name, dataset version/release date, source URL/commit of the dataset card) granularity, not just (dataset name); SWE-rebench V1 vs. V2 and SWE-bench vs. SWE-bench Verified vs. SWE-bench Pro vs. SWE-bench Pro Verified are all cases where "the same name" denotes materially different, separately-published artifacts, and evidence/routing statistics must not silently merge across them.
- Given SWE-bench Verified's own post-release instance failures, any Goal built from a SWE-bench-family "verified solution" should carry a re-validation timestamp/version field, since "verified" at ingestion time is not a permanent guarantee (this aligns with the repo's own bi-temporal invalidate-and-append model — an update to instance validity should close the old validity window rather than overwrite).

### Gaps
- No consolidated, maintainer-published changelog document was found for SWE-bench/SWE-bench-Verified/SWE-bench-Lite; version history has to be reconstructed from GitHub issue/PR history and Hugging Face dataset-card revision history, which is labor-intensive and was not fully done in this pass.
- No source found on DS-1000, BigCodeBench, HumanEval/MBPP variants', or Terminal-Bench's formal revision/deprecation practices (only EvalPlus's HumanEval+/MBPP+ "why we added more tests" rationale was found, not a version-tracking mechanism).
