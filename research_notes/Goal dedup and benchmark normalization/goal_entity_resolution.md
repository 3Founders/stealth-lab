# Maximal Deduplication / Entity Resolution for Streaming Goal/Task-Intent Statements

## Entity resolution pipelines: blocking, pairwise matching, and clustering — which techniques and papers apply, and what are their tradeoffs?

### Takeaway
The state-of-the-art ER pipeline is three stages — (1) cheap blocking/candidate generation (ANN over embeddings, LSH/MinHash, or meta-blocking over token keys) to cut the O(n²) pair space; (2) a matcher that escalates from cheap to expensive (fine-tuned cross-encoder like Ditto, then an LLM judge/comparator, batched); (3) clustering that repairs the transitivity violations pairwise matchers inevitably produce — connected components only works when precision is very high, otherwise correlation clustering or LLM-based "in-context clustering" is needed. For Kel's short goal strings, this maps to: pgvector ANN blocking (already in place) → LLM-judge pairwise/triage (already in place) → the missing piece is a clustering layer that corrects intransitive LLM verdicts instead of doing single-pass same/different merges.

### Cited Findings
- **Ditto** (Li et al., VLDB 2020, arXiv:2004.00584) casts entity matching as BERT/RoBERTa/DistilBERT sequence-pair classification, beats prior SOTA by up to 29% F1, and reaches 96.5% F1 on a 789K×412K company-matching task; its three optimizations (domain-knowledge injection, summarization of long strings, augmentation with hard negatives) add up to 9.8% F1 and it needs ~half the labeled data of prior systems. — [arXiv:2004.00584](https://arxiv.org/abs/2004.00584), [VLDB PDF](https://www.vldb.org/pvldb/vol14/p50-li.pdf)
- **Entity Matching using LLMs** (Peeters et al., 2023–2024, arXiv:2310.11244) shows GPT-4 and other LLMs need zero or only a few training examples to match PLMs fine-tuned on thousands of examples, show higher robustness to unseen entities than fine-tuned PLM matchers, and GPT-4 can produce structured explanations of its matching decisions — but no single prompt is best across model/dataset combos; prompts need per-pair tuning. — [arXiv:2310.11244](https://arxiv.org/abs/2310.11244)
- **ComEM** ("Match, Compare, or Select?", COLING 2025, arXiv:2405.16884) formalizes three LLM ER strategies — *matching* (binary pairwise), *comparing* (rank candidates against a probe), *selecting* (feed a whole candidate set for one global decision) — and shows *selecting* alone beats matching/comparing because it captures cross-record consistency, but is expensive (long context, position bias). ComEM's compound pipeline filters with cheap matching/comparing first, then applies the expensive global-selecting step only on the survivors, evaluated across 8 ER datasets and 10 LLMs, delegating most computation to medium-sized LLMs to cut cost while gaining effectiveness. — [arXiv:2405.16884](https://arxiv.org/abs/2405.16884), [GitHub](https://github.com/tshu-w/comem)
- **Batching LLM ER calls** reduces API cost/latency but raises risk of malformed JSON as batch size grows and output complexity increases — a direct operational risk for Kel's existing "batched LLM identity judge." — [Elasticsearch Labs](https://www.elastic.co/search-labs/blog/elasticsearch-entity-resolution-llm-semantic-search)
- **Transitivity is not guaranteed by pairwise LLM/ML matchers**: r₁=r₂ and r₂=r₃ does not imply r₁=r₃ in practice. Empirically, when the underlying matcher's baseline precision is above ~0.9, treating matches as transitive (i.e., connected components / union-find over positive edges) is safe; below ~0.5 precision it produces "mega-clusters" that silently merge unrelated entities. — [Entity Resolution in Practice](https://arxiv.org/pdf/2607.26298) (self-serve pipeline lessons)
- **Correlation clustering** is framed as the natural formalism when both positive and negative pairwise edges exist: it maximizes agreement (links kept within clusters + non-links kept across clusters) rather than naively taking connected components of positive edges, and gives a principled way to resolve conflicting pairwise verdicts instead of picking one edge to trust arbitrarily. Historically, Monge & Elkan first framed ER as detecting connected components of a pairwise-match graph — the naive baseline that correlation clustering improves on. — [(Almost) All of Entity Resolution, Binette & Steorts, Science Advances 2022](https://www.science.org/doi/10.1126/sciadv.abi8021), [arXiv:2008.04443](https://arxiv.org/pdf/2008.04443)
- **In-context Clustering-based ER with LLMs** (arXiv:2506.02509, 2025) explores giving an LLM a candidate set and asking it to directly propose clusters (not just pairs), which is a design-space alternative to pairwise-then-cluster and may better preserve global consistency for short text entities. — [arXiv:2506.02509](https://arxiv.org/html/2506.02509v1)
- **Splink** (UK Ministry of Justice, open-source, 6M+ downloads) implements the classic **Fellegi-Sunter model**: match probability is derived from λ (prior match probability), m (probability of an observed agreement pattern given a true match) and u (given a true non-match), estimated via EM; it links ~1M records/minute on a laptop and gives fully transparent, explainable match scores — a strong low-cost/high-explainability baseline layer before LLM judging, especially useful for the structured slot fields (library name, version) rather than free text. — [Splink Fellegi-Sunter docs](https://moj-analytical-services.github.io/splink/topic_guides/theory/fellegi_sunter.html), [ResearchGate](https://www.researchgate.net/publication/363226193_Splink_Free_software_for_probabilistic_record_linkage_at_scale)
- **JedAI Toolkit** (VLDB 2018 "The return of jedAI", arXiv/ACM) is schema-agnostic, needs no training data or domain knowledge, and is built around **blocking + meta-blocking**: meta-blocking prunes a block-based candidate graph of redundant/superfluous comparisons at per-comparison granularity (edge pruning/weighting) rather than at the coarser block level, and is JedAI's main runtime bottleneck since it must iterate every comparison in every block. — [return of jedAI, VLDB'18](https://dl.acm.org/doi/10.14778/3229863.3236232), [JedAIToolkit GitHub](https://github.com/scify/JedAIToolkit), [Survey of Blocking/Filtering, arXiv:1905.06167](https://arxiv.org/pdf/1905.06167)

### Inferences
- Kel's current architecture (pgvector ANN blocking + batched LLM identity judge) already implements stages 1–2 of the standard pipeline but is missing stage 3 (a clustering/transitivity-repair layer). Adding connected-components merging on top of an LLM judge is only safe if the judge's empirical pairwise precision is verified ≥0.9 on a held-out set — absent that number, silent mega-cluster risk exists in the *opposite* direction of the reported bug (over-merging), while under-eager judging causes the reported under-merging ("docx-js" vs "docx" not merged).
- ComEM's filter-then-select architecture is directly transferable: use the existing embedding ANN + cheap check as the "matching/comparing" filter, then run one **global LLM call per candidate cluster** (not per pair) that sees all near-duplicate candidates together and decides cluster membership at once — this is what would catch "docx-js library" vs "'docx' library" cases, because a single record-pair prompt without the string-normalization context (see next section) may treat "docx-js" as a distinct npm package name literal rather than resolving it against the registry.
- A Splink-style structured/probabilistic layer over *normalized slot fields* (action, object/library, version — see next section) run before the LLM step would give a cheap, explainable pre-filter and could directly resolve library-name variants if package identity is treated as one of the Fellegi-Sunter match fields with its own m/u probabilities (aliases have high u, i.e. they agree by chance rarely, so should carry strong evidentiary weight when they do agree post-normalization).

- No published numeric comparison of Ditto vs ComEM vs Splink vs pure LLM-judge specifically on *short intent/goal phrases* (all cited benchmarks are product/company/publication entity matching, not task-goal text) — precision/recall for this text genre must be measured on Kel's own gold set (see the maximal-dedup section below), not assumed from these papers.

## Normalization before matching: canonical forms, slot filling, entity linking to package registries, and paraphrase/intent-clustering literature — what works?

### Takeaway
The literature converges on **slot-filling into an action/object/modifier template before similarity computation**, exactly the "verb-object" canonicalization Kel is missing: normalize each goal into (action, object, tool/library, version) slots, resolve the tool/library slot against a registry identifier (npm/PyPI canonical name), and only then compute embedding similarity or run the LLM judge — this collapses "docx-js library" and "'docx' library" into the same object-slot value before they ever reach pairwise matching.

### Cited Findings
- In task-oriented dialogue NLU, **intent detection + slot filling** is the standard joint task: slot filling fills empty positions in an intent template using extracted tokens, and joint modeling of intent + slots outperforms modeling them separately because it captures correlations between intent label and slot-value distributions. — [Survey: Recent Neural Methods on Slot Filling and Intent Classification, arXiv:2011.00564](https://arxiv.org/html/2011.00564)
- Formal intent descriptions require an **Action** and an **Object**, optionally a **Modifier** — directly analogous to Kel's "upgrade (action) a Django project (object) to 5.x (modifier/version)" goal shape. — [Slot-filling/intent template literature via USPTO filing "Unsupervised induction of user intents from conversational customer service corpora"](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11126793)
- **Query canonicalization** in search: a canonical query is "the authoritative, normalized version of a search query that represents a group of similar user inputs, consolidating variations — misspellings, synonyms, or paraphrases — into a single, stable query form"; two queries have the same intent if they share the same objective/goal regardless of surface phrasing (e.g., "how old is Jane Doe" vs "Jane Doe age"). Search engines explicitly perform **query deduplication** to filter near-duplicate candidate queries covering the same intent. — [Canonical Query overview](https://www.nizamuddeen.com/community/semantics/what-is-a-canonical-query/), [Query intent mapping, Daniel Tunkelang](https://dtunkelang.medium.com/search-queries-and-search-intent-1dec79ad155f)
- **DSTC-11 Intent Induction track (2023)** formalized two subtasks relevant here: *intent clustering* (assign cluster labels to turns) and *open intent induction* (induce a labeled intent set from raw clusters) — directly analogous to inducing canonical Goals from raw agent-trace utterances. — [arXiv:2304.12982](https://arxiv.org/abs/2304.12982)
- A DSTC-11 companion paper (**arXiv:2212.02021**, "Analysis of Utterance Embeddings and Clustering Methods") systematically tested embeddings × clustering algorithm combinations for intent induction and found **smaller distilled embedding models (e.g., MiniLM) outperformed much larger models**, and pairing MiniLM-class embeddings with **agglomerative clustering** gave the state-of-the-art pipeline for this task — a concrete, citable recommendation against always reaching for the biggest embedding model. — [arXiv:2212.02021](https://arxiv.org/abs/2212.02021)
- A **two-stage progressive intent clustering** approach (DSTC-11 paper, aclanthology 2023.dstc-1.7) pretrains with contrastive loss over all conversation data, then jointly optimizes clustering loss + contrastive loss with an adaptive progressive k-means to reduce vanilla k-means' sensitivity to random initialization — relevant if Kel ever needs to batch-recluster the whole goal graph rather than incrementally match new goals against it. — [ACL Anthology 2023.dstc-1.7](https://aclanthology.org/2023.dstc-1.7/)
- On **package-name aliasing**: npm supports explicit aliasing (`npm install <ALIAS>@npm:<REAL_PACKAGE>@<VERSION>`), and PyPI has no built-in alias mechanism but community tooling (`pypi-alias`) creates thin "alias" distributions that depend on the real package (e.g., `python-hunter` aliasing `hunter`) — meaning registry-name variance ("docx" vs "docx-js" vs scoped names) is a real, recurring phenomenon that requires resolving against the **registry's canonical package identifier**, not string similarity alone, since alias package names can be arbitrarily different strings from the real name. — [NPM aliasing guide](https://medium.com/@mahesh.jsdev/demystifying-npm-package-name-aliasing-a-comprehensive-guide-5a0a59519de9), [PyPI alias tool](https://github.com/ionelmc/pypi-alias)

### Inferences
- Kel's "docx-js library" vs "'docx' library" bug is a **registry entity-linking failure**, not primarily an embedding/LLM-judge failure: both strings should first be resolved to an npm package identifier (there is a real npm package literally named `docx`; "docx-js" appears to be a colloquial/GitHub-org-derived alias for it) before any text-similarity step runs. This argues for a dedicated normalization pass that extracts a library/tool mention from each goal, queries the relevant package registry (npm search API / PyPI JSON API) for canonical name + aliases, and stores the resolved registry ID as a first-class slot — then dedup keys primarily off (action-lemma, resolved-object-id, version) rather than off raw text embeddings.
- The DSTC-11 finding that small distilled embeddings + agglomerative clustering beat larger embedding models for intent-level clustering suggests Kel's Voyage embeddings (large, general-purpose) may be over-powered/noisy for this specific short-goal-clustering task; a cheaper, distilled sentence embedding tuned or selected for intent similarity (rather than general semantic similarity) paired with agglomerative (not just top-k ANN) clustering could be tested as an alternative to the current pgvector nearest-neighbor approach.
- The action/object/modifier template gives a natural way to distinguish "same goal" from "parent/child" (hypernymy): if action and object slots match but the modifier differs by specificity (e.g., "upgrade Django" vs "upgrade Django to 5.x"), that is evidence for a parent/child edge, not a same-node merge — this operationalizes the "maximal dedup vs over-merge" distinction the team wants without needing a separate model.

### Gaps
- No paper found that directly applies package-registry entity linking (npm/PyPI canonical IDs) inside an LLM-based procedural-memory or goal-graph deduplication pipeline — this appears to be a genuine gap between the software-engineering-specific need (library/package identity) and the general entity-resolution/intent-clustering literature, which mostly targets people, businesses, or abstract dialogue intents. Kel likely needs to build this registry-linking slot itself (npm registry API / PyPI JSON API lookups with alias/redirect resolution) rather than adopt an existing tool.
- Could not retrieve numeric comparisons of MiniLM-class vs Voyage-class embeddings specifically for short technical/goal text (the DSTC-11 result is for customer-service dialogue utterances, a different domain).

## Incremental/streaming ER at scale: how should Kel handle records arriving continuously, with cost control and active learning?

### Takeaway
The literature treats streaming ER as "match new record against existing clusters, then repair" — with **incremental correlation clustering** supporting insert/delete/merge/split and evidence-driven error correction, and cost is controlled via a cheap-to-expensive cascade (blocking → cheap classifier → expensive LLM judge only on survivors) plus **active learning** that sends only the most informative/uncertain pairs to a human or an expensive oracle.

### Cited Findings
- **Incremental Multi-source ER for KG Completion** frames the problem exactly as Kel's: a stream of new entities arrives and must be matched/clustered against an existing cluster graph, linking new-to-old and new-to-new without full reprocessing. — [Springer 2020 / PMC7250616](https://pmc.ncbi.nlm.nih.gov/articles/PMC7250616/)
- The **Max-Both Merge (MBM)** approach adds a new entity to the most similar existing cluster or spins up a new cluster; when no clean merge is possible it **iteratively splits existing clusters** and reassigns members to maximize the clustering objective — i.e., a later goal arriving can retroactively split a previously over-merged cluster, which matches the team's "maximal dedup without over-merge" goal (corrections happen, not just one-way merges). — [Incremental Multi-source ER, Springer/PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC7250616/)
- **Incremental Correlation Clustering** explicitly supports insert, delete, individual-description changes, and merging/splitting of entire clusters, and allows **fixing prior clustering errors as new evidence arrives** — directly relevant to bi-temporal, append-only systems like Kel's, since a correction can be recorded as a new event rather than mutating history. — [Modern Data 101 overview](https://www.moderndata101.com/blogs/entity-resolution-at-scale-deduplication-strategies-for-knowledge-graph-construction), background op description also appears in incremental-clustering survey material found via search (see Findings above, "Incremental entity resolution streaming clustering merge split" query).
- **Zingg's "Living Clusters"** writeup frames incremental flow as the hardest part of production fuzzy-matching-at-scale systems, implying this is an acknowledged, unsolved-at-the-tooling-level problem in industry, not just academia. — [Zingg blog, Fuzzy Matching at Scale Part 5](https://www.zingg.ai/post/fuzzy-matching-at-scale-part-5-incremental-flow-and-living-clusters)
- **Active learning for ER** (Proceedings ACM CIKM 2017, and 2026 arXiv "BEACON: Budget-Aware Entity Matching Across Domains") follows a standard loop: train a matcher on a small labeled seed, score all unlabeled candidate pairs, select the most informative pairs by an acquisition function (e.g., closest to the decision boundary / highest disagreement), send only those to a human oracle, retrain, and repeat until a labeling budget is exhausted or performance converges. — [ACM CIKM 2017 Active Learning for Large-Scale ER](https://dl.acm.org/doi/10.1145/3132847.3132949), [BEACON arXiv:2603.11391](https://arxiv.org/pdf/2603.11391)
- Human-in-the-loop record linkage integrates human expertise "at various stages, from data labeling and training data generation to linkage model evaluation," not just at final QA — implying Kel could route only low-confidence LLM-judge verdicts to a human reviewer rather than reviewing all merges/splits. — [Human-Interactive Linkage, Springer](https://link.springer.com/chapter/10.1007/978-3-032-21932-9_11)

### Inferences
- Kel's "per-document goal cache" is effectively a batching/blocking optimization but does not by itself solve incremental clustering — cross-document duplicates (like docx-js vs docx arising from different source documents) require comparing each new goal against the **existing global cluster set**, not just against goals seen so far in the same document. A dedicated "candidate cluster lookup" step (ANN search over existing goal cluster centroids/representative members, not just raw goal embeddings) before the identity judge would close this gap.
- Given Kel's append-only, bi-temporal architecture (per CLAUDE.md: "an update closes the old validity window and appends a new row"), the "split existing cluster" operation from incremental correlation clustering maps naturally onto Kel's semantics: a merge-correction should invalidate the old goal-identity claim and append a new one, never mutate history — this is an architectural fit, not a gap, and should be called out to the team as validation that their existing invalidate-and-append model already supports the "fix errors with new evidence" requirement from the ER literature.
- A cascade — cheap ANN blocking (existing) → cheap structured/Fellegi-Sunter-style slot match (new, on normalized action/object/version slots) → LLM judge only on the remaining ambiguous pairs (existing, but scoped down) → active-learning queue of the lowest-confidence LLM verdicts to a human — would reduce LLM judge call volume while improving precision, addressing both cost and the maximal-dedup-without-over-merge goal simultaneously.

### Gaps
- No source found with published latency/throughput numbers for incremental correlation clustering at the goal/task-intent scale Kel operates at (likely thousands–low millions of goals, not the web-scale benchmarks in most ER papers) — Kel would need to benchmark this itself.
- No direct evidence on how large an active-learning labeling budget is typically needed to reach a given precision/recall on short technical text; BEACON and the CIKM 2017 paper's numbers are for classic structured-record benchmarks (products, publications), not short free-text goals.

## Maximal dedup vs over-merge: how to calibrate thresholds, measure quality (B-cubed/pairwise F1), build a cheap gold set, and distinguish same/variant/parent-child?

### Takeaway
B-cubed is the more reliable metric for this problem (it correctly penalizes both splitting large clusters and merging distinct ones, unlike pairwise F1 which under-penalizes singleton errors), and the standard way to calibrate "maximal but not over-merged" is to build a small stratified gold set (including deliberately adversarial near-duplicate and hypernym/hyponym pairs), measure B-cubed precision/recall on it, and tune thresholds against that curve rather than a single global similarity cutoff — while treating "parent/child" as a third label alongside same/different so the clustering layer isn't forced into a binary choice that causes exactly the over/under-merge failures the team is worried about.

### Cited Findings
- **B-cubed** computes, per item, the precision/recall of its own predicted cluster against its true cluster, then averages over all items — this gives a record-centered view of cluster structure and, per the entity-resolution evaluation literature, is empirically the most accurate estimator (lowest RMSE) of the three families compared (pairwise, cluster-level, B-cubed), with pairwise metrics singled out as "overly optimistic" because splitting/merging large clusters barely moves the pairwise score while B-cubed properly captures the damage from large-cluster errors. — [How to Evaluate Entity Resolution Systems, arXiv:2404.05622](https://arxiv.org/html/2404.05622), [A Practitioner's Guide to Evaluating ER Results, arXiv:1509.04238](https://arxiv.org/pdf/1509.04238)
- **Pairwise precision/recall/F1** treats every within-cluster pair as a sample; useful for link-level error auditing but should be a secondary, not primary, metric given the above finding. — [arXiv:2404.05622](https://arxiv.org/html/2404.05622)
- Empirically, **pairwise-matcher precision above ~0.9 makes transitive closure (connected components) safe; below ~0.5 it produces mega-clusters** — this is a concrete, actionable threshold for Kel: measure the LLM identity judge's raw pairwise precision on a gold set first, and only allow naive transitive merging if it clears ~0.9; otherwise a clustering-with-correction layer (correlation clustering / incremental correction) is mandatory, not optional. — [Entity Resolution in Practice, arXiv:2607.26298](https://arxiv.org/pdf/2607.26298)
- **Weak supervision** ("replacing hand-labeling with acquiring and aggregating noisy-but-cheap label estimates from labeling functions") is a documented low-cost way to bootstrap a gold/near-gold set: models trained on large noisy-labeled sets can match performance of models trained on small hand-labeled gold sets, and weak supervision has been used to build large medical entity datasets in hours instead of physician-months. — [lxt.ai Weak Supervision overview](https://www.lxt.ai/ai-glossary/weak-supervision/); ER-specific: **Ground Truth Inference for Weakly Supervised Entity Matching**, arXiv:2211.06975. — [arXiv:2211.06975](https://arxiv.org/pdf/2211.06975)

### Inferences
- For Kel, a cheap gold set can be built by: (1) sampling goal pairs the current pipeline already flagged as *high embedding similarity but LLM-judge "different"* (likely false negatives, e.g. the docx-js case) and (2) sampling pairs flagged "same" with only moderate embedding similarity (candidate false positives / over-merges), then hand-labeling ~100–300 of each stratum as same / variant(paraphrase) / parent-child / unrelated. This directly targets the failure mode reported (slipped-through duplicates) while also stress-testing for over-merging, and is far cheaper than a random sample because it's drawn from the pipeline's own disagreement/boundary cases — consistent with the active-learning "most informative pair" principle above.
- Because binary same/different forces the LLM judge to either merge two goals of different granularity or leave them as unrelated duplicates, adding an explicit **parent/child (hypernymy) label** to the judge's output schema (same / paraphrase-variant / parent-of / child-of / unrelated) should directly reduce both failure modes: near-duplicates that are actually the same node get the "paraphrase-variant → merge" path, while genuinely different-granularity goals get a DAG edge instead of a forced merge-or-not decision.
- Given the pairwise-precision-0.9 threshold finding, Kel should not rely on simple connected-components merging over LLM "same" verdicts unless it has verified its judge clears that bar on the constructed gold set; if it hasn't been measured, correlation-clustering-style consistency checking (or at minimum, a "does this candidate merge also match every existing member of the target cluster, not just the nearest one" check before merging into an existing cluster) is warranted.

### Gaps
- No existing published gold set or benchmark was found that matches Kel's exact object (short software/task goal statements with library/version slots); the team will need to construct its own, there is no off-the-shelf dataset to borrow thresholds from.
- No source quantifies how much weak supervision specifically improves entity-resolution gold-set construction cost/quality for *short free-text* entities (the cited medical/NER weak-supervision results are for structured/tabular or long-document domains).

## How do procedural/skill knowledge bases and agent-memory systems (WikiHow PKGs, Voyager, Agent Workflow Memory, Mem0, Letta) deduplicate — what worked?

### Takeaway
Existing agent-memory and procedural-KB systems mostly use lightweight, exact-key or single-pass deduplication (not full entity resolution): WikiHow procedural graphs cluster near-duplicate step headlines, Agent Workflow Memory deduplicates *by identical action sequence* (a strict structural key, not semantic similarity), Voyager avoids duplication by never modifying existing skills (append-only, so duplicates simply accumulate rather than get merged), and both Mem0 and Letta report real, currently-unsolved gaps in deduplication/consolidation — evidence that Kel's dedup problem is harder than what shipped agent-memory tooling currently handles, and that building a real ER layer (rather than reusing an off-the-shelf memory framework's dedup) is justified.

### Cited Findings
- **WikiHow procedural knowledge graphs**: nodes are "(clustered) steps from WikiHow," and because two step headlines can express the same step in different words (their own example: "jack up the car" vs "jack the car up"), a clustering-based deduplication step is applied to unify semantically identical step headlines before graph construction — the closest published analogue to Kel's goal-dedup problem, but at the step level, with no reported precision/recall numbers found. — [Procedural Knowledge Graph description](https://medium.com/@QuarkAndCode/knowledge-graphs-normalization-deduplication-and-entity-resolution-a8ba384d539c) (context sourced alongside PKG-from-WikiHow discussion)
- **Voyager** (Minecraft agent, skill library) stores each new successful skill program indexed by a natural-language description in a continually growing library, and explicitly does **not modify existing skills when adding new ones** — this avoids merge complexity entirely but means duplicate/near-duplicate skills are never consolidated, only accumulated; Voyager discovered 63 unique items (3.3× more than baselines) via this append-only design. — [Voyager summary via search](https://arxiv.org/html/2409.07429v1) (context)
- **Agent Workflow Memory (AWM)** (arXiv:2409.07429) performs deduplication as part of a *rule-based* workflow-induction module: it groups experiences **by identical extracted action sequence** and randomly retains a sample from each group — i.e., deduplication is a structural/exact-match operation over normalized action traces, not a semantic-similarity or LLM-judged merge. — [arXiv:2409.07429](https://arxiv.org/html/2409.07429v1)
- **Mem0** (per third-party comparative analysis, 2026) runs an extract → consolidate → retrieve loop; its v3 (April 2026) moved to "single-pass ADD-only extraction with cross-memory entity linking," described as having "the most polished write-time operations API" among compared systems for handling duplicate/related facts at write time. — [Mem0 vs Letta comparison, vectorize.io](https://vectorize.io/articles/mem0-vs-letta), [AI Agent Memory 2026 comparison](https://medium.com/@wasowski.jarek/i-compared-5-ai-agent-memory-systems-across-6-dimensions-none-wins-6a658335ed0a)
- **Letta** has an open, unresolved feature request (GitHub issue #3116, letta-ai/letta) for **archival memory deduplication and consolidation** — confirming this remains a known gap in a widely-used production agent-memory framework as of 2026, not a solved problem. Letta's `memory_rethink()` provides agent-driven consolidation, but the comparative write-up explicitly notes Letta is "missing archival memory deduplication capabilities" and exposes no write-side dedup primitive in its OSS path. — [letta-ai/letta issue #3116](https://github.com/letta-ai/letta/issues/3116), [Mem0 vs Letta comparison](https://vectorize.io/articles/mem0-vs-letta)
- Broader memory-consolidation framing (2026 survey-style source, Hindsight blog): consolidation happens at three granularities — **local** (pairwise dedup), **cluster-wise** (e.g., approaches like PREMem, CAM, TiM), and **global** (e.g., MOOM, AgentFold) — giving Kel a vocabulary for where in this spectrum its own approach should sit (Kel's goal-DAG dedup is closest to "cluster-wise" consolidation, since goals form a graph with parent/child structure, not just a flat memory list). — [The Consolidation Problem in Agent Memory, Hindsight blog, 2026](https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation)

### Inferences
- None of the surveyed agent-memory/procedural systems implement a full ER pipeline (blocking + LLM/cross-encoder matching + clustering with transitivity repair) — AWM's exact-action-sequence dedup and Voyager's no-merge-ever policy are both far simpler than what Kel already has (embedding ANN + LLM judge), meaning Kel is already ahead of typical shipped agent-memory dedup and the improvement needed is the "next tier" (normalization + clustering-with-correction + calibrated thresholds) described in the sections above, not a wholesale architecture swap.
- The Letta and Mem0 gaps are a useful data point for the team: dedup/consolidation is widely acknowledged as unsolved-at-the-tooling-level even in funded, production agent-memory frameworks as of 2026, which supports investing in a custom pipeline rather than expecting to adopt an existing library's dedup logic wholesale.

### Gaps
- No paper or writeup was found reporting **quantitative precision/recall for WikiHow step deduplication** — the "jack up the car" example is illustrative, not benchmarked, in the sources found.
- No detailed technical description of Mem0's "cross-memory entity linking" (v3, April 2026) algorithm was retrievable beyond the comparative-analysis summary — the primary Mem0 documentation/paper would need to be fetched directly for implementation-level detail.

## What concrete pipeline should Kel adopt to maximize goal deduplication without over-merging?

### Takeaway
Layer four stages onto Kel's existing embedding+LLM-judge system: (1) a normalization pass that slot-fills each goal into action/object/library-registry-ID/version before any similarity computation; (2) keep pgvector ANN as blocking but block on the normalized object/registry-ID slot too, not just raw-text embeddings; (3) replace the current single-shot pairwise LLM same/different judge with a compound judge (cheap slot/structured match → LLM comparator against a *candidate cluster*, not just the nearest pair) that also outputs a parent/child label, not just same/different; (4) add a clustering-with-correction layer (correlation clustering or incremental-cluster merge/split) instead of naive connected components, calibrated against a purpose-built gold set measured with B-cubed, with active-learning-style routing of low-confidence verdicts to human review.

### Cited Findings
(This section is synthesis; see the cited findings in the five sections above for primary sourcing of each component — Ditto/ComEM/Peeters for the matcher, Splink/JedAI for structured blocking, npm/PyPI aliasing sources for registry linking, DSTC-11 papers for slot-based normalization, correlation-clustering and incremental-ER sources for the clustering layer, B-cubed/precision-threshold sources for calibration.)

### Inferences
- **Normalization first**: extract (action-lemma, object/library-mention, version/modifier) from each goal at ingestion time; resolve the library-mention against npm/PyPI registry search APIs to a canonical package ID + known aliases, and store that ID as the primary blocking/matching key. This directly fixes the "docx-js" vs "docx" case class, independent of any embedding/LLM improvement.
- **Blocking**: keep pgvector ANN for recall on the free-text action/description, but add a second exact/fuzzy blocking key on the resolved registry ID (à la JedAI's schema-agnostic block-then-meta-block approach) so candidates sharing a registry ID are always compared even if their surface text embeds far apart.
- **Matching**: replace pairwise-only LLM judging with a ComEM-style filter-then-select: cheap slot-match/embedding filter narrows to a candidate cluster, then one LLM call evaluates the whole candidate cluster at once (in-context clustering) and returns same/paraphrase-variant/parent-child/unrelated for each member versus the cluster anchor — this both cuts LLM call volume (fewer, bigger calls vs many pairwise calls) and captures the cross-record consistency that pure pairwise judging misses.
- **Clustering with correction**: do not assume transitivity from LLM "same" verdicts; measure the judge's pairwise precision against a gold set first. If it clears ~0.9, connected components is defensible; if not, apply correlation clustering, or at minimum require a new candidate to be confirmed against multiple existing cluster members (not just the nearest one) before merging, and support Kel's existing invalidate-and-append semantics for later splits when new evidence contradicts an old merge.
- **Calibration and gold set**: build the gold set from the pipeline's own disagreement cases (high-embedding-similarity/LLM-different, and moderate-similarity/LLM-same pairs), label same/variant/parent-child/unrelated, and report B-cubed precision/recall (not just pairwise F1) when tuning thresholds — since B-cubed is the more accurate estimator per the cited evaluation literature and pairwise F1 would under-report exactly the "mega-cluster over-merge" failure mode the team wants to avoid.

### Gaps
- This recommended pipeline is a synthesis from adjacent-domain literature (structured ER, dialogue intent clustering, general agent memory) rather than a system validated end-to-end on short software-task-goal text in any single cited paper — it should be treated as a design hypothesis to validate against Kel's own gold set and production data, not a proven-in-domain recipe.
