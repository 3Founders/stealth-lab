# Normalizing and Aggregating Model Performance Across Heterogeneous Benchmarks (2019–2026)

## Simple normalizations and their pitfalls (min-max, z-score, percentile, baseline-normalized, mean win rate, rank aggregation, statistical-precipice critique)

### Takeaway
Point-estimate normalizations (min-max, z-score, human/random-baseline normalization, mean win rate) are cheap but each has a documented, specific failure mode — baseline normalization breaks when baselines underperform random policies, win-rate aggregation discards magnitude information, and any point-estimate aggregate (mean/median across tasks) hides the sampling uncertainty that the "statistical precipice" literature showed dominates apparent algorithm differences; the recommended fix from RL (Agarwal et al. 2021) is interquartile mean (IQM) plus stratified-bootstrap confidence intervals, and this critique has direct, cited analogues in recent LLM-eval and leaderboard papers.

### Cited Findings
- Human Normalized Score (HNS), used widely in RL, is computed as `(Algorithm Score − Random Score) / (Human Average Score − Random Score)`; on Atari, several games (e.g., in Procgen, "heist" and "maze") have baseline policies that underperform the random policy, producing a negative denominator that inverts the ranking direction and "unfairly penalizes agents that perform better than the random policy" — [Deep RL at the Edge of the Statistical Precipice, NeurIPS 2021 / arXiv:2108.13264](https://arxiv.org/abs/2108.13264)
- Min-max normalized scores "fail to intuitively reflect the gap between the algorithm and the average level of humans," and HNS ≥ 100% is read as "surpassed human average" — a framing that breaks down once baselines are noisy or non-monotonic — [arXiv:2108.13264](https://arxiv.org/abs/2108.13264)
- Z-score normalization is a common substitute for min-max/baseline normalization because it uses the mean/std of a value group rather than an absolute baseline, but "extreme outliers can still significantly influence the mean and standard deviation, affecting the Z-score" — [OpenSearch blog: Introducing z-score normalization for hybrid search](https://opensearch.org/blog/introducing-the-z-score-normalization-technique-for-hybrid-search/)
- Agarwal, Schwarzer, Castro, Courville, Bellemare, "Deep Reinforcement Learning at the Edge of the Statistical Precipice," NeurIPS 2021: deep RL algorithms are predominantly evaluated by comparing relative performance across many tasks using point estimates (mean, median) that ignore statistical uncertainty from a finite number of runs; they propose the Interquartile Mean (IQM) — which corresponds to a specific region of the performance profile and "typically results in smaller confidence intervals than median scores" — and stratified bootstrap confidence intervals, computed by resampling runs with replacement independently per task to build an empirical bootstrap distribution over N runs × M tasks — [arXiv:2108.13264](https://arxiv.org/abs/2108.13264); tools released at [rliable](https://agarwl.github.io/rliable/)
- HELM's aggregation metric, Mean Win Rate (MWR), is "a Borda Count variant" that computes, per scenario, the fraction of head-to-head comparisons in which a given model beats all other models on a metric, then averages the win rate over scenarios; HELM's own documentation notes MWR's "notable disadvantage" is that it "obscures the magnitude of variation in the metric associated with each test model and only conveys ordinal information about the relative performances of each model" — [Stanford CRFM HELM](https://crfm.stanford.edu/helm/) and search-summarized findings from [HELM paper, arXiv:2211.09110](https://arxiv.org/abs/2211.09110)
- A leaderboard uncertainty paper states plainly: "A score reported without an interval is a measurement reported without error bars, and in any other branch of empirical science that would be unpublishable" — cited in search results discussing statistical rigor in LLM evaluation (specific paper title/venue not confirmed in the snippet; treat as a strongly-worded position, not an established consensus statement — see Gaps).

### Inferences
- For a routing system pulling in benchmark scores with different scales (accuracy %, pass@1, Elo, etc.), min-max and human/random-baseline normalization are risky as a default because the baseline itself can be unstable or absent for coding-agent benchmarks (there is no canonical "random" or "human" baseline for SWE-bench-style tasks the way there is for Atari). Z-score is a safer default *only* if per-benchmark score distributions across a reasonably large, stable reference set of models are available and outlier models are winsorized or excluded from computing the reference mean/std.
- Because HELM's own docs flag MWR's ordinal-only weakness, mean-win-rate-style aggregation is defensible for producing a single leaderboard rank but is a poor substrate for a Bayesian ability estimate that needs magnitude and uncertainty, not just order.
- The rliable/IQM + stratified-bootstrap methodology is the most directly reusable recipe here: it is designed exactly for "many tasks × noisy per-task, per-run measurements" and generalizes naturally to "goals × benchmarks × instances" if the system already has multiple runs (or repeats) per (model, goal) cell to bootstrap over.

- No direct primary-source coverage in this pass of a rank-aggregation method (e.g., Borda, Copeland, Kemeny) applied specifically to LLM coding benchmarks beyond HELM's MWR — worth a follow-up search if rank aggregation specifically (vs. score aggregation) becomes a candidate method.

## Latent-ability models: IRT, Bradley-Terry/Elo, factor analysis, and how they handle missing data / different scales

### Takeaway
The dominant modern approach for cross-benchmark comparability is Item Response Theory (IRT): treat each benchmark item as having difficulty/discrimination parameters and each model as having a latent ability, jointly estimated from the sparse matrix of (model × item) correctness; this handles missing data natively (models need not attempt every item), puts otherwise-incomparable benchmarks on one latent scale, and underlies tinyBenchmarks, metabench, Epoch AI's ECI, and the "Rosetta Stone" stitching framework. A complementary factor-analytic approach (observational scaling laws) reduces many benchmark scores to a low-dimensional PCA "capability vector" and handles missing data via PCA imputation (~1% missingness in their data). Bradley-Terry/Elo (Chatbot Arena) is a distinct latent-ability model for pairwise preference data, not item-correctness data, and has documented failure modes when the pairwise-comparison generating process is non-stationary.

### Cited Findings
- **tinyBenchmarks** (ICML 2024, Polo et al.): proposes a generalized p-IRT (gp-IRT) estimator combining direct sampling-based estimation with IRT model predictions; selects a small, informative item subset via stratified random sampling, correctness-based clustering, or IRT-based clustering; achieves ~2% average estimation error with as few as 100 examples per scenario, cutting MMLU evaluation cost by ~140x (14K→100 items) and the Open LLM Leaderboard by ~160x (29K→180 items across 6 scenarios) — [arXiv:2402.14992](https://www.alphaxiv.org/abs/2402.14992), [ICML 2024 proceedings](https://dl.acm.org/doi/10.5555/3692070.3693466)
- **metabench** (Kipnis et al., ICLR 2025): applies IRT to 5,000+ LLMs' results across six Open-LLM-Leaderboard benchmarks (ARC, GSM8K, HellaSwag, MMLU, TruthfulQA, WinoGrande; 28,632 items total), fits item parameters by maximum likelihood, selects the 858 most "informative" items, then uses Generalized Additive Models (GAMs) to map performance on the sparse subset back to predicted full-benchmark scores; reconstructs individual benchmark scores with average RMSE 1.24% and the total leaderboard score with 0.58% RMSE; a single latent factor explains 79.3% of total variance across latent abilities (Pearson r = 0.938 with the grand average score) — [arXiv:2407.12844](https://arxiv.org/html/2407.12844), [GitHub: adkipnis/metabench](https://github.com/adkipnis/metabench), ICLR 2025 proceedings
- **Rodriguez, Barrow, Hoyle, Lalor, Jia, Boyd-Graber, "Evaluation Examples are not Equally Informative: How should that change NLP Leaderboards?"**, ACL-IJCNLP 2021, pp. 4486–4503: scales IRT to full NLP-benchmark leaderboard analysis using a 2-parameter-logistic (2PL) model that jointly estimates item difficulty, item discriminability, and subject (model) ability; proposes IRT-based leaderboards instead of raw-accuracy leaderboards — [ACL Anthology 2021.acl-long.346](https://aclanthology.org/2021.acl-long.346/)
- **Observational Scaling Laws** (Ruan, Maddison, Hashimoto, NeurIPS 2024 Spotlight, arXiv:2405.10938, submitted May 2024): builds scaling laws from ~100 publicly available models without new training runs; uses PCA to reduce many benchmark scores to a low-dimensional "capability vector," models benchmark score ≈ sigmoid(capability vector · learned coefficients + bias); finds LM performance is governed by a low-dimensional capability space shared across model families, with families differing mainly in compute→capability efficiency; missing data (~1% of the evaluation matrix) is handled via PCA imputation; validated via systematic holdouts splitting models by scale/capability — [arXiv:2405.10938](https://arxiv.org/abs/2405.10938), [NeurIPS 2024 poster](https://neurips.cc/virtual/2024/poster/95350), [GitHub: ryoungj/ObsScaling](https://github.com/ryoungj/ObsScaling)
- **Epoch AI's Epoch Capabilities Index (ECI)**: built on IRT, functions "like Elo scores," rating both model capability and benchmark difficulty simultaneously by comparing performance across benchmarks of varying difficulty; as of the retrieved snapshot, ECI draws on 1,123 distinct evaluations covering 147 models and 39 underlying benchmarks, combining at least 4 benchmark scores per model out of 50+ candidate benchmarks; explicitly built to counter benchmark saturation (individual benchmarks saturate "sometimes within months") — [epoch.ai/eci](https://epoch.ai/eci), [epoch.ai/data/eci-documentation](https://epoch.ai/data/eci-documentation), [epoch.ai/data-insights/interpreting-eci](https://epoch.ai/data-insights/interpreting-eci)
- **"A Rosetta Stone for AI Benchmarks"** (Epoch AI, with Google DeepMind researchers; arXiv:2512.00193): uses logistic item-response modeling plus "robust statistical stitching" to put model capability and benchmark difficulty on one common interpretable numeric scale, assuming benchmark accuracy scales roughly linearly with underlying capability with a sigmoidal transition, explicitly designed to handle incomplete benchmark coverage (models not evaluated on every benchmark) — [epoch.ai/publications/a-rosetta-stone-for-ai-benchmarks](https://epoch.ai/publications/a-rosetta-stone-for-ai-benchmarks), [arXiv:2512.00193](https://arxiv.org/pdf/2512.00193)
- **Chatbot Arena / "The Leaderboard Illusion"** (Singh, Nan, Wang et al., NeurIPS 2025 Datasets & Benchmarks Track; arXiv:2504.20879, submitted April 2025): documents that silent model deprecations violate Bradley-Terry assumptions and destabilize ratings, especially for open-weight/open-source models (64% of silently deprecated models were open-weight or fully open); finds major asymmetries in private pre-release testing (one provider tested 27 private variants before publicly releasing one); frames the core statistical problem as "distributional shift" — Bradley-Terry/Elo assume a static comparison environment (like chess), which Arena's evolving model roster and non-uniform sampling violate — [NeurIPS 2025 paper PDF](https://proceedings.neurips.cc/paper_files/paper/2025/file/70a93f260a51123b3c0e33ecd1b4de97-Paper-Datasets_and_Benchmarks_Track.pdf), [arXiv:2504.20879](https://arxiv.org/pdf/2504.20879), LMArena's own response acknowledging the testing-policy asymmetry but disputing unfairness — [LMArena blog response](https://lmarena.ai/blog/our-response/)
- **Flash-HELM** (Perlitz, Bandel et al., "Efficient Benchmarking (of Language Models)," NAACL 2024, originally arXiv:2308.11696): a "coarse-to-fine" tournament algorithm that eliminates low-ranked models early using partial data and only fully evaluates finalists, cutting compute up to ~200x with minimal ranking deviation from full HELM; introduces a reliability/decision-impact metric (DIoR) — [ACL Anthology NAACL 2024](https://aclanthology.org/2024.naacl-long.139.pdf), [IBM Research blog](https://research.ibm.com/blog/efficient-llm-benchmarking)
- **py-irt**: open-source scalable IRT library for Python explicitly built for NLP benchmark leaderboards, underlies several of the above lines of work — [arXiv:2203.01282](https://arxiv.org/pdf/2203.01282)

### Inferences
- The IRT family (tinyBenchmarks, metabench, py-irt, Rosetta Stone, ECI) is the closest existing methodological match to what the recommender needs: it already jointly models "instance difficulty" and "model ability," handles arbitrary missingness (models that never ran a given benchmark), and multiple independent groups have converged on it (2021 NLP leaderboards → 2024 tinyBenchmarks/metabench/observational-scaling-laws → 2025-26 Epoch AI production system). This suggests IRT-derived ability estimates are a mature, low-risk choice for the "import external benchmark evidence" half of the recommender, complementary to — not a replacement for — the system's own hierarchical IRT/GLMM over its own runs.
- Bradley-Terry/Elo is appropriate for pairwise-preference data (Arena-style human/judge comparisons) but the Leaderboard Illusion paper is a strong, recent, peer-reviewed warning that it is fragile to a *non-stationary* pool of competitors (models silently added/removed) — directly relevant if the system ever ingests Arena-style pairwise or LLM-judge preference data as one evidence stream; it should not assume a fixed comparison pool.
- Observational scaling laws' PCA capability-vector approach is a useful alternative/complement to IRT for goal-level pooling: if the recommender wants a low-dimensional "general capability" prior to shrink sparse per-goal estimates toward (analogous to hierarchical partial pooling), a PCA/factor-analytic capability axis computed across all ingested benchmarks could serve as that prior, especially where IRT item-level data (raw per-item correctness) isn't available and only aggregate benchmark scores are.
- None of tinyBenchmarks/metabench/Rosetta Stone/ECI report handling of *scaffold or harness* as a model-side covariate within the IRT model itself — this is a gap addressed instead by the harness-effect literature (see next section), suggesting the system needs to combine IRT-style latent ability estimation with an explicit scaffold covariate/offset, not expect IRT alone to absorb it.

Treat "Polo, flash-HELM" as unconfirmed; tinyBenchmarks (Polo et al.) and Efficient Benchmarking/Flash-HELM (Perlitz/Bandel et al.) are two separate lines of work.

## Scaffold/harness effects, pass@k vs pass@1, contamination adjustment, and encoding them as covariates

### Takeaway
Coding-agent benchmark scores (especially SWE-bench-family) are now documented to vary by double-digit percentage points purely from harness/scaffold choice, holding the model fixed — meaning raw external leaderboard scores are not safely comparable across sources unless the harness is controlled for or reported; pass@k has a standard unbiased combinatorial estimator (Chen et al. 2021) but is a different quantity from pass@1 and should never be silently equated with it; contamination-aware benchmarks like LiveCodeBench solve comparability by time-windowing (only scoring problems released after a model's training cutoff) rather than statistical adjustment.

### Cited Findings
- "Stop Comparing LLM Agents Without Disclosing the Harness" (arXiv:2605.23950): independent third-party monitoring reports up to 15 percentage points of scaffold-only variation on SWE-bench Verified, holding the model fixed; on SWE-bench Pro with Claude Opus 4.5, one independent standardized run reports ~45.9% while a vendor comparison of three harnesses on the same model reports ~49.8–51.8% — "same model, four setups, a spread of several points"; the paper's normative claim is that agent benchmark scores are "not valid for cross-model comparison unless the execution harness is disclosed," and proposes either a locked-harness protocol (one harness applied to all models) or a factorial protocol (harness varied as a controlled factor, with variance components reported) — [arXiv:2605.23950](https://arxiv.org/html/2605.23950)
- "Harness or Model? Isolating the Harness Effect in Agentic Coding with a Contamination-Controlled Private Suite" (arXiv:2609.11987) and "The Double Measurement Confound in Agent Benchmarks: De-Scaffolding, Ground-Truth Scoring, and Reliability Beyond the Mean" (arXiv:2609.09218) are both dedicated recent papers isolating scaffold vs. model contribution to agent benchmark scores — titles and existence confirmed via search; full methodology not independently fetched in this pass (see Gaps).
- Holding the model fixed and changing only the harness raised Terminal-Bench 2 pass@1 from 69.7% to 77.0% — cited within the harness-disclosure literature search results — [arXiv:2605.23950](https://arxiv.org/html/2605.23950)
- "Scaffold choice has the single biggest impact on overall performance on SWE-bench Verified" per the same source line — [arXiv:2605.23950](https://arxiv.org/html/2605.23950)
- Chen et al., "Evaluating Large Language Models Trained on Code" (Codex/HumanEval, 2021, arXiv:2107.03374): the unbiased pass@k estimator is `pass@k = 1 − C(n−c, k)/C(n, k)` where n = total samples per task, c = number of correct samples, k = attempts considered; naively computing pass@k directly from n=k samples has high variance, so the paper generates n≥k samples and applies the combinatorial correction; a numerically stable implementation uses `1.0 − prod(1.0 − k/arange(n−c+1, n+1))` rather than direct binomial-coefficient computation — [arXiv:2107.03374](https://arxiv.org/pdf/2107.03374), [OpenAI human-eval GitHub](https://github.com/openai/human-eval)
- Terminal-Bench reports scores "averaged across four independent runs," additionally reporting pass@4 alongside pass@1 — search-summarized from Terminal-Bench evaluation pages
- BigCodeBench uses Pass@1 with greedy decoding as its primary metric across 1,140 function-level tasks spanning 139 libraries, explicitly designed to be less contaminated and more "practical" than HumanEval — [Hugging Face blog: BigCodeBench, the next generation of HumanEval](https://huggingface.co/blog/leaderboard-bigcodebench)
- LiveCodeBench (Jain et al., arXiv:2403.07974, first submitted March 2024) addresses contamination via a rolling-cutoff design: problems are tagged with release dates from Leetcode/AtCoder/Codeforces contests, and when evaluating a model, only problems released after that model's training-data cutoff are scored; standard practice reports scores over a fixed recent window (commonly the most recent six months) for the "cleanest head-to-head signal"; performance is tracked in bimonthly windows and shows visible drops immediately after each model's cutoff date, which the authors use as evidence the filtering is working; the benchmark (as retrieved) spans 600+ problems published May 2023–Aug 2024, with 50+ models evaluated — [livecodebench.github.io](https://livecodebench.github.io/), [arXiv:2403.07974](https://arxiv.org/abs/2403.07974)

### Inferences
- For importing SWE-bench-family (and likely Terminal-Bench) evidence specifically, harness/scaffold must be encoded as an explicit covariate (or random effect) in the GLMM — the ~15-point swings documented are far larger than typical model-to-model gaps the recommender is trying to resolve, so treating "SWE-bench Verified score" as a single scalar without a scaffold term would badly contaminate the ability estimate. This matches the system's own "scaffold effect" term already in its per-Goal hierarchical model — external evidence should be mapped into that same scaffold-effect slot rather than pooled as if scaffold-neutral.
- pass@k vs pass@1 is a distinct, cheaper fix: since Chen et al.'s estimator is a closed-form, exact combinatorial transform, any external benchmark reporting pass@k>1 with n and c available (or even just k, n) can in principle be re-expressed at a common k (e.g., converted toward pass@1-equivalent) before being fed into the ability model — but only if the source reports n and c, not just the final pass@k percentage; many leaderboards report only the final pass@k number, which the objective's "external leaderboards report only point estimates" concern (see the Uncertainty section) also raises.
- LiveCodeBench's rolling-window contamination control is a time-based filter, not a statistical correction — meaning "contamination-adjustment" as a covariate is largely not necessary for LiveCodeBench specifically (already contamination-controlled by construction) but very much needed for older/static benchmarks (HumanEval, original DS-1000, static SWE-bench splits) where contamination is a live confound that isn't otherwise flagged in the reported score.

## Mapping benchmark items to skills/goals for per-skill ability, and hierarchical pooling across related goals

### Takeaway
Skill-level (vs. whole-benchmark) analysis is an active but less mature sub-literature than benchmark-level IRT: SKILL-MIX (2023) established combinatorial skill-composition testing as an evaluation paradigm, and follow-on work has produced "skill-slice" annotations and a "Skill-Index" for skill-level analysis of existing datasets, but none of the retrieved sources describe a full production system for mapping arbitrary external-benchmark items onto a shared skill/goal ontology the way the system's own "per-Goal" structure requires; hierarchical Bayesian partial pooling (standard multilevel/hierarchical IRT) is a well-established statistical technique directly applicable to pooling ability estimates across related goals, especially for goals with sparse external evidence.

### Cited Findings
- SKILL-MIX (arXiv:2310.17567, Yu, Arora, et al.): evaluates a model's ability to *combine* k randomly-selected skills into a single output; because the number of possible skill-subsets grows combinatorially with k, even modest k forces genuinely novel (non-memorized) generations; grading is automated via GPT-4 or open models (e.g., LLaMA-2 70B) — [arXiv:2310.17567](https://arxiv.org/pdf/2310.17567), [OpenReview](https://openreview.net/forum?id=Jf5gplvglq)
- "Unearthing Skill-Level Insights for Understanding Trade-Offs of Foundation Models" (arXiv:2410.13826): computes skill annotations across datasets to produce "skill-slices" and releases a "Skill-Index" enabling skill-level analysis of arbitrary models — [arXiv:2410.13826](https://arxiv.org/pdf/2410.13826)
- Bayesian hierarchical (multilevel) IRT models use a two-level structure: individual item/ability parameters nested within groups, with group-level parameters themselves drawn from a higher-level distribution; this enables *partial pooling*, shrinking each group's (e.g., each goal's) estimate toward the overall mean by an amount governed by that group's own sample size and the between-group variance — smaller/sparser groups get pulled more strongly toward the pooled estimate, larger groups are trusted more on their own data — [CASRAI: Bayesian Hierarchical Models: Partial Pooling](https://casrai.org/guides/bayesian-hierarchical-models); "accurate personalized profiles can be constructed even for individuals with sparse measurements, by embedding the item response model within a Bayesian hierarchical framework," improving parameter stability "especially in the context of small or noisy datasets" — [Bayesian Hierarchical Multidimensional IRT for Sparse Data, PMC8377345](https://pmc.ncbi.nlm.nih.gov/articles/PMC8377345/)
- Multilevel multidimensional IRT models have been proposed for settings with multiple correlated latent traits (e.g., reading/cognitive/computing ability) where test-takers (here: models) are nested within higher-level groups (here: could map to model families or providers) — [Bayesian multilevel multidimensional item response modeling, Communications in Statistics](https://www.tandfonline.com/doi/abs/10.1080/03610918.2021.1919707)

### Inferences
- There is no off-the-shelf "benchmark item → goal taxonomy" crosswalk in the literature the system can adopt wholesale; mapping SWE-bench/DS-1000/BigCodeBench/Terminal-Bench/LiveCodeBench items onto the system's own per-Goal ontology will likely need to be done manually or semi-automatically (e.g., via LLM-based tagging, analogous to SKILL-MIX's skill tags or the Skill-Index's skill-slices) rather than imported from a published mapping.
- The hierarchical partial-pooling technique is directly reusable regardless of how the goal mapping is done: once external benchmark evidence is (even approximately) tagged to goals, standard multilevel IRT/GLMM partial pooling — which the system's own model already resembles (model ability, goal difficulty, instance difficulty as nested random effects) — is the correct mechanism for letting sparse-evidence goals borrow statistical strength from related goals or from a global "general coding ability" level, rather than treating each goal as fully independent or fully pooled.
- Given the system already models goal difficulty and instance difficulty explicitly, the cleanest integration point for external evidence is likely: (1) tag/crosswalk external benchmark items to goals (skill-slice style), (2) treat "benchmark" and "scaffold" as additional random-effect/covariate levels in the same hierarchical model, (3) let existing partial-pooling machinery handle sparse per-goal external evidence.

### Gaps
- No primary source found describing a maintained, general-purpose "capability ontology" or item-to-skill crosswalk specifically for coding-agent benchmarks (SWE-bench, DS-1000, BigCodeBench, Terminal-Bench, LiveCodeBench) that the system could directly adopt — this appears to be a genuine open gap requiring either original tagging work or a targeted follow-up search (e.g., "SWE-bench task category taxonomy," "CWE/issue-type tagging SWE-bench").
- Did not find a paper directly combining SKILL-MIX-style skill decomposition with IRT-based ability estimation in one pipeline — the two lines of work (skill tagging, and IRT ability estimation) appear to still be separate in the literature as surfaced by this search pass.

## Uncertainty: propagating sample sizes and CIs from external leaderboards reporting only point estimates

### Takeaway
When only a point estimate (e.g., "62.3% pass@1") is published without n, standard practice is to reconstruct a binomial confidence interval from the implied number of benchmark instances (if the benchmark's total item count is known) using a proper interval method (Wilson score, not naive normal approximation), and recent leaderboard-specific work has begun formalizing rank-level uncertainty propagation (task-level CIs → leaderboard-level rank intervals via bootstrap/conformal methods) — but this remains a live methodological gap, with at least one paper stating flatly that unreported error bars should be treated as unpublishable-grade omissions.

### Cited Findings
- "Rank Intervals for Leaderboards: A Hierarchical Framework for Model Evaluation" (arXiv:2606.08679) identifies "a lack of unified mechanisms to propagate variability observed at the individual task level into the ranking at the leaderboard level," and introduces a hierarchical framework constructing model rank intervals with statistical guarantees at two levels: task-level rank confidence intervals derived from pairwise comparisons, and leaderboard-level rank prediction intervals via a conformal-prediction approach — [arXiv:2606.08679](https://arxiv.org/html/2606.08679v1)
- Standard practice for binomial accuracy metrics: report a confidence interval (e.g., 80/90/95%) around the point accuracy; practitioners have proposed Wilson-score 95% intervals for accuracy/precision/recall specifically because Wilson intervals behave better than the naive normal (Wald) approximation at extreme proportions (near 0% or 100%, common in saturated benchmarks), plus seeded deterministic item-level bootstrap CIs for F1/MCC-style metrics; an "add two successes and two failures" adjusted-Wald approach is also used as a simple closed-form alternative — summarized from search results on binomial CI construction, e.g. [AFIT: Recommended Confidence Intervals for a Binomial Proportion](https://www.afit.edu/STAT/statcoe_files/12_Binomial%20proportion%20intervals%20DRAFT%20-%20PA%20copy(1).pdf), [MachineLearningMastery: report classifier performance with CIs](https://machinelearningmastery.com/report-classifier-performance-confidence-intervals/)
- The stratified-bootstrap methodology from Agarwal et al. 2021 (see first section) is explicitly designed to propagate per-run/per-task sampling variability into an aggregate confidence interval and is reusable wherever multiple runs (even a handful) exist per (model, benchmark) cell — [arXiv:2108.13264](https://arxiv.org/abs/2108.13264)

### Inferences
- The most defensible default for external leaderboard evidence with only a point estimate `p̂` and a known/inferable item count `N`: construct a Wilson-score interval from `(p̂, N)` and feed that as an approximate effective sample size / precision into the recommender's Bayesian update, rather than treating the reported percentage as if it came with infinite precision. If `N` itself is unknown, the system should treat that evidence as low-confidence (wide prior, heavily shrunk toward the pooled/global estimate via partial pooling) rather than fabricate a precision.
- Where a benchmark reports pass@k rather than pass@1 with no n/c breakdown (a common case per the SWE-bench/Terminal-Bench findings above), uncertainty propagation is compounded: the point estimate is already a transformed statistic, and Wilson-style intervals computed naively on the pass@k value would understate true uncertainty. This is a compounding risk the objective's own framing anticipated ("propagate sample sizes and CIs... that report only point estimates") — the literature surfaced here does not yet offer a turnkey solution for the pass@k+unknown-n case specifically.
- The rank-interval / conformal-prediction line of work (arXiv:2606.08679) is the most directly relevant emerging primary source for the "how do I get a calibrated uncertainty out of a leaderboard" question, but it targets *rank* uncertainty (position on a leaderboard) rather than *ability-scale* uncertainty (posterior variance on a latent ability parameter) — the recommender needs the latter, so this would need adaptation rather than direct reuse.

### Gaps
- Could not find a primary source (in this pass) giving a standard method for inferring an *effective* sample size / precision for a benchmark score when even the item count N is not disclosed by the leaderboard (common for closed/proprietary leaderboards) — likely requires either contacting benchmark maintainers for N, using the known published benchmark size (e.g., SWE-bench Verified = 500 instances) as a proxy N when the specific run's N isn't stated, or explicitly modeling "leaderboard-reported, N unknown" as its own low-trust evidence tier.

## Overall Recommendation (synthesis for the report writer)

Based on the above, a defensible design for importing external benchmark evidence into the per-goal Bayesian recommender:

1. **Do not use min-max/human-baseline normalization** as the primary comparability mechanism (no stable baseline exists for coding-agent benchmarks, and the RL literature shows this method can invert rankings when baselines are unstable).
2. **Prefer an IRT-style latent-ability layer** (à la tinyBenchmarks/metabench/Rosetta Stone/ECI) to convert heterogeneous benchmark scores onto one latent "coding ability" scale, feeding that as a prior/covariate into the system's own hierarchical GLMM rather than replacing it — this is the most validated, most-replicated approach in the 2024-2026 literature (tinyBenchmarks, metabench, observational scaling laws, Epoch AI's ECI and Rosetta Stone all converge on IRT or closely related factor-analytic methods).
3. **Treat harness/scaffold as an explicit random-effect covariate**, never assumed away — the harness-disclosure literature (2605.23950, 2609.11987, 2609.09218) shows scaffold-only variance of 8-15+ points on SWE-bench-family benchmarks, large enough to dominate true model-ability differences if ignored.
4. **Normalize pass@k to a common k via Chen et al.'s exact combinatorial estimator** wherever n and c are disclosed; where only a final pass@k is published with no n/c, flag as a lower-trust evidence tier.
5. **Use contamination-aware (rolling-window) benchmarks like LiveCodeBench preferentially**, and treat static/older benchmarks (HumanEval, original DS-1000, non-Verified SWE-bench splits) as needing an explicit contamination-risk discount or covariate.
6. **Map benchmark items to goals via manual/semi-automated skill-tagging** (SKILL-MIX/Skill-Index style), since no ready-made crosswalk exists in the literature, then let the existing hierarchical structure's **partial pooling** (standard multilevel IRT/GLMM technique) handle sparse per-goal external evidence by shrinking toward related-goal or global estimates.
7. **Propagate uncertainty from point estimates via Wilson-score CIs** when item count N is known or inferable (e.g., published fixed benchmark sizes like SWE-bench Verified's 500 instances); when N is unknown, treat the evidence as low-precision/low-trust by default rather than assuming implicit high confidence.
