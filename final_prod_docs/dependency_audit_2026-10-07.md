# Dependency vulnerability audit, 2026-10-07

**What this is:** a one-time scan for publicly known vulnerabilities (CVE/GHSA/PYSEC advisories) in dependency versions. It is not a code review and not a penetration test. Nothing in the repo was changed. Tools: `pip-audit 2.10.1` (OSV data), `npm audit --package-lock-only`.

## Read this first: what was and was not scanned

- **Python:** `backend/requirements*.txt` are **not pinned** (for example `anthropic`, `jax>=0.11.2`, `boto3>=1.34`), so pip-audit cannot scan them directly. I scanned the **Python environment on the author's machine** (575 packages, which also holds Jupyter, Django, LangChain, Streamlit and other development tools). That environment is **not** the deployed image. A Docker build with unpinned requirements installs whatever is newest on build day, so the deployed image may have none of these versions.
- **npm:** scanned from the lockfiles (`prod_frontend/package-lock.json`, `frontend/package-lock.json`). `packaging/npm` has no lockfile and was not scanned.
- Advisory counts are per advisory ID in OSV, many of which repeat across sources. Applicability of each advisory to how we use the package was **not** checked.

## What I recommend

1. **Pin the MCP server's dependencies.** Create `requirements-mcp.txt` with exact versions (and hashes if possible), generated by `pip-compile` or `uv pip compile` from a clean environment, and build the image from it. This makes the scan meaningful and the build reproducible, and it is also the size fix noted earlier (several large packages in `requirements.txt` are unused by the MCP server).
2. **Re-run pip-audit against that file**, then fix findings in this order: PyJWT, cryptography, anything on the request path (`urllib3`, `h2`, `pyasn1`, `python-jose`).
3. **Check whether `python-jose` and `ecdsa` are installed in the image at all.** `python-jose` has an advisory with no fix; if it is only a transitive dependency we do not use, remove it.
4. **Upgrade `next` and `sharp` in `prod_frontend`** (`next` to 16.4.0 is a minor/major bump to test), then re-run `npm audit`. The `frontend/` app is older; decide whether to keep deploying it. Upgrade `vitest` separately (dev-only, lower urgency).
5. **Make it routine.** The repo already has a weekly `security` workflow (audits and SBOMs). Check its latest run: it should fail the build on a high or critical finding in a shipped dependency, and it should scan the pinned file, not a developer's environment.
6. **Do not report these counts to a customer.** They describe a development machine. Report the result of step 2 instead.
